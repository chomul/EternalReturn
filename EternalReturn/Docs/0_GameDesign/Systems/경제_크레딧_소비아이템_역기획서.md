## 0. 이 시스템의 정체

**소비 아이템은 회복 수단이 아니라 "교전 후 복귀 시간"을 통제하는 장치다.**
음식은 즉시 회복이 아니라 **15초짜리 버프**로 들어오고, **전투 중에는 효율 70%**, **최대 2중첩**이다.
즉 게임은 "체력을 얼마나 채우냐"가 아니라 **"다음 교전까지 몇 초가 필요하냐"** 를 설계하고 있다.
음식을 많이 들고 있는 팀은 회복량이 아니라 **교전 회전율**을 사는 것이다.

**크레딧은 파밍 실패를 돈으로 보정하는 장치다.**
장비 문서 §4.1이 "원격 드론(10 크레딧)이 파밍 실패의 복구 수단"이라고 짚은 것의 심화판이 이것이다.
크레딧은 **초당 자동으로 들어오는 시간 통화**이므로, 실력·운과 무관하게 **모든 플레이어에게 동일한 속도로 축적된다.**
그래서 크레딧으로 살 수 있는 것들(재료·부활·초월 방어구·탈출 카드)이 곧 **게임이 보장하는 하한선**이다.
파밍 경제(실력 편차 큼)와 시간 경제(편차 0)를 병렬로 돌리고, **역전 레버는 전부 시간 경제 쪽에 몰아놨다.**

> **구현 관점의 결론:** 소비 아이템은 "회복 함수"가 아니라 **틱 버프 + 중첩 규칙 + 보정 계수**의 조합이다.
> 크레딧은 "돈"이 아니라 **매치 타이머에 종속된 파생 자원**이다. 둘 다 서버 권위로만 갱신된다.

## 1. 매치 내 크레딧 vs 매치 외 재화 (혼동 방지)

| 재화 | 스코프 | 저장 위치 | 매치 종료 시 |
|---|---|---|---|
| **크레딧 (Credit)** | **매치 내부 전용** | `APlayerState` (매치 인스턴스) | **소멸** |
| A-Coin / NP / ER 포인트 / 시즌 토큰 / 데이터 조각 | 계정 | 백엔드 계정 DB | 영구 보존 |

> ⚠ **이름이 비슷해서 섞기 쉽다.** 크레딧은 게임 서버가 관리하고, 나머지는 **게임 서버가 건드리면 안 되는 계정 재화**다.
> 데디케이티드 서버 구조에서 이 둘을 같은 컴포넌트에 넣으면 치팅·정합성 사고가 난다.

**구현 메모**
- 크레딧: `APlayerState`에 `Replicated int32`. 매치 종료 시 폐기. 계정 DB 접근 없음.
- 계정 재화: 게임 서버가 아니라 **로비/백엔드 책임**. 이 문서 범위 밖이며, 매치 서버 코드에 API를 만들지 않는다.
- 크레딧 잔액은 **서버만 쓴다.** 클라는 복제된 값을 읽어 UI에 표시할 뿐, 예측 차감하지 않는다.

> ⚠ **출처 불일치**: 나무위키는 희귀를 **550~622**, 영웅을 **600~750**으로 **구간**으로 기술한다.

### 2.3 회복 규칙 (⭐ 여기가 구현의 본체다)

| 규칙 | 값 | 성격 |
|---|---|---|
| 적용 방식 | 섭취 시 아이템 소비 → **초당 1회 틱, 총 15초 버프** | 즉시 회복 **아님** |
| 틱당 회복량 | 총 회복량 ÷ 15 (산출값) | 예: 전설 800 → 초당 약 53.3 |
| **최대 중첩** | **2중첩**. 섭취 순서대로 적용 | 3개째 섭취는 낭비 |
| **날씨 보정** | 루미아 섬 **맑음 시 모든 음식 +20%** | 전역 상태 → 곱연산 |
| **전투 보정** | **전투 중 회복 효율 70%** | 틱 시점의 전투 상태로 판정 |
| 최대 보유 | 대부분 **6개** | ⚠ 아래 불일치 참조 |

> ⚠ **최대 보유 개수 출처 불일치**: 상위 문서는 **6개**, 나무위키는 "0.51에서 6개로 증가 → 정식 출시 후 **4개**로 감소"로 기술한다.
> **12.2 시점의 값은 (미확인).** 인게임 확인 필요.

**계산 순서가 결과를 바꾼다.** 아래 순서를 데이터가 아니라 **코드로 고정**해야 한다.

```
틱당 회복 = (아이템 회복량 / 15초)
          × (맑음이면 1.2)
          × (전투 중이면 0.7)
```

> **전투 판정 시점이 핵심이다.** 섭취 시점에 한 번 판정하는가, **매 틱마다 판정하는가**에 따라
> "안전한 곳에서 먹고 교전에 들어간다"는 플레이가 성립하는지가 갈린다. **(미확인 — 반드시 인게임 확인)**
> 상위 문서 §3.2.7의 휴식(Rest)이 "피격 시 캐스팅 취소"인 것과 대비하면, 음식은 **취소 개념 없이 효율만 깎이는** 쪽으로 보인다.

### 2.4 ⚠ 스태미나(음료)에 대한 중대한 정정

나무위키는 **"스태미나 시스템이 시즌 9에서 완전히 삭제되어 음료 분류 아이템이 전부 삭제됐다"** 고 기술한다.
상위 문서 §3.2.7의 휴식 시스템이 회복하는 **기력(SP)** 은 스킬 자원이며, **삭제된 스태미나와 다른 자원**이다.

| 자원 | 현재 상태 | 회복 수단 |
|---|---|---|
| **체력(HP)** | 존재 | 음식, 휴식(X), 비전투 자동 회복 |
| **기력(SP)** | 존재 | **휴식(X) 캐스팅**, 비전투 자동 회복 (0.5초당 최대치 2%) |
| ~~스태미나~~ | ❌ 시즌 9 삭제 | — (음료 아이템 동반 삭제) |

> ⭐ **클론 개발 판단:** **음료(스태미나 회복) 아이템 카테고리를 만들지 마라.** 원작이 이미 걷어냈다.
> 기력 회복은 **소비 아이템이 아니라 휴식 시스템의 역할**이다. 이 경계를 흐리면 "교전 후 복귀 = 휴식 캐스팅"이라는 원작 설계가 무너진다.
> 단, 소비 아이템 중 기력을 회복시키는 개별 아이템이 남아 있는지는 **(미확인)** — 스키마에는 자리만 열어둔다.

| 아이템 | 효과 | 12.x 변경 | 비고 |
|---|---|---|---|

| **감시 카메라 / 드론** | 시야 확보 | 12.0에서 설치 판별·표시 개선 | 밤에 가치 급등 |
| **조명탄총 R** | **초월 보급 상자 호출** | — | 3일차 밤 보급 상자에 포함 |
| ~~CNOT 게이트(가젯)~~ | — | ❌ **12.0 삭제** | |

> **주의:** 위 아이템 대부분은 "회복"이 아니라 **월드에 오브젝트를 스폰**한다(안전지대·카메라·보급상자).
> 즉 **음식과 같은 시스템이 아니다.** 데이터 테이블은 하나로 묶되, **실행 경로는 `회복 버프 부여` / `액터 스폰`으로 분기**시켜야 한다.

**구현 메모**
- 회복은 **틱 기반 버프**로 구현. 즉시 `Heal()` 호출 금지 — 중첩·날씨·전투 보정이 전부 틱 시점에 걸린다. `FTimerManager` 반복 타이머 사용, `Tick` 금지.
- 중첩 2 제한은 **버프 컨테이너에서 관리**. 3번째 섭취는 서버가 **거부**해야 한다(아이템 소모 없이). 소모 후 무효화면 유저가 손해를 본다.
- 아이템 소비·회복 적용 전부 **서버 권위**. 클라는 사용 요청 `Server` RPC(`WithValidation`)만 보내고, 인벤토리에서 임의로 개수를 깎지 않는다.
- 연출(먹는 모션·사운드)만 `NetMulticast`. 회복 수치는 복제된 체력으로 자연히 반영된다.
- 회복 계산은 **한 함수에 모은다.** 데미지 파이프라인과 대칭인 "회복 파이프라인"이 필요하다 (CLAUDE.md §8: 계산을 흩뿌리지 않는다).

### 3.3 균형 구조 분석 — 크레딧의 실제 단위는 "초"다

크레딧은 시간으로 자동 축적되므로 **모든 가격을 초로 환산할 수 있다.** (2일차 이후 2초당 1 기준 산출)

| 상품 | 가격 | **= 순수 대기 시간** |
|---|---|---|
| 일반 재료 1개 (드론) | 10 | **20초** |
| 금지 구역 복원 | 20 | **40초** |
| 루프 카드 키 / 초월 방어구 | 100 | **200초 (3분 20초)** |
| 부활 1회 | 200 | **400초 (6분 40초)** |
| VF 혈액 샘플 | 500 | **1,000초 (16분 40초)** |

여기서 세 가지가 읽힌다.

**① 인플레이션 통제는 "가격"이 아니라 "개방 시점"으로 한다.**
1~2일차 낮까지는 **키오스크가 아예 닫혀 있고 부활도 무료(자동)** 다. 즉 **초반에는 소비처가 사실상 드론뿐이다.**
크레딧이 쌓이는 것을 막는 대신, **쓸 곳이 열리는 시각을 뒤로 미뤄** 후반에 한꺼번에 회수한다.
`2일차 정오 키오스크 개방 → 3일차 부활 유료화 → 4일차 VF 500` 순으로 **싱크(sink)가 계단식으로 열린다.**

**② 획득 속도 자체가 시간에 따라 감속된다.**
1일차 1.5초당 1 → 2일차 이후 2초당 1. **후반일수록 크레딧이 귀해진다.**
가격을 올리는 게 아니라 **수입을 줄이는** 방식의 인플레 억제이며, 결과적으로 후반 1크레딧의 실질 가치가 상승한다.

**③ 부활 200이 경제의 기준점이다.**
부활(200) = VF의 40%, 드론 재료 20개분, 순수 대기 6분 40초.
즉 **"한 번 죽는 비용 = 초월 재료 절반"** 이다. 3일차 이후 사망 페널티가 실질화된다는 상위 문서 §2의 서술이
경제 수치로도 그대로 확인된다. **크레딧 밸런싱을 건드릴 때 기준으로 잡을 값은 부활가 200이다.**

> ⚠ **수지가 실제로 맞는지는 계산할 수 없다.** 총 수입을 내려면 1·2일차 낮/밤 길이가 필요하고,
> 킬·사냥 크레딧이 (미확인)이라 **전투 수입 비중을 알 수 없다.** 이 문서는 **구조만** 확정하고 총량은 열어둔다.

**구현 메모**
- 시간 수입은 `Tick`이 아니라 **`FTimerManager` 반복 타이머**. 게임 서버에서 1개만 돌린다 (CLAUDE.md §2).
- 일차 전환 시 **타이머 간격을 교체**한다(1.5초 → 2.0초). 수입률은 매치 페이즈 상태에 종속된다.
- 구매는 전부 `Server` RPC + `WithValidation`. 검증 순서: **잔액 확인 → 개방 시점 확인 → 차감 → 지급**. 클라 예측 차감 금지.
- 금지 구역 복원의 **"페이즈당 1팀"** 은 팀 단위 락이다. 동시 요청 경합이 발생하므로 **GameState에서 단일 권위**로 처리.
- 크레딧은 **팀 공유가 아니라 개인 소유**로 보인다(부활을 개인이 지불). **(미확인 — 팀 공유 여부 확인 필요)**. 스키마상으로는 `PlayerState` 소유가 안전하다.

## 4. 인벤토리 운용

| 항목 | 값 |
|---|---|
| 장비 슬롯 | **5** (무기 1 + 방어구 4) — 장비 문서 §2 |
| **소지품(가방) 칸 수** | **(미확인)** |
| 무게 제한 | **(미확인)** — 존재 여부조차 불명 |
| 음식 최대 보유 | **6개** (⚠ 4개 설과 불일치, §2.3) |
| 스택 규칙 | 아이템별 최대 보유 개수 존재 → **아이템 단위 스택 상한** |
| 사용 방식 | 단축키 기반 사용 (정확한 키 배열 미확인) |

**확인된 것은 "칸이 부족하다"는 압박이 실제로 존재한다는 사실뿐이다.**
공략에서 반복적으로 "인벤토리가 넘치지 않는 선에서 음식을 모아두라"는 조언이 나온다.
즉 **가방 칸 = 전략 자원**이며, 제작 재료와 소비 아이템이 **같은 공간을 두고 경쟁**한다.

> **이것이 소비 아이템 밸런싱의 숨은 축이다.** 음식 6개를 들면 재료 6칸을 못 든다.
> 회복량만 보고 밸런싱하면 이 기회비용이 통째로 빠진다.

**구현 메모**
- 인벤토리는 **서버 권위 배열**. 클라 UI는 복제본을 그린다. 드래그·정렬도 서버 검증 후 반영.
- 스택 상한은 하드코딩 금지. **`FConsumableRow.MaxStack`** 으로 뺀다 — 패치마다 바뀐 이력이 있는 값이다(6 ↔ 4).
- 칸 수는 (미확인)이므로 매직넘버를 박지 말고 **설정값**으로 둔다. 나중에 원작 수치를 넣을 자리를 만들어 놓는다.
- 사망 시 아이템 드롭(상위 문서 §8.7-3)이 소비 아이템에도 적용되는지는 **(미확인)**.

## 데이터 스키마 제안

**핵심 원칙: "이동 중 사용 가능?", "피격 시 취소?" 같은 규칙을 코드 분기가 아니라 데이터로 다룬다.**
원작이 패치마다 바꾸는 것이 정확히 이 규칙들이기 때문이다(휴대용 안전지대 7초→5초, 휴식 취소 조건·캐스팅 시간 등).

```
FConsumableRow : FTableRowBase
  ItemName        : FName
  Grade           : EItemGrade          // 장비 문서와 동일 enum 재사용
  UseType         : EConsumableUseType  // Heal / SpawnActor / Utility  ← 실행 경로 분기

  // --- 회복 ---
  HealAmount      : float               // 총 회복량. 등급이 아니라 아이템 단위 (§2.1 불일치 대응)
  SpHealAmount    : float               // 기력 회복 (현재 확인된 소비 아이템 없음. 자리만 확보)
  HealDuration    : float = 15.0f       // 지속 시간(초)
  HealTickInterval: float = 1.0f        // 틱 주기(초)
  MaxBuffStack    : int32 = 2           // 버프 중첩 상한

  // --- 사용 규칙 (전부 데이터) ---
  CastTime        : float               // 사용(캐스팅) 시간. 0이면 즉시  ← (미확인)
  bUsableWhileMoving : bool             // 이동 중 사용 가능?             ← (미확인)
  bCancelOnDamage    : bool             // 피격 시 취소?                  ← (미확인)
  bCancelOnCC        : bool             // 군중제어 적중 시 취소?
  CancelCooldown     : float            // 취소 후 재사용 대기 (휴식은 1초)

  // --- 보정 ---
  bAffectedByWeather : bool             // 맑음 +20% 적용 대상?
  CombatEfficiency   : float = 0.7f     // 전투 중 효율 배수

  // --- 인벤토리 / 제작 ---
  MaxStack        : int32               // 최대 보유 개수 (6 또는 4)
  CraftMaterialA  : FName               // 장비 문서 §6.2와 동일하게 항상 2개 조합
  CraftMaterialB  : FName

  // --- SpawnActor 계열 (휴대용 안전지대 · 감시 카메라 등) ---
  SpawnedActorClass : TSoftClassPtr<AActor>
  SpawnDuration     : float             // 안전지대 5초 등
  EnergyCost        : int32             // 가젯 에너지 (안전지대 50)
```

```
FCreditPriceRow : FTableRowBase
  ProductId       : FName
  Price           : int32               // 부활 200 / VF 500 / 드론 10 …
  DiscountRegion  : FName               // 병원 = 50 할인
  DiscountAmount  : int32
  OpenDay         : int32               // 개방 일차  ← 인플레 통제의 실체(§3.3-①)
  bOncePerPhasePerTeam : bool           // 금지 구역 복원 전용 락
```

> **왜 이렇게 쪼개는가:** 12.0~12.2 패치노트에서 실제로 바뀐 값은
> `지속 시간 / 에너지 코스트 / 회복 비율 / 획득 주기 / 부활 체력%` 뿐이다. **구조는 그대로고 숫자만 바뀐다.**
> 이 값들이 전부 데이터 테이블에 있으면 패치 대응이 **재빌드 없이 CSV 교체**로 끝난다.

> **GAS 구현 (`CLAUDE.md` §8):** `HealAmount / HealDuration / HealTickInterval / MaxBuffStack` 은
> **`UGameplayEffect` 의 `Period` · `Duration` · `Stacking Policy` 에 그대로 대응된다.**
> 즉 **틱 회복 버프를 직접 만들지 않는다** — 주기 실행·중첩 상한·만료가 전부 GE 기능이다.
> ⭐ 각 아이템 클래스가 직접 체력을 더하게 만들면 클램프(`PreAttributeChange`)와 회복 보정 파이프라인을 우회한다.
> 날씨·전투 중 보정은 GE의 Modifier 또는 별도 Execution 한 곳에 모은다.

## 구현 우선순위

```
1순위. 크레딧 자원 (PlayerState Replicated + 일차별 타이머 수입)
       → 검증: 1일차 1.5초당 1, 2일차 이후 2초당 1로 서버에서 증가하고 클라 UI에 복제됨
2순위. 소비 아이템 데이터 테이블(FConsumableRow) + 인벤토리 스택/상한
       → 검증: 음식 MaxStack 초과 획득이 서버에서 거부됨
3순위. 틱 기반 회복 버프 (15초 / 초당 1회 / 2중첩 상한)
       → 검증: 전설 음식 섭취 시 15틱에 걸쳐 총 800 회복, 3개째 섭취가 아이템 소모 없이 거부됨
4순위. 회복 보정 파이프라인 (맑음 +20%, 전투 중 ×0.7)
       → 검증: 날씨·전투 상태 변경 시 틱당 회복량이 산식대로 변함
5순위. 크레딧 구매 (FCreditPriceRow + 서버 검증: 잔액 → 개방시점 → 차감 → 지급)
       → 검증: 2일차 정오 전 키오스크 구매가 거부되고 크레딧이 차감되지 않음
6순위. 원격 전송 드론 (일반 재료 10 크레딧)  ← 장비 문서 §6.3의 7순위와 동일 항목
       → 검증: 크레딧 10 차감 후 지정한 일반 재료가 인벤토리에 들어옴
7순위. 부활 구매 200 / 병원 150 + 3~5일차 게이팅
       → 검증: 3일차 진입 전에는 자동 부활, 이후 크레딧 지불 부활로 전환
8순위. SpawnActor 계열 소비 아이템 (휴대용 안전지대 · 감시 카메라)
       → 검증: 서버가 액터 스폰, 5초 후 소멸, 모든 클라이언트에 보임
```

> **회복(3·4순위)이 구매(5순위)보다 먼저다.** 순서를 바꾸면 "살 건 많은데 살아남을 수단이 없는" 상태로 테스트하게 된다.
> 멀티 검증은 전부 `Play As Client / Number of Players: 2` 이상에서 확인한다.

|---|---|---|
| **음식 사용(캐스팅) 시간** | 교전 중 사용 가능 여부 = 설계의 핵심 | 인게임 계측 |
| **이동 중 사용 가능 여부** | 도주 중 회복 성립 여부 | 인게임 |
| **피격 시 취소 여부** | 교전 회전율 전체 | 인게임 |
| **전투 판정 시점 (섭취 시 1회 vs 매 틱)** | 전투 중 효율 70%의 실제 체감 | 인게임 계측 |
| **인벤토리 칸 수 / 무게 제한 유무** | 인벤토리 시스템 전체 설계 | 인게임 |
| **음식 최대 보유 6개 vs 4개** | 스택 상한 | 인게임 (⚠ 출처 불일치) |
| **개별 음식 전수 목록 + 아이템별 실제 회복량** | 밸런싱. 현재 등급 대표값만 확보 | 인게임 / 아이템 DB |
| **킬·어시 크레딧 (위키 10/6, 패치 시점 불명)** | 전투 수입 비중 | 12.x 패치노트 / 인게임 |
| **야생동물 사냥 크레딧** | 파밍 수입 비중 | 인게임 계측 |
| **크레딧 팀 공유 여부** | 부활 비용 부담 주체 | 인게임 |
| **1·2일차 낮/밤 실제 길이** | 총 크레딧 수입 산출 불가 상태 | 상위 문서 §2 타임라인 교차 확인 |
| 기력(SP) 회복 소비 아이템 잔존 여부 | 스키마 `SpHealAmount` 사용 여부 | 인게임 |
| 코발트 합성기 개방 시점 | 초월 방어구 획득 타이밍 | 인게임 |
| 소비 아이템의 사망 시 드롭 여부 | 킬 보상 구조 | 인게임 |
| 음식 등급별 제작 재료 트리 | 제작 시스템 연동 | 아이템 DB |
| 소비 아이템 단축키 배열 | UI / 입력 | 인게임 |

> **추측값을 넣지 않았다.** 특히 회복량 외 수치(캐스팅 시간·칸 수·사냥 크레딧)는 **하나도 확인되지 않았다.**
> 채울 때는 "원작 확인값이 아니라 자체 결정값"임을 반드시 기록할 것.
