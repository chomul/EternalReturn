## 0. 이 시스템의 정체

**탑다운 MOBA에서 입력 레이어가 하는 일은 하나 — 화면 좌표 하나를 "무엇에 대한 의도인가"로 분류하는 것이다.**
같은 클릭이 상황에 따라 이동 명령, 공격 대상 지정, 스킬 착탄점, 핑, UI 클릭, 아이템 요청으로 갈린다.
원본 §11.2·§11.3이 남긴 조작 목록이 그대로 보여준다 — **좌클릭 하나에 이미 `Alt`·`Ctrl`·드래그 세 수식자가 붙어 있다.**

| 원본에서 확인된 조작 | 의미 | 출처 |
|---|---|---|
| `Alt + 좌클릭` | 일반 지시 · 대상 지정 핑 | §11.2 |
| `Ctrl + 좌클릭` | 중요 위치 상시 핑 | §11.2 |
| `Ctrl + 좌클릭 드래그` | 팀 커뮤니케이션(요청/감사) | §11.2 |
| `Alt + 클릭` | 팀원에게 아이템 요청 (제작 UI) | §11.3 |
| 말풍선 **우클릭** | 아이템 요청 응답 | §11.3 |
| `M` / `Alt + M` / `F8` | 확장맵 / 파밍 오버레이 / 오버레이 토글 | §11.2 |
| `X` | 휴식 캐스팅 (취소 조건에 **이동 입력** 포함) | §3 |
| `Ctrl + Alt + 우클릭` | **연습 모드 즉시 이동** (12.2) | §11.6 |
| 기본 공격 | **클릭 대상 지정 방식**, 사거리는 무기 계열이 결정 | §7.5 |

> **원본은 키 목록을 준 적이 없다.** 위 표는 다른 시스템을 설명하다 흘린 조작 서술을 전수 수집한 결과이고, §7의 키 표는 **원본 복원이 아니라 이 9개 관측점에서 역산한 설계안**이다.

> ⭐ **이 문서가 지켜야 할 제약 (원본 §12.3 / §12.4):** 12.0 휴식 개편은 *"초보자가 쉽게 파악하도록"* 이라는 선의로 시작했으나 **숙련자의 조작 리듬을 파괴해 커뮤니티 투표 87%가 롤백을 요구**했고 12.1에서 병존으로 봉합됐다. 원본 §12.4는 이를 **"핵심 조작 리듬을 건드리는 개편은 즉시 이탈로 이어진다"** 로 정리한다.
> → **이동·스킬 조작의 기본형은 초기에 정하고, 이후 변경은 옵션 추가(병존)로만 한다.**

## 1. ⭐ 최상위 결정 — 이동 입력 방식

**이 절이 §2~§9 전부를 결정한다. 그래서 맨 앞에 있다.**

### 1.1 원본에서 확인 가능한 것

**원본에 "우클릭으로 이동한다"는 직접 서술은 없다. (미확인)** 정황은 셋이다.

| 정황 | 내용 | 출처 |
|---|---|---|
| ① 장르 정의 | *"쿼터뷰(탑다운) MOBA의 **조작**·성장·전투 문법"* 계승 명시 | §1.1 |
| ② **연습 모드 즉시 이동 = `Ctrl+Alt+우클릭`** | **이동 계열 기능이 우클릭 조합 위에 얹혀 있다** | §11.6 (12.2 신규) |
| ③ 좌클릭이 이미 점유됨 | `Alt+좌클릭`·`Ctrl+좌클릭`·`Ctrl+좌클릭 드래그`가 전부 핑·지시 | §11.2 |

> ②가 가장 강한 정황이다. ③은 좌클릭 계열이 통신·지시 축에 몰려 있음을 보여준다. **그러나 정황이지 확인이 아니다.**

### 1.2 〔제안〕 마우스 우클릭 이동을 기본형으로 한다

| 축 | **A. 우클릭 이동** 〔제안·채택〕 | B. WASD 이동 |
|---|---|---|
| 원본 정합 | ①②③과 모순 없음 | ②의 `Ctrl+Alt+우클릭 즉시 이동`을 설명하지 못함 |
| 기본 공격 | §7.5의 **"클릭 대상 지정"** 과 같은 버튼에 통합 가능 | 별도 버튼 필요 → 원본 서술과 어긋남 |
| 카메라 | 캐릭터 추적 + 마우스 자유 → §6과 정합 | 이동 방향과 조준 방향이 분리돼 설계가 달라짐 |
| 스킬 조준 | 커서가 조준의 유일한 입력원 → 일관됨 | 커서 조준 + 키보드 이동 병행. 조작 부하↑ |
| 네트워크 | **목적지 1개만 전송 가능**(§3) → 대역폭 유리 | 매 프레임 입력 전송(CMC 기본 경로) |
| 구현 비용 | 좌표 변환 + 경로 추종 필요 | 엔진 기본 경로 그대로. **더 쉽다** |

**결론 〔제안〕: A를 기본형으로 하고 WASD는 구현하지 않는다.** 근거는 "원본 정합" 행 — B를 고르면 §0의 관측 9개 중 최소 3개를 버려야 한다.

> ⚠ **`Ctrl+Alt+우클릭`이 "우클릭 이동 위에 얹힌 수식자"라는 해석 위에서만 성립한다.** 이 해석이 틀리면 §7 전체를 다시 짜야 한다 — **인게임 확인 1순위**.

## 2. 클릭 이동의 구현 경로 — 엔진이 이미 주는 것부터

`CLAUDE.md` §1 — 직접 구현 전에 엔진 제공 기능부터 본다. 필요한 조각은 **전부 엔진에 있다.**

| 단계 | 엔진 API | 위치 (`C:/UnrealEngine-5.4.4/Engine/Source/Runtime/`) |
|---|---|---|
| 커서 표시 / 클릭 이벤트 | `bShowMouseCursor` · `bEnableClickEvents` · `bEnableMouseOverEvents` | `Engine/Classes/GameFramework/PlayerController.h:553` · `:557` · `:565` |
| **커서 아래 월드 지점** | `GetHitResultUnderCursorByChannel(...)` | 같은 파일 `:738` (역투영 대안 `:761`) |
| 경로 계산 | `UNavigationSystemV1::FindPathToLocationSynchronously(...)` | `NavigationSystem/Public/NavigationSystem.h:527` |
| 경로 추종 | `RequestMove(...)` · `OnRequestFinished` · `SetAcceptanceRadius(...)` | `AIModule/Classes/Navigation/PathFollowingComponent.h:248` · `:229` · `:335` |
| 원샷 헬퍼 | `UAIBlueprintHelperLibrary::SimpleMoveToLocation(AController*, const FVector&)` | `AIModule/Classes/Blueprint/AIBlueprintHelperLibrary.h:95` |
| 이동력 인가 | `APawn::AddMovementInput(Dir, Scale, bForce)` | `Engine/Classes/GameFramework/Pawn.h:474` |

`NavigationSystem` · `AIModule` · `EnhancedInput` · `InputCore`는 **이미 모듈 의존에 있다** — `Source/EternalReturn/EternalReturn.Build.cs:13`. 새 의존 추가 없이 전부 쓸 수 있다.

### 2.1 ⭐ `SimpleMoveToLocation`은 `AIController`를 요구하지 않는다

내부의 `InitNavigationControl`은 컨트롤러가 `AAIController`가 아니면 **`UPathFollowingComponent`를 런타임에 `NewObject`로 생성해 붙인다** — `AIModule/Private/Blueprint/AIBlueprintHelperLibrary.cpp:414-435`.
즉 **`APlayerController`에서 그대로 호출 가능하고, 플레이어 폰을 AI가 빙의할 필요가 없다.**

### 2.2 〔제안〕 세 가지 안

| 안 | 방식 | 평가 |
|---|---|---|
| A. `SimpleMoveToLocation` 한 줄 | 헬퍼 호출 | 가장 빠름. 단 컴포넌트가 **런타임에 몰래 생성**되고(`:428`) 시작·중단·완료 훅을 잡기 어려워 CC·스킬 캔슬과 엮기 나쁘다 |
| **B. `UPathFollowingComponent` 명시 선언 + `RequestMove`** 〔채택〕 | 생성자에서 컴포넌트 생성, 직접 요청 | `OnRequestFinished`(`:229`)로 도착·중단 콜백, `SetAcceptanceRadius`(`:335`)로 정지 거리 제어. **A와 같은 엔진 코드를 쓰되 통제권만 가져온다** |
| C. 경로 배열을 직접 들고 매 틱 `AddMovementInput` | 웨이포인트 수동 순회 | **`PathFollowingComponent`가 이미 하는 일의 재구현.** 코너 컷·재경로·회피를 전부 직접 짜야 한다. `CLAUDE.md` §1 위반 |

> **채택: B.** A는 프로토타입까지만 쓰고, CC·스킬과 엮이는 시점에 B로 옮긴다.
> C는 선택하지 않는다 — 참고로 커밋 `6100863`에 C 방식(경로 배열 + `PlayerTick` 순회)의 흔적이 있었으나 **해당 파일들은 현재 전부 삭제된 상태**이며 되살릴 대상이 아니라 재설계 대상이다.

## 3. ⭐⭐ 클릭 이동과 서버 권위 — 이 문서 최대의 논점

**클릭 이동이 언리얼 기본 이동 모델과 어긋나는 지점은 하나다: 경로를 누가 계산하는가.**

### 3.1 언리얼 기본 이동 모델 (엔진 사실)

`UCharacterMovementComponent`는 **소유 클라가 이동을 즉시 실행 → 압축 무브를 서버로 전송 → 서버가 오차 검사 후 보정**하는 구조다.

| 요소 | 위치 (`Engine/Classes/GameFramework/CharacterMovementComponent.h`) |
|---|---|
| 클라 → 서버 무브 전송 | `:2322-2330` (`CallServerMovePacked`) |
| 서버의 오차 검사·보정 | `:2338` (`ServerMoveHandleClientError`) |
| 클라 예측 데이터 | `:2271` (`ClientPredictionData`) |
| 보정 비활성 스위치 | `:954` (`bIgnoreClientMovementErrorChecksAndCorrection`) |

**이동 예측·보정은 이미 엔진이 해 준다.** `CLAUDE.md` §6의 "클라 예측은 요청받았을 때만"은 **새 예측 코드를 짜지 말라는 뜻**이지 CMC 기본 동작을 끄라는 뜻이 아니다.

### 3.2 클릭 이동이 만드는 균열

CMC가 보내는 것은 **"이 프레임의 가속 방향"** 이다. 클릭 이동에서 그 방향은 **경로의 다음 코너를 향한 방향**이다.
따라서 **경로를 서버와 클라가 각각 계산하는데 두 경로가 다르면, 매 프레임 방향이 어긋나고 서버 보정이 지속 개입한다 → 러버밴딩.**

**경로가 갈릴 수 있는 이유 (프로젝트 설정 관측):** `Config/DefaultEngine.ini:76-77`에 `[/Script/NavigationSystem.NavigationSystemV1]` / `bAllowClientSideNavigation=true` 가 **이미 설정돼 있다.** 이 값은 `ShouldLoadNavigationOnClient()`의 반환값이 되어 **클라도 내비 데이터를 로드**한다 — `NavigationSystem.h:335`, `:783`. 즉 **현재 설정에서 클라도 독자 경로 계산이 가능하다.** 축복이자 함정이다.

### 3.3 ⭐ 〔제안〕 권위 모델 — "목적지는 서버 권위, 경로는 양쪽 계산, 이동은 CMC 예측"

| 항목 | 결정 | 근거 |
|---|---|---|
| **전송하는 것** | **목적지 `FVector` 1개** (`ServerSetMoveDestination`, `WithValidation`) | 매 프레임 입력 대신 클릭당 1회. 24인 매치에서 대역폭이 선형으로 줄어든다 |
| **명령의 권위** | **서버.** 목적지 유효성(내비 위 지점인지, CC로 이동 금지인지)을 검증하고 서버의 `PathFollowingComponent`에 `RequestMove` | `CLAUDE.md` §6 |
| **경로 계산** | **서버·소유 클라가 각자 계산.** 단 **같은 목적지·같은 내비메시·같은 쿼리 필터** | `bAllowClientSideNavigation=true`(`DefaultEngine.ini:77`). 경로 전체 복제보다 싸다 |
| **이동 실행** | **CMC 기본 예측·보정 그대로.** 새 예측 코드 금지 | `CharacterMovementComponent.h:2322` 이하 |
| **비소유 클라(나머지 23명)** | 복제된 위치·속도만 보간. 경로 계산 안 함 | 23명분 패스파인딩을 각 클라가 돌릴 이유가 없다 |
| **목적지 복제** | **소유자 전용(`COND_OwnerOnly`)** | 남의 목적지를 받으면 **은신·부쉬에서 정보 유출** (전투 문서 §5.2 relevancy 원칙) |

> ⭐ **경로가 갈리는 조건은 실제로 존재한다** — 동적 장애물(설치물·소환물), 내비 갱신 타이밍 차, 부분 경로(partial path). 안전장치:
> 1. **서버가 항상 옳다.** 클라 경로는 예측 표시일 뿐, 어긋나면 CMC 보정이 이긴다.
> 2. **도착 판정은 서버만**(`OnRequestFinished`). 클라의 도착은 연출이다.
> 3. **경로 계산 실패 시 클라는 이동을 시작하지 않는다.** "일단 직선으로 간다"를 넣으면 벽을 뚫는 예측이 되고 매번 보정된다.
> 4. 어긋남이 반복 관측되면 **그때** 서버 경로 복제안(대역폭↑)을 별도 안건으로 올린다. 처음부터 만들지 않는다 (`CLAUDE.md` §2).

### 3.4 〔제안〕 하지 말아야 할 것

| 금지 | 이유 |
|---|---|
| 매 프레임 `ServerSetMoveDestination` | 클릭 이동의 유일한 장점을 버린다. **드래그 이동은 클라에서 목적지를 갱신하되 서버 전송은 스로틀링**한다 〔제안: 0.1초 또는 일정 거리 이상 변화 시. 정확한 값 **(미확인)**〕 |
| `bIgnoreClientMovementErrorChecksAndCorrection=true`(`:954`)로 보정 끄기 | 러버밴딩이 아니라 **치트 검증**이 사라진다 |
| 클라가 도착 판정 후 스킬 자동 실행 | 도착 시점이 서버와 다르면 사거리 밖에서 나간다. 도착→행동 연결은 **서버 `OnRequestFinished`에서만** |
| 클릭 이동을 `AERCharacterBase`에 구현 | 이동 명령은 **컨트롤러의 책임**. 캐릭터에 박으면 관전·리스폰에서 분리가 안 된다 |

## 4. 스킬 조준(타게팅) 조작

**"무엇을 표시하는가"는 [`스킬_프레임워크_역기획서.md`](스킬_프레임워크_역기획서.md) 담당이다. 이 절은 "어떤 조작으로 무엇을 서버에 보내는가"만 다룬다.**
판정 타입은 [`../Characters/00_공통_구현규약.md`](../Characters/00_공통_구현규약.md) **§2.2** 를 따른다. **조작 열은 전부 〔제안〕.**

| 판정 타입 (§2.2) | 조작 〔제안〕 | 서버 페이로드 | 취소 |
|---|---|---|---|
| **대상 지정** | 키 → 커서 아래 적 확정 | `AActor* Target` | 우클릭 / `Esc` |
| **방향 지정 투사체(스킬샷)** | 키 → 커서 방향 확정 | `Direction` | 우클릭 / `Esc` |
| **위치 지정(착탄형)** | 키 → 커서 월드 지점, **사거리 클램프** | `Location` | 우클릭 / `Esc` |
| **부채꼴 / 직선 관통** | 방향 지정과 동일 | `Direction` | 동일 |
| **자기 중심 원형** | **즉시 시전** (조준 없음) | 없음 | 취소 불가 |
| **자기 이동(대시·도약)** | 방향 또는 위치 지정 | `Direction` / `Location` | 우클릭 / `Esc` |
| **설치물 / 소환물** | 위치 지정 | `Location` | 우클릭 / `Esc` |
| **충전형(홀드)** | 누름 유지 → 뗌. `ETriggerEvent::Started` → `Completed` | 두 이벤트 + **서버가 계산한** 충전 시간 | 유지 중 우클릭 |
| **리캐스트(재시전)** | 같은 키 2회. 첫 입력 후 일정 시간 컨텍스트 활성 | 2차 페이로드 | 시간 초과 시 자동 종료 |

> ⭐ **충전 시간은 반드시 서버가 잰다.** 클라가 "3초 눌렀다"를 보내면 그대로 조작 가능하다. 클라는 **누름·뗌 두 이벤트만** 보내고 서버가 자기 시계로 계산한다 (`CLAUDE.md` §6).
> ⭐ **사거리 클램프는 클라·서버가 같은 함수를 쓴다.** 클라 클램프는 인디케이터 표시용, **서버 클램프가 진짜다.** 함수가 둘이면 "표시된 곳과 다른 곳에 떨어지는" 버그가 난다.
> **큐잉(선입력)은 이 문서 범위가 아니다** — [`스킬_프레임워크_역기획서.md`](스킬_프레임워크_역기획서.md)로 넘긴다. 다만 입력 레이어의 계약 하나는 여기 있다: **"조준 중"은 클라 로컬 상태이며 복제하지 않는다.** 서버는 확정 페이로드만 받는다.

## 5. 스마트캐스트 〔제안〕

**원본에 스마트캐스트 서술은 없다. (미확인)** 아래는 전부 제안이다.

| 모드 | 조작 | 장점 | 단점 |
|---|---|---|---|
| A. 즉시 시전(스마트) | 키를 떼는 순간 커서 위치/방향으로 확정 | 입력 지연 0. 콤보 속도 유리 | 오조준 취소 불가 |
| B. 인디케이터 확정 | 키 → 인디케이터 → **좌클릭 확정 / 우클릭 취소** | 조준 정확. 학습 곡선 완만 | 입력 2회. 느림 |
| **C. 병존 (A 기본 + 스킬 슬롯별 토글)** 〔채택〕 | 설정에서 슬롯마다 A/B 선택 | 원본 §12.3의 **"병렬 추가"** 교훈과 정합 | 설정 UI + 상태 분기 필요 |

**채택 근거:** 원본 §12.3은 12.0 휴식 개편 실패를 **"온보딩 장치는 기존 시스템을 대체하는 게 아니라 병렬로 추가해야 한다"** 로 결론짓는다. A만 넣으면 신규 유저가 못 쓰고, B만 넣으면 숙련자 조작 리듬을 파괴한다 — **원본이 실패라고 기록한 바로 그 패턴이다.**

**구현 메모 〔제안〕**
- 스마트캐스트 설정은 **순수 클라 로컬**. 복제하지 않는다 (`UI_HUD_역기획서.md` §1 "로컬 전용 상태"와 동일).
- 서버 입장에서 A와 B는 **구분되지 않는다.** 둘 다 같은 RPC 페이로드(§4)를 보낸다. **서버 코드에 스마트캐스트 분기가 있으면 설계가 틀린 것이다.**
- B 모드 조준 중에는 우클릭이 이동이 아니라 취소로 소비된다 → 컨텍스트 우선순위(§8)로 처리한다.

## 6. 카메라 〔제안〕

**원본에 카메라 각도·높이·FOV·투영 서술은 전혀 없다. 전 항목 (미확인).** 확인된 것은 장르가 "쿼터뷰(탑다운)"라는 사실 하나(§1.1)뿐이다.

### 6.1 카메라 리그

| 항목 | 제안 | 엔진 근거 |
|---|---|---|
| 구성 | `USpringArmComponent` + `UCameraComponent` | — |
| 거리 | `TargetArmLength` | `Engine/Classes/GameFramework/SpringArmComponent.h:25` |
| **폰 회전 추종 끄기** | `bUsePawnControlRotation = false` — 캐릭터가 돌아도 각도 고정. **탑다운 필수 조건** | `:57` |
| **지형 충돌 테스트 끄기** | `bDoCollisionTest = false` — 켜면 나무·건물 밑에서 카메라가 튄다 | `:45` |
| 부드러운 추적 | `bEnableCameraLag` + `CameraLagSpeed` | `:76` / `:101` |
| **투영** | **원근 유지** 〔제안〕. 직교 전환은 가능하나 커서 역투영·높이 판정이 달라져 조준 코드가 복잡해진다 | `Engine/Classes/Camera/CameraComponent.h:141` (`ProjectionMode`) · `:39` · `:33` |

> **각도·높이·FOV 수치는 이 문서가 정하지 않는다((미확인)).** 결정 기준만 명확하다: **스킬 최대 사거리(6인 중 최대 = 시셀라 R 반경 20m, `00_공통_구현규약.md` §2.2)가 화면 안에 들어와야 한다.** 이 값이 카메라 높이의 하한을 만든다.

### 6.2 ⭐ 카메라 잠금 / 해제 — 구조 결정

| 상태 | 동작 | 조작 〔제안〕 |
|---|---|---|
| 잠금(기본) | 카메라가 내 캐릭터 추적 | — |
| 잠금 해제 | 가장자리 스크롤·미니맵 클릭으로 캐릭터를 떠남 | `Y` 토글 |
| 복귀 | 카메라를 캐릭터로 즉시 되돌림 | **`Space` 홀드=임시 복귀 / 탭=잠금 토글** |
| 맵 가장자리 스크롤 | 커서가 화면 테두리 N px 안이면 그 방향으로 이동 | 항상 활성 (끌 수 있어야 함) |
| 미니맵 / 확장맵 클릭 | 해당 월드 지점으로 카메라 이동 (**캐릭터는 안 움직인다**) | 좌클릭 |

> ⭐ **가장 중요한 구조 결정 〔제안〕: 카메라 위치는 폰의 위치가 아니라 "카메라 타깃 지점"이라는 별도 상태다.**
> 스프링암을 캐릭터에 직접 붙이면 잠금 해제·미니맵 클릭 이동을 만들 수 없다. → **`APlayerController`(또는 전용 카메라 액터)가 카메라 타깃을 소유**하고, 잠금 상태에서만 그 타깃이 폰을 따라간다.
> **이 상태는 전부 클라 로컬이며 복제하지 않는다.** 서버는 남의 카메라가 어디를 보는지 알 필요가 없다.

### 6.3 카메라와 맵 UI의 연결

원본 §11.2가 확인해 준 것: **미니맵(우하단), 확장맵 `M`, 파밍 오버레이 `Alt+M`, 토글 `F8`.**

| 연결 지점 | 입력 레이어의 책임 | 넘기는 곳 |
|---|---|---|
| 미니맵 클릭 → 카메라 이동 | 맵 UV → 월드 역변환 후 **카메라 타깃만** 이동 | 위젯·마커는 `UI_HUD_역기획서.md` §4 |
| 미니맵 `Alt/Ctrl+좌클릭` → 핑 | 수식자 해석 + Server RPC 호출 | 핑 표시·도배 제한은 `UI_HUD_역기획서.md` §4.2 |
| 확장맵(`M`) 열림 중 | **월드 컨텍스트를 내리고 맵 컨텍스트를 올린다** (§8) | 오버레이 내용은 `UI_HUD_역기획서.md` §4.3 |

> **좌표 변환은 UI 문서가 정의한 `WorldToMapUV()` 하나를 공유한다** (`UI_HUD_역기획서.md` §4 구현 메모). 입력 레이어가 자기 역변환을 따로 만들면 **핑 찍은 곳과 카메라가 간 곳이 어긋난다.**

## 8. EnhancedInput 구조 〔제안〕

| `IMC_Spectate` | 0 | 관전 카메라 조작만 (이동·스킬 없음) | 사망 후 관전 진입 |
| `IMC_Practice` | 5 | **`Ctrl+Alt+우클릭` 즉시 이동** (§11.6) | 연습 모드 전용 |

> ⭐ **사망 후에는 `IMC_Survival`을 `RemoveMappingContext`로 내리고 `IMC_Spectate`를 올린다.** "죽었으니 핸들러마다 `if (bIsDead) return;`"으로 처리하면 **모든 입력 핸들러에 같은 가드가 복사된다.** 컨텍스트 교체가 엔진이 의도한 방식이다.
> **컨텍스트 전환은 전부 클라 로컬이다.** 서버는 어떤 컨텍스트가 올라가 있는지 모르고 알 필요도 없다 — **서버는 도착한 RPC가 "지금 가능한 행동인지"만 검증한다**(§9).

### 8.2 애셋 분할

- `UInputAction`은 **의미 단위 1개당 1개**(`IA_MoveCommand`, `IA_Skill_Q`, `IA_Ping_Danger` …). 한 애셋을 여러 의미로 재사용하지 않는다.
- 수식자 조합(`Alt+좌클릭`)은 **코드에서 `IsInputKeyDown(EKeys::LeftAlt)`로 분기하지 말고** `UInputMappingContext`의 **`FInputChord` 트리거**로 별도 `UInputAction`에 매핑한다. 코드 분기로 만들면 재바인딩·우선순위가 전부 무너진다.
- 액션 참조는 `UDataAsset` 한 곳에 모으고 컨트롤러가 `EditDefaultsOnly`로 소유한다 (`CLAUDE.md` §5). 커밋 `6100863`에 `InputDataAsset`이라는 같은 목적의 클래스가 있었으나 **현재 삭제된 상태**이며, 위 구조는 그것을 되살리는 게 아니라 새로 정의하는 것이다.

## 9. 입력이 막히는 상황 — CC ↔ 입력 레이어의 계약

**CC의 정의·차단 플래그·저항은 [`전투판정_상태이상_역기획서.md`](전투판정_상태이상_역기획서.md) §3 담당이다. 여기서는 "입력 레이어가 그 플래그에 어떻게 반응하는가"만 쓴다.**

### 9.1 ⭐ 이중 게이트

전투 문서 §3.5가 이미 확정했다: *"CC 플래그를 `Replicated`로 두고 **클라에서도 이동 입력을 게이트**한다. 서버에서만 막으면 클라가 계속 움직이려 해서 튄다."*

| 위치 | 하는 일 | 목적 |
|---|---|---|
| **클라 입력 레이어** | 복제된 차단 플래그를 보고 **RPC를 아예 보내지 않는다** | 러버밴딩 방지 + 트래픽 절감. **보안 목적이 아니다** |
| **서버 RPC 핸들러** | 도착한 모든 이동·스킬 RPC를 **차단 플래그로 다시 검증** | ⭐ **이쪽이 진짜 방어선.** 클라 게이트는 조작 가능하다 |

> **클라 게이트를 "검증"이라고 부르지 말 것.** 그것은 예측 표시다.

### 9.2 CC 축별 입력 레이어 반응 〔제안〕

| CC 축 (전투 문서 §3) | 입력 레이어 동작 |
|---|---|
| **이동 차단** (기절·속박 등) | 이동 RPC 차단 + 진행 중 경로 추종 중단(`AbortMove`). ⚠ **속박은 이동기 스킬이 허용된다**(전투 §3.1) → 이동 차단과 스킬 차단은 **반드시 별개 플래그** |
| **기본 공격 차단** (무장 해제) | 기본 공격 RPC 차단. 우클릭은 **이동으로만** 해석 |
| **스킬 차단** (침묵) | 스킬 RPC 차단 + **조준 컨텍스트 강제 해제**(`IMC_Targeting` 제거). 안 내리면 조준 UI만 뜬 채 아무것도 안 나가는 상태가 된다 |
| **행동 강제 계열** (공포·매혹·도발·광기) | 서버가 이동 목표·공격 대상을 대신 지정 → 클라는 **모든 조작 RPC 전송 정지**. 6인 중 요구 없음 → 초기 미구현 (전투 §6) |
| **강제 이동** (넉백·그랩) | 이동 입력 차단 + 경로 추종 중단. **위치는 서버가 계속 바꾼다** (전투 §3.5) |
| **채널링(정신 집중)** | 이동 또는 스킬 입력이 들어오면 취소 (§9.3과 동일 규칙) |

### 9.3 휴식(`X`) 캐스팅 취소 — 원본이 준 유일한 입력 사양

> §3 원문: *취소 조건 = **단축키/이동 입력**, 피격, 군중제어 적중 → 캐스팅 취소, **1초 재사용 대기***

1. 캐스팅 중 **어떤 단축키든, 이동 지시든** 들어오면 취소된다 → 입력 레이어는 취소 대상을 화이트리스트가 아니라 **블랙리스트**로 다뤄야 한다. 카메라 조작·맵 열기 같은 비-게임플레이 입력이 예외인지는 **(미확인)**.
2. **취소 판정과 1초 대기는 서버가 소유한다.** 클라는 취소 연출만.
3. `SetIgnoreMoveInput`(`Engine/Classes/GameFramework/Controller.h:355`) / `IsMoveInputIgnored`(`:363`) / `ClientIgnoreMoveInput`(`PlayerController.h:1094`)는 엔진 스위치지만 **누적 카운터 방식**이라 CC가 겹칠 때 짝이 안 맞으면 영구히 잠긴다. **이 프로젝트는 CC 플래그 캐시(전투 §3 구현 메모)를 단일 진실로 쓰고 엔진 카운터에 의존하지 않는다** 〔제안〕.

## 11. GAS와의 접점

이 프로젝트는 **GAS 기반이다** (`CLAUDE.md` §8). **입력 레이어는 GAS의 영향을 거의 받지 않는다.**

| 요소 | GAS와의 관계 |
|---|---|
| `UInputMappingContext` / `UInputAction` 애셋, 컨텍스트 전환(§8) | ✅ **GAS와 무관** — 그대로 만든다 |
| 카메라 리그·잠금·스크롤 (§6) | ✅ GAS와 접점 없음 |
| 클릭 → 좌표 변환, 경로 요청, 이동 권위 모델 (§2·§3) | ✅ **이동은 GAS 대상이 아니다** — `CharacterMovementComponent` 소관 |
| 재바인딩 (`UEnhancedInputUserSettings`) | ✅ GAS와 무관 |
| **스킬 입력 → 발동** | ⚠ **`UAbilitySystemComponent::TryActivateAbility` 또는 `AbilityLocalInput` 계열**을 호출한다. 자체 `Server` RPC를 만들지 않는다 |
| **조준 페이로드(대상/방향/위치)** | ⚠ **`FGameplayAbilityTargetData` 로 실어 보낸다.** 단 ⭐ **조작 방식·인디케이터·클램프 규칙은 이 문서 소관** |
| **CC 차단 플래그 조회 (§9)** | ⚠ **`GameplayTag` 쿼리**로 한다 (`ASC->HasMatchingGameplayTag`) |

> ⭐ **입력 → 어빌리티 발동 경로를 얇은 어댑터 한 곳에 모은다.**
> 입력 핸들러가 ASC를 직접 여기저기서 부르면, 나중에 입력 방식(스마트캐스트 등)을 바꿀 때 호출부가 흩어진다.
> 어댑터 하나를 두면 **입력 애셋·컨텍스트·카메라는 GAS를 전혀 모른 채로 남는다.**
>
> ⚠ **GAS 예측(prediction)을 지금 켜지 않는다.** 먼저 서버 권위로 정확히 동작시킨다 (`CLAUDE.md` §8).
> 즉 클릭 이동의 러버밴딩 문제는 `CharacterMovementComponent` 기본 보정으로 풀고, GAS 예측에 기대지 않는다.

## 데이터 스키마 제안

**전제:** 키 바인딩은 코드 상수가 아니라 **애셋 + 유저 저장 데이터**다. 코드에 `EKeys::Q`가 박히는 순간 재바인딩은 불가능해진다.

```
Content/Input/
  IMC_Lobby(0) / IMC_Survival(0) / IMC_Targeting(10) / IMC_FullscreenUI(20)
  IMC_Chat(30) / IMC_Spectate(0) / IMC_Practice(5)          <- 괄호 = Priority
  Actions/
    IA_MoveCommand, IA_Stop, IA_AttackMove
    IA_Skill_Q / W / E / R / D                (F는 초기 컷 — 애셋 자리만)
    IA_Rest_X,  IA_QuickSlot_1~4,  IA_Inventory, IA_Scoreboard
    IA_Map_Open, IA_Map_Overlay, IA_Map_ToggleF8
    IA_Ping_Direct(Alt+LMB), IA_Ping_Location(Ctrl+LMB), IA_Ping_Wheel(Ctrl+LMB Drag)
    IA_CameraLockToggle, IA_CameraRecenter, IA_CameraTeammate_1~3
    IA_Targeting_Confirm, IA_Targeting_Cancel, IA_Practice_Blink(Ctrl+Alt+RMB)
```

```cpp
// 입력 애셋 참조를 한 곳에. 컨트롤러가 EditDefaultsOnly로 소유한다.
UCLASS()
class UERInputConfig : public UDataAsset
{
    GENERATED_BODY()
public:
    UPROPERTY(EditDefaultsOnly, Category="Context") TObjectPtr<UInputMappingContext> IMC_Survival;
    UPROPERTY(EditDefaultsOnly, Category="Context") TObjectPtr<UInputMappingContext> IMC_Targeting;
    UPROPERTY(EditDefaultsOnly, Category="Context") TObjectPtr<UInputMappingContext> IMC_FullscreenUI;
    UPROPERTY(EditDefaultsOnly, Category="Context") TObjectPtr<UInputMappingContext> IMC_Spectate;

    UPROPERTY(EditDefaultsOnly, Category="Action") TObjectPtr<UInputAction> IA_MoveCommand;
    // 슬롯은 배열로. 개별 변수로 두면 슬롯 추가 시 전부 고쳐야 한다.
    UPROPERTY(EditDefaultsOnly, Category="Action") TArray<TObjectPtr<UInputAction>> IA_SkillSlots;  // Q W E R D
    UPROPERTY(EditDefaultsOnly, Category="Action") TArray<TObjectPtr<UInputAction>> IA_QuickSlots;  // 1~4
};

// §4 조준 결과 — 서버로 가는 유일한 형태.
USTRUCT()
struct FSkillInputPayload
{
    GENERATED_BODY()
    UPROPERTY() int32                     SlotIndex = INDEX_NONE;
    UPROPERTY() TWeakObjectPtr<AActor>    TargetActor;      // 대상 지정
    UPROPERTY() FVector_NetQuantize       TargetLocation;   // 위치 지정 (서버가 사거리 재클램프)
    UPROPERTY() FVector_NetQuantizeNormal TargetDirection;  // 방향 지정
};
```

**구현 메모**
- `UObject*`/`TObjectPtr` 멤버에 **반드시 `UPROPERTY()`** — GC dangling 방지 (`CLAUDE.md` §5).
- 페이로드는 **`FVector_NetQuantize` 계열**로. 원시 `FVector`는 좌표 하나에 12바이트다. 24인 매치에서 무시할 수 없다.
- `TargetActor`는 `TWeakObjectPtr`로 두되 **서버가 유효 대상인지 반드시 재검증**한다 (전투 문서 §5.2 `IsValidTarget`).
- 키 바인딩 저장은 자체 `USaveGame`을 만들지 말고 **`UEnhancedInputUserSettings`**(`:471`)를 쓴다. `bEnableUserSettings`(`EnhancedInputDeveloperSettings.h:106`) 활성화가 선행 조건이다.

## 구현 우선순위

```
1순위. 카메라 리그 (SpringArm+Camera, bUsePawnControlRotation=false, bDoCollisionTest=false)
       → 검증: 빌드 통과 + 캐릭터가 회전해도 카메라 각도 고정
2순위. EnhancedInput 기본 구성 (UERInputConfig + IMC_Survival + 컨트롤러 바인딩)
       → 검증: 빌드 통과 + 우클릭이 핸들러에 도달 (UE_LOG)
3순위. ⭐ 클릭 이동 — 커서 히트 → 목적지 → Server RPC 1회 → 서버 RequestMove
       → 검증: Play As Client / Players 2 에서 서버·타 클라가 같은 경로로 이동, 러버밴딩 없음
4순위. 도착 콜백(OnRequestFinished) + 정지(S) + 이동 중단
       → 검증: 이동 중 S 입력 시 서버에서 AbortMove 호출, 클라도 즉시 정지
5순위. 카메라 잠금/해제/복귀 + 맵 가장자리 스크롤 (전부 로컬)
       → 검증: 해제 후 Space로 복귀. 복제 트래픽이 발생하지 않음
6순위. 스킬 조준 3종(대상/방향/위치) + IMC_Targeting 컨텍스트
       → 검증: 조준 중 우클릭이 이동이 아니라 취소로 소비됨. 사거리 클램프가 클라·서버 동일
7순위. CC 차단 플래그 ↔ 입력 이중 게이트 (§9.1)
       → 검증: 기절 중 클라가 RPC를 보내지 않고, 강제로 보낸 RPC도 서버가 거부
8순위. 컨텍스트 전환 (사망→Spectate, 확장맵→FullscreenUI, 채팅→Chat)
       → 검증: 사망 후 이동·스킬 입력이 전부 무시되고 관전 카메라만 동작
9순위. 핑 3종 (Alt+LMB / Ctrl+LMB / Ctrl+LMB 드래그) — Server RPC → 팀 한정 Multicast
       → 검증: 같은 팀에만 표시 (UI_HUD_역기획서.md §4.2와 공동 작업)
10순위. 재바인딩(bEnableUserSettings + MapPlayerKey) + 스마트캐스트 토글
       → 검증: 키를 바꾸고 재접속해도 유지됨
11순위. 충전형 / 리캐스트 조작, 강제 공격(A+클릭)
       → 검증: 충전 시간이 서버 시계로 계산되고 클라 조작으로 늘릴 수 없음
```

> 멀티플레이 검증은 전부 **`Play As Client, Number of Players: 2` 이상**에서. 각 단계의 1차 검증은 **빌드 통과**다 (`CLAUDE.md` §4).
> `F`(전술 슬롯)는 초기 버전 컷이라 이 목록에 없다 (`UI_HUD_역기획서.md` §9).
