## 레이아웃 표

> **측정 방법** — `아이템 제작.png` (1097×817) 를 Python PIL 로 직접 쟀다: 한 줄을 따라 색이 바뀌는 구간(run) 경계 · 밝은 픽셀 bbox · 격자선 밝기 피크. 눈대중 값 없음. 값이 ±1px 흔들리는 곳은 `(근사)`.
> **좌표계** — 전부 **창 내부 좌표**(창 좌상단 = 캡처 (0,0)). 근거: 탭1 배경이 x=0, 제목 바가 y=0 에서 시작. ⚠ 단 탭 선택 강조선(2px)이 B 캡처에선 탭 양쪽에 있는데 A 캡처 탭1 은 오른쪽에만 보인다 → **창 왼쪽이 2px 이상 잘렸을 수 있다 (미확인)**.
> **두 캡처 공통** — 창 셸 · 오른쪽 패널(H·I·J) · 퀵바 좌표는 `모든 아이템.png` 에서도 같은 값으로 측정됐다(±0px). 이 표가 **창 셸의 원본**이고 [04 레이아웃 표](04_모든아이템.md#레이아웃-표) 는 왼쪽 패널만 정의한다.
> **슬롯 · 툴팁 크기는 여기 적지 않는다** → [04 레이아웃 표 · 공용 위젯](04_모든아이템.md#레이아웃-표) 이 유일한 정의.
> ⚠ §3 트리는 Box 배치라 아래 (x,y) 는 그대로 넣는 값이 아니라 **Padding · SizeBox 로 환산할 목표 위치**다. CanvasPanel 은 여전히 트리 뷰(I) 안에서만.

### 배율 추정 — 캡처 1px = 1080p 1px 로 본다 `(근사)`

| 근거 | 측정 | 1080p 1:1 이면 | 1440p 캡처(×0.75)라면 |
|---|---|---|---|
| 탭 · 섹션 제목 한글 글자 높이 | 14px (`후반 아이템 리스트` · `시작 아이템`) | UMG 12pt — 1080p 게임 본문 크기로 자연스럽다 | 10.5px → 9pt. 제목치고 너무 작다 |
| 도감 슬롯 (04) | 66×41 | 화면 높이의 3.8% | 50×31 — 아이콘이 읽히기 어렵다 |
| 창 + 퀵바 너비 | 1097px | 1920 의 57% | 823px — 43% |

→ **배율 1.0 을 기본 가정.** 원작 해상도 정보가 캡처에 없으므로 `(미확인)`. UMG DPI Scale 기본 커브는 짧은 변 1080 에서 1.0 이므로, 아래 값은 디자이너(1920×1080)에 그대로 넣는다.

## 영역별 내부 구조

> §1 의 영역(A–K)마다 **위젯 트리를 잎까지** 적고, 위젯마다 *부모 슬롯 설정* 과 *위젯 자체 설정* 을 적었다. 이 절만 보고 UMG 디자이너에서 위에서 아래로 따라 만들면 된다. 형식은 [02 §2.2c](02_캐릭터선택.md#22c-영역별-내부-구조) 와 같다.
> - 수치는 `아이템 제작.png` 를 PIL 로 **다시 잰 값**이다 (행/열 run · 밝기 bbox · 픽셀 덤프). [레이아웃 표](#레이아웃-표)와 다르면 **실측을 따르고 `⚠ 실측`** 으로 표시했다
> - **색은 픽셀에서 뽑은 sRGB Hex** → 색 선택기의 **`Hex sRGB`** 칸에 넣는다. 알파를 안 적었으면 1.0. 창 바탕처럼 **뒤 월드가 비치는 곳**은 잰 색에 월드가 섞여 있다 → `(근사)`
> - 좌표 = **창 내부 좌표** (레이아웃 표와 같다)
> - 표시만 하는 위젯은 Visibility = **`Not Hit-Testable (Self & All Children)`** ([00 §4.7](00_UI_공통원칙.md)) → 표에서 `NHT`
> - **Bind 드롭다운 금지 · Event Tick 없음** ([00 §2.4 · §4.8](00_UI_공통원칙.md)). Canvas Panel 은 **창이 놓이는 HUD 루트**와 §3 대로 **I 트리 뷰 안 2개**뿐
> - **BindWidget 대상**은 **굵게** (C++ 베이스가 아직 없다 — 이름만 미리 맞춘다) · `(추가)` = §3 트리에 없던 위젯을 보탠 것 · 기존 이름은 그대로
> - ⭐ **`WBP_ItemSlot` · `WBP_ItemTooltip` 의 내부(레이어 · 등급 색 · 빈 칸 모양)는 여기 적지 않는다** → [04 「영역별 내부 구조」 ④ · 툴팁](04_모든아이템.md#영역별-내부-구조). 이 문서는 칸을 **어디에 어떤 크기로 놓는지**만 적는다
> - 슬롯 칸 읽는 법 · `RB(W, 색)` 줄임말(텍스처 없는 테두리 + 단색 브러시)도 04 의 같은 절 머리말과 같다

## 4. 제작 트리(I) 렌더링 — 재귀 위젯 vs 평탄화 리스트

> ⚠ 방안이 둘이라 원칙상 `Docs/4_Argument/` 감이다(CLAUDE.md §1.2). 이 작업은 이 파일만 쓰도록 제한돼 있어 여기 둔다 — **C++ 착수 전에 Argument 로 옮겨 결정받는다.**

**전제 (코드 확인)**
- 제작은 항상 `A + B → C` 이진 (`ERItemData.h:66`). 깊이 제한 없음 · 초월은 건너뛴다 (`ERCraftLibrary.h:27-28`)
- 따라서 노드 수 ≤ 2^(깊이+1)−1. 깊이 = 등급 수(6) 이하라면 최대 63 — **실제 최대 깊이는 DT_Items 기준 (미확인)**. `ER.Craft.Tree <최종템>` 으로 세어 본다 (§10 T1)

### 방안 1 — 재귀 위젯

`WBP_CraftTreeNode` 가 자기 재료 2개에 대해 자식 노드를 `CreateWidget` 해 자기 아래 Box 에 넣는다. `UI_HUD_역기획서.md` §5.4 가 적어 둔 방식 (*"C++ 베이스 위젯이 자식 노드를 CreateWidget 으로 생성"*).

- 장점: 레이아웃이 Box 중첩으로 자동. 트리 모양 = 위젯 계층이라 직관적
- 단점: 목표를 바꿀 때마다 노드 전부 파괴·생성 → 매 단계 **Child Invalidation**. 위젯 깊이 = 트리 깊이 × (노드+Box) 로 중첩이 깊다. BP 자기 참조는 순환 경고 위험(역기획서 §5.4) → C++ 베이스 필수
- 연결선을 그리려면 결국 각 노드의 지오메트리를 알아야 한다 — Box 레이아웃이 끝난 **다음 프레임**에야 위치가 나온다 (미확인: 측정 안 함)

### 방안 2 — 평탄화 리스트 + 노드 풀 (추천)

C++ 가 트리를 **한 번** 펼쳐 `TArray<FERCraftTreeNode>` (`ItemId · Depth · ParentIndex · Column`) 로 돌려준다. 뷰는 미리 만들어 둔 노드 위젯 풀에서 필요한 만큼 꺼내 Canvas 좌표에 놓고, 남는 건 `Collapsed`.

- 장점: 목표 변경 = 좌표 · 데이터 재할당만. 풀 크기를 넘지 않으면 자식 추가/제거가 없다. 위젯 깊이 1단. 좌표를 C++ 가 알기 때문에 연결선도 같은 프레임에 그린다. 인게임 창과 로비 플래너가 **같은 노드 배열**을 쓴다 (역기획서 §5.4 "트리 계산은 위젯이 아니라 서브시스템에")
- 단점: 좌표 계산(열 배치)을 직접 짠다 (~30줄 예상, 미측정). 풀 크기를 정해야 한다 → T1 측정값 + 여유

### 비교

| 축 | 1 재귀 | 2 평탄화+풀 |
|---|---|---|
| 구현 난이도 | 중 (C++ 베이스 위젯 + 선 그리기 지연) | 중 (배치 계산) |
| 목표 변경 비용 | 노드 전부 파괴·생성 → Child Invalidation | 위치 변경 → Layout Invalidation |
| 인벤토리 변경 비용 | 노드 색 · 투명도만 → Paint | 동일 → Paint |
| 위젯 중첩 깊이 | 트리 깊이에 비례 | 1단 |
| 로비 플래너 공유 | 위젯에 계산이 섞이기 쉽다 | 노드 배열 그대로 공유 |
| 네트워크 | 없음 (로컬 정적 데이터) | 없음 |

**근거 (Epic 문서)**
- Child Invalidation 은 *"if you add or remove children from the widget"* 에서 나고, 그 뒤 *"the Layout and Paint calculations will need to be updated on the widget and all of its children"* — *"if your UI does it each frame, it can be a substantial performance bottleneck"* · [Invalidation in Slate and UMG](https://dev.epicgames.com/documentation/unreal-engine/invalidation-in-slate-and-umg-for-unreal-engine)
- 위치·크기 변경은 *"Layout Invalidation"*, 색만 바꾸면 *"Paint Invalidation on that widget"* · 같은 문서
- ⚠ 공정하게: 목표 변경은 **클릭 시 1회**라 "매 프레임" 이 아니다. 방안 1 의 비용 차이는 실측 전엔 체감 여부 **(미확인)**. 추천 이유의 무게는 성능보다 **로비 공유 · 연결선 같은 프레임 · BP 순환 회피** 쪽에 있다

**추천: 방안 2.** 노드 위젯 BP 는 한 칸의 외형만 맡는다 (CLAUDE.md §7).

## 5. 갱신 정책 — Tick · 바인딩 금지, 이벤트로만

| 규칙 | 근거 |
|---|---|
| **UMG 프로퍼티 바인딩(Bind) 쓰지 않는다** — 수량 · 보유 · 크레딧 텍스트 전부 | *"When you bind attributes to fields in your UI, they poll the attribute every frame."* → *"you should set up your project to call functions and events in your UI to update these fields"* · [UMG 최적화](https://dev.epicgames.com/documentation/unreal-engine/optimization-guidelines-for-umg-in-unreal-engine) |
| **Event Tick 비우고 끈다** (위젯 Details > `Tick Frequency` = Never — 00 규칙 확인) | *"Whenever possible, you should avoid using On Tick or On Paint to run logic in your UI."* · 같은 문서. 그리고 Slate 는 *"Slate sleeps whenever … No active timer need to execute"* — Tick/타이머가 없으면 UI 가 잠들 수 있다 · [Slate Sleeping and Active Timers](https://dev.epicgames.com/documentation/unreal-engine/slate-ui-sleeping-and-active-timers-in-unreal-engine) |
| 트리 뷰를 **InvalidationBox** 로 감싼다. 퀵바 · 창 본문 등 거의 안 변하는 것도 같은 원칙 | *"Invalidation is especially well-suited for widgets that do not change often."* · *"you should try using Invalidation Boxes first"* · [Invalidation](https://dev.epicgames.com/documentation/unreal-engine/invalidation-in-slate-and-umg-for-unreal-engine) |
| **Volatile 표시하지 않는다** — 매 프레임 변하는 게 이 창엔 없다 | Volatile 은 *"does not cache its Paint data"* — 매 프레임 갱신하는 위젯용 · 같은 문서 |
| 창은 **열 때 만들고 닫을 때 버린다** (또는 00 의 창 관리 규칙) — 매치 대부분 닫혀 있다 | 오래 안 보이는 복잡한 위젯은 *"asynchronously at runtime and destroyed when dismissed"* · *"All children inside a widget are loaded and constructed regardless of whether they are visible."* · [UMG 최적화](https://dev.epicgames.com/documentation/unreal-engine/optimization-guidelines-for-umg-in-unreal-engine) |
| 탭 3개는 `WidgetSwitcher` 지만 **모든 아이템 탭 본문(04)은 처음 열 때 생성**을 검토 | 위 인용 — 숨겨도 생성 비용은 낸다 |
| 아이콘은 `Icon` 소프트 참조를 **보일 때** 비동기 로드 | 프로젝트 결정 `ERItemData.h:54` ("수백 행이 한꺼번에 텍스처를 로드하면 안 된다") — Epic 문서 3개는 텍스처 로드를 다루지 않는다 |

**이벤트 흐름 (C++ C2 후)**
```
서버 Craft() → Bag/Equipped 변경 → 복제
  → 클라 OnRep_Bag / OnRep_Equipped
     → (신규) OnInventoryChanged.Broadcast()
        → WBP_CraftWindow::Refresh
            ├ 트리 노드: 보유 플래그만 다시 (Paint)
            ├ H 상위 아이템: 필터 다시
            └ G 행 슬롯: 수량/보유만
```
목표 변경(행 클릭)만 트리 노드 배열을 새로 받는다.

## 주의점

- `WBP_ItemSlot` 을 이 문서용으로 **복제해 따로 만들지 않는다** — 등급 색이 두 군데서 어긋난다
- 슬롯 숨김은 `Collapsed` (자리까지 빠짐) vs `Hidden` (자리 유지) — G 행2·3 의 빈칸은 **자리가 보여야 하므로** 빈 슬롯 상태로 그린다. (Epic 문서 3개는 이 차이를 다루지 않는다 — UMG 일반 동작)
- Bind 를 "임시로" 써 두면 C2 가 들어와도 매 프레임 폴링이 남는다. 처음부터 쓰지 않는다

## 못 하는 검증

- 실제 데이터 흐름(T4·T5) — C2~C5 가 없어서. **F17 C++ 합의 · 빌드 후**
- 크레딧 · 퀵바 — F15 전까지
- 트리 노드 모양 · 연결선 스타일 — 레퍼런스가 **빈 트리 상태**라 원작 모양 (미확인). 노드가 보이는 캡처가 있으면 이 문서를 고친다
