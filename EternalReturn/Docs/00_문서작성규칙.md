# 문서 작성 규칙

`CLAUDE.md` 가 **언제** 문서를 쓰는지 정하고, 이 파일이 **어떻게** 쓰는지 정한다.
셋 중 하나를 쓰기 전에 해당 절을 읽는다.

## 전 문서 공통

- ⭐ **모든 주장에 근거와 출처를 단다. 출처 없는 주장은 쓰지 않는다.**
  | 종류 | 형식 |
  |---|---|
  | 엔진 코드 | `파일 경로:라인` (예: `GameplayEffect.cpp:4238`) |
  | 공식 문서 | URL + 문서 제목 |
  | 이 프로젝트 문서 | 상대 경로 + 절 번호 |
  | 이 프로젝트 코드 | `Source/EternalReturn/...:라인` |
  | 측정값 | **어떻게 측정했는지**까지 |
- ⭐ 확인 못 한 것은 **`(미확인)`** 으로 남긴다. **추측을 근거처럼 쓰지 않는다.**
- 채팅에는 **경로와 3줄 요약만.** 긴 내용을 복붙하지 않는다.
- 주석·문서는 한국어.

# 1. `Docs/4_Argument/` — 구현 방안 비교

**언제:** 세부 구현에 선택 가능한 방안이 2개 이상일 때. **구현 시작 전.**
이미 짜놓고 사후 정당화하지 않는다.

**이름:** `N_주제.md` — `N` 은 1부터 증가

**채팅에는:** 문서 경로 + 방안 이름 한 줄씩 + **내 추천 1개**

## 반드시 포함할 것

1. **결정할 것** — 한 문장
2. **방안 목록** — 각 방안마다
   - 어떤 방식인지 (필요하면 코드 스케치 5~15줄)
   - **장점 / 단점을 각각 불릿으로.** 한쪽만 쓰지 않는다
   - 이 프로젝트 기준 비용: 구현 난이도, 네트워크 비용, **GAS 가 이미 제공하는 걸 다시 만드는 건 아닌지**
3. **비교표** — 축은 최소한 `구현 난이도 / 확장성 / 네트워크 / GAS 정합성 / 성능`
4. **추천** — 어느 것을 왜. **나열만 하고 끝내지 않는다**
5. **근거와 출처** (공통 규칙)

**원칙:** 사용자가 문서만 보고 고를 수 있어야 한다. "상황에 따라 다릅니다"로 끝내지 않는다.

## 결정된 뒤

- 문서 상단 **결정 요약 표**에 결과를 적는다
- 방침이 바뀌면 **옛 추천에 철회 표시**를 하고 논거는 기록으로 남긴다 — 지우지 않는다

# 2. `Docs/5_ErrorReport/` — 원인을 찾은 문제

**언제:** 고친 **직후.** 다음 작업으로 넘어가기 전에.

**이름:** `E##_짧은제목.md` — 번호는 1부터 증가
**목록:** `00_에러목록.md` 에 한 줄 추가 (최신이 위)

## 대상

| 적는다 | 적지 않는다 |
|---|---|
| 빌드 에러 | ⛔ **git 조작** (커밋·머지·revert·충돌) |
| 조용히 안 먹는 설정 | 단순 오타, 즉시 알아챈 실수 |
| 설계 오류 | 원인을 못 찾은 것 |
| 사용자가 지적한 문제 | 에디터 사용법 |
| 레퍼런스 대조로 찾은 결함 | |

⭐ **특히 "빌드는 통과하는데 동작하지 않는" 종류를 반드시 남긴다.**
기록이 없으면 몇 달 뒤에 똑같이 하루를 쓴다.

## 반드시 포함할 것

1. **증상** — 에러 메시지는 **원문 그대로**
   ⚠ 런타임에 목격 못 했으면 **"목격한 증상은 없다"** 고 먼저 적는다
2. **원인** — 근거를 단다 (공통 규칙)
   ⭐ 못 찾았으면 **`(원인 미확인)`**. 부분만 밝혀졌으면 어디까지 확인했는지 명시
3. **해결** — 무엇을 어떻게 고쳤나
4. **재발 방지** — 다음에 어떻게 막나. **못 막으면 "못 막는다"고 적는다**

# 3. `Docs/3_EditorTasks/` — 에디터 작업과 테스트

**언제:** 빌드가 통과한 **직후.** 빌드 실패 상태로 만들지 않는다.

**이름:** `F##_기능명.md` — Task 폴더와 **같은 이름**
⚠ 날짜를 파일명에 넣지 않는다. 기능이 갱신되면 같은 파일을 고친다.

⚠ **에디터에서 할 게 하나도 없어도 문서는 만든다.** "없음"이라고 적는다 —
사용자가 확인할 게 없다는 것도 정보다.

## ⭐ 두 섹션을 반드시 분리한다

섞어 쓰지 않는다. "지금 뭘 해야 하나"와 "뭘 확인해야 하나"가 구분돼야 한다.
각 항목에 **체크박스(`- [ ]`)** 를 단다.

### ① 에디터 작업 — 애셋·설정을 실제로 **바꾸는** 일

- 애셋 전체 경로 (`/Game/Core/BP_ERGameMode`)
- 메뉴·패널 위치 (`File > Reparent Blueprint`, `Details 패널 > Match 카테고리`)
- 프로퍼티 **에디터 표시 이름**과 넣을 값 (C++ 변수명이 아니다)
- 새로 만들 애셋은 타입·부모 클래스·이름·저장 위치까지
- 데이터 테이블은 컬럼명과 예시 행을 표로, 행 이름 규칙도

### ② 테스트 — PIE 로 **확인만** 하고 끝나는 일

- Net Mode / 플레이어 수를 명시 (`Play As Client, Number of Players: 4`)
- **성공 판정을 구체적으로.** 어떤 로그가 몇 줄 나와야 하는지, 무엇이 보이면 실패인지
- 실패 시 **증상 → 고칠 곳** 대응표

## 그 밖에 포함할 것

- **목적** — 끝나면 무엇이 동작하는지 한 문단
- **선행 조건** — 에디터 재시작 필요 여부, 먼저 끝나 있어야 할 작업
- **주의점** — 흔한 실수, 값을 잘못 넣었을 때 나타나는 증상
- **못 하는 검증** — 아직 시험할 수단이 없는 것은 왜 못 하는지와 **언제 하는지**
- **끝나면** — 어느 체크리스트의 어느 항목이 채워지는지

**원칙:** 사용자가 문서만 보고 그대로 따라 하면 끝나야 한다.
"적당히 설정하세요"를 쓰지 않는다. 값을 모르면 추측하지 말고 그 자리에서 묻는다.
