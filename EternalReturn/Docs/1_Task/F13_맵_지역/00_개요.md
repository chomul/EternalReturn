## ⚠ F05 에서 미룬 결정 — 큰 맵의 네비메시

F05-02(클릭 이동)가 네비메시를 요구한다. 작은 테스트 맵에서는 문제가 없지만
`ER_Level` 로 옮기면 설정을 정해야 한다.

### 조사 결과 (2026-09-09)

| 비용 | 맵 크기에 비례하나 |
|---|---|
| 네비메시 **빌드 시간** | ⭐ **예** — 크면 수 분 |
| 네비메시 **메모리** | ⭐ **예** |
| **경로 탐색 비용** | ❌ **아니오** — 경로 **길이**에 비례한다 |

⭐ **탐색 비용은 맵 크기와 무관하다.** A\* 는 출발지~목적지 구간만 훑는다.
24명이 초당 한 번 클릭해도 24 쿼리/초라 부하가 아니다.

### ⭐⭐ 진짜 위험은 크기가 아니라 `Runtime Generation` 이다

```cpp
// NavigationData.h:492-502
enum class ERuntimeGenerationType : uint8
{
    Static,                // 런타임 생성 없음. 완전 정적
    DynamicModifiersOnly,  // 네비 수정자만 갱신
    Dynamic,               // 지오메트리 변경까지 전부  ← 엔진 기본값
};
```

⚠ **`Dynamic` 이면 물체가 움직일 때마다 그 타일을 다시 굽는다.**
큰 맵에서 프레임 드랍의 실제 원인은 이것이지 맵 크기 자체가 아니다.

**이터널 리턴 맵은 지형이 거의 고정이다** → **`Static`** 이 맞다.

### 정해야 할 설정

| 설정 | 엔진 기본값 | 제안 | 근거 |
|---|---|---|---|
| `Runtime Generation` | `Dynamic` | ⭐ **`Static`** | 지형이 고정이다 |
| `Agent Max Step Height` | **35** | ⭐ **45** | ⚠ CMC 와 불일치 (아래) |
| `Agent Radius` | 35 | 캐릭터 캡슐과 일치 | 네비가 크면 좁은 틈이 막힌다 |
| `Cell Size` | **25** | ⚠ **큰 맵에서 낮추면 위험** (아래) | `RecastNavMesh.h:640` |
| `Tile Size UU` | **988** | 큰 맵이면 **2000** 검토 | `RecastNavMesh.cpp:428`. 타일 수가 1/4 |
| `Min Region Area` | 기본 | 좁은 곳이 사라지면 낮춘다 | 작은 영역을 통째로 버린다 |

⚠ 문 · 파괴물 같은 **움직이는 장애물**이 있으면 `DynamicModifiersOnly` 를 검토한다.
`Dynamic` 은 마지막 수단이다.

## ⚠⚠ 네비메시 튜닝 — F05 에서 실제로 겪은 문제 (2026-09-09)

사용자 질문: *"작은 둔턱이나 원하는 곳에 네비 메시가 안 깔리거나 이런 문제가 발생하는데
우리 프로젝트에서 NavMesh 를 꼭 사용해야 하나?"*

### ⭐ 결론 — 필요하다. 문제는 설정이었다

| | 네비메시 없이 |
|---|---|
| 클릭 이동 | ⚠ **직진만.** 벽 뒤를 클릭하면 벽에 붙어서 멈춤 |
| ⭐ **야생동물 · 보스 AI (F12)** | ❌ **불가능.** 추격·귀환이 전부 직진 |
| "갈 수 있는 곳인가" 판정 | ❌ 없음 |

⭐ **F12 가 결정적이다.** 야생동물이 플레이어를 쫓고 어그로가 풀리면 원위치로 돌아가야 한다.
직진 추격은 지형에 걸려 성립하지 않는다. `AIModule` 이 이미 의존성에 있는 것도 그래서다.

⚠ 자체 패스파인딩을 만들어도 **"둔턱을 넘을 수 있나"를 똑같이 결정해야 한다.**
문제가 사라지지 않고 우리 코드로 옮겨올 뿐이다.

### ⭐⭐ 둔턱 문제의 진짜 원인 — 엔진 기본값이 서로 안 맞는다

| | 값 | 출처 |
|---|---|---|
| **CMC** `MaxStepHeight` | **45** | `CharacterMovementComponent.cpp:604` |
| **네비메시** `AgentMaxStepHeight` | **35** | `RecastNavMesh.h:648` |

⭐ **캐릭터는 45까지 올라갈 수 있는데 네비메시는 35까지만 길을 낸다.**
높이 35~45 사이의 둔턱은 실제로는 넘을 수 있는데 **네비메시가 벽으로 취급**한다.

→ 둘을 같은 값으로 맞춘다. **한쪽만 바꾸면 다시 어긋난다.**

### ⚠ `Cell Size` 는 큰 맵에서 함정이다

좁은 통로에 네비메시가 안 깔리면 `Cell Size` 를 낮추는 게 정석이다.
**작은 테스트 맵에서는 공짜처럼 보인다.**

⚠⚠ 그러나 복셀 수는 `Cell Size` 의 **제곱에 반비례**한다.
25 → 12.5 로 낮추면 **복셀이 4배**가 되고, `ER_Level` 규모에서는
**빌드 시간과 메모리가 그만큼 늘어난다.**

→ **테스트 맵에서 낮춰 놓고 `ER_Level` 로 옮기면 빌드가 몇 분씩 걸린다.**

### ⏸ F05 에서 넘어온 **검증 항목** (2026-09-09 결정)

사용자 결정: *"일단 이건 나중에 맵 할 때 더 테스트해 보자.
지금은 F05 까지 다 되는 거 확인했으니"*

⭐ **F05 의 코드는 끝났다.** 아래는 **네비메시 설정에 달린 것**이라
`ER_Level` 에서 설정을 확정한 뒤에 한꺼번에 확인하는 게 맞다.
작은 테스트 맵에서 통과시켜도 큰 맵에서 다시 봐야 하므로 두 번 하게 된다.

- [ ] ⭐ `Agent Max Step Height` 를 **45** 로 맞춘다 (CMC 와 일치 — 위 참조)
- [ ] 설정 후 `Build > Build Paths` (⚠ `Static` 은 런타임에 안 굽는다)
- [ ] ⭐ **장애물(상자·벽)을 클릭하면 옆 바닥으로 이동**한다 — 제자리에 안 멈춘다
- [ ] 하늘을 클릭하면 아무 일도 안 일어난다 (크래시 아님)
- [ ] ⭐ 벽 뒤를 클릭하면 **돌아서 간다** (`P` 키로 네비메시 확인)
- [ ] 작은 둔턱을 넘어간다 (35~45 구간)

관련 코드: `AERPlayerController::ResolveNavigableDestination`
관련 체크리스트: [`../../2_Checklist/F05_입력_카메라_이동/02_클릭이동_서버권위.md`](../../2_Checklist/F05_입력_카메라_이동/02_클릭이동_서버권위.md)

### F13 에서 측정할 것

- [ ] `ER_Level` 에서 `Cell Size` 25 로 빌드했을 때 **빌드 시간 · 네비메시 메모리**
- [ ] 좁은 통로가 실제로 문제가 되는지 (안 되면 낮출 이유가 없다)
- [ ] 낮춰야 한다면 **어디까지** 낮출 수 있는지 (12.5? 20?)
- [ ] `Tile Size UU` 를 2000 으로 키웠을 때의 효과
- [ ] ⚠ **World Partition 전환 여부**와 함께 본다 — 타일 스트리밍이 되면 계산이 달라진다

## ⚠ 더 큰 문제 — `ER_Level` 이 World Partition 을 안 쓴다

확인 방법: `Content/__ExternalActors__/` 에 `ER` 폴더가 **없다**.
(`ERCharacter` 와 `TopDown` 만 있다 = 그 둘만 OFPA 를 쓴다)

⭐ **통짜 레벨이면 맵 전체가 한꺼번에 로드된다.** 9.9 GB 콘텐츠를 쓰는 맵에서는
네비메시보다 이쪽이 훨씬 큰 부담이다.

### F13 에서 정해야 할 것

- [ ] `ER_Level` 을 **World Partition 으로 전환**할지
- [ ] 전환한다면 네비메시도 **타일 스트리밍**과 맞물린다
- [ ] 전환 안 한다면 **로딩 시간 · 메모리 상한**을 측정해서 감당 가능한지 확인
- [ ] 지역(§ 역기획서)별 스트리밍 경계를 맵 구조와 맞출지

⚠ **지금 결정하지 않는다.** 맵 구조를 모르는 채로 정하면 추측이 된다.

## ⚠ 이미 켜져 있는 설정 — 클라이언트 네비게이션

```ini
# Config/DefaultEngine.ini:76-77
[/Script/NavigationSystem.NavigationSystemV1]
bAllowClientSideNavigation=true
```

⭐ **F05-02 의 클릭 이동 설계가 이걸 요구한다.** 클라가 로컬에서 `SimpleMoveToLocation` 을
돌려 클릭 지연을 없애기 때문이다.

⚠ 대신 **네비메시가 클라에도 로드**되어 메모리를 쓴다.

| | 켬 (현재) | 끔 |
|---|---|---|
| 클릭 반응 | ⭐ **즉시** | 서버 왕복 지연 |
| 클라 메모리 | 네비메시만큼 더 | 절약 |

**켜 두는 것이 맞다** — MOBA 에서 클릭 지연은 체감이 크다.
⚠ 다만 `ER_Level` 규모에서 클라 메모리를 **측정**해 보고 다시 판단한다.
