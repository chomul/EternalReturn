# F09-01 — 조합 데이터 · 재귀 트리 탐색 ⭐

> 기능 [F09](00_개요.md) · 근거 [`장비_아이템_역기획서.md`](../../0_GameDesign/Systems/장비_아이템_역기획서.md) §3 · §6.2 · 우선순위 3
> 체크리스트 [`../../2_Checklist/F09_제작/01_조합데이터_트리탐색.md`](../../2_Checklist/F09_제작/01_조합데이터_트리탐색.md)

## 할 일

`FERItemRow` 에 **재료 2개**를 붙이고, 두 방향 조회를 만든다:
- **정방향** "A + B 로 무엇이 되나" (제작 실행 · UI 의 조합 후보)
- **역방향** "C 를 만들려면 무엇이 필요한가" → **잎 재료까지 재귀** (파밍 루트 · 자동 제작)

## 데이터 — 결과 행에 재료 2개 (F08 Argument 20 에서 예약한 자리)

```
FERItemRow (끝에 추가)
  CraftMaterialA : FName   // 행 이름 참조. 둘 다 비면 제작 불가(기본 재료 · 보급품)
  CraftMaterialB : FName   // ⭐ 항상 2개 (§3.1 ①). 1개 조합 · 3개 조합 없음
```

⚠ **A/B 순서는 의미 없다** — `망치 + 고무` 와 `고무 + 망치` 는 같다. 조회 시 정렬해서 비교.
⚠ 같은 재료 2개(`쇠구슬 + 쇠구슬`)가 있는가 — (미확인). 있어도 구조는 같다 (수량 검사만 2개).

## 조회 — 테이블에서 **인덱스를 한 번** 만든다

수백 행을 매번 훑지 않는다. 테이블 로드 시 한 번:
- `TMap<TPair<FName,FName>, FName>` 정방향 (정렬된 쌍 → 결과)
- `TMultiMap<FName, FName>` 역방향 (재료 → 그 재료를 쓰는 결과들) — "이 돌멩이로 뭘 만들 수 있나"
- 테이블이 바뀌면(에디터 재임포트) 인덱스 무효화

## 재귀 트리 — `C 를 만들려면?`

```
Expand(C) :
  C 에 재료가 없으면 → 잎 (C 자체를 모아야 한다)
  아니면 → Expand(A) ∪ Expand(B)
결과: 잎 재료 목록 + 수량 (같은 잎이 여러 갈래에서 나오면 합산)
```
- 깊이 제한을 두지 않는다 — 데이터가 순환하면(A 가 A 를 요구) **에러 로그 + 중단** (방문 집합)
- "이미 가진 것" 을 빼는 계산(`남은 재료`)은 인벤토리를 받아 **02 · UI** 가 한다. 여기는 순수 함수 — 테이블만 읽는다

## 검증 — PIE 1인 (네트워크 없음)

- **빌드 통과**
- ⭐ 망치 계열 §3 표 17종을 `DT_Items` 에 넣고 `ER.Craft.Tree 토르의망치` → `망치 + 고무 → 사슴 망치`, `사슴 망치 + 트럼프 카드 → 운명의 망치`, `+ 배터리` — 잎: 망치 · 고무 · 트럼프 카드 · 배터리
- ⭐ `ER.Craft.Tree 피스브링어-진홍` → 잎: 망치 · VF 혈액 샘플 · 진홍의 샤드 (**건너뛰기** 가 그대로 나온다, §3.1 ④)
- `ER.Craft.With 망치` → 사슴 망치 · 워해머 · 개밥바라기 · 레비아탄 · 뿅망치 · 피스브링어 (역방향)
- 순환 데이터를 일부러 넣으면 에러 로그 후 멈춘다 (무한 루프 · 스택 오버플로 없음)
- 행 500개로 늘려도 인덱스 조회는 즉시 (한 번 만든 뒤 O(1))

## 주의점

- ⭐ **순수 함수** — 인벤토리 · 액터를 모른다. 서버 · 클라 · UI 가 같은 답을 낸다
- ⚠ 행 이름이 ID 다 — 재료 이름 오타는 인덱스 생성 때 **에러 로그**로 (조용히 "제작 불가" 가 되면 못 찾는다)
- ⚠ F08 의 `FERItemRow` 끝에 붙인다. 기존 필드 순서 불변
