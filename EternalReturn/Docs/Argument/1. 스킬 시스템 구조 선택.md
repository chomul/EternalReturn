# 1. 스킬 시스템 구조 선택

> 작성일 2026-09-02 · 대상 문서 [`../GameDesign/Systems/스킬_프레임워크_역기획서.md`](../GameDesign/Systems/스킬_프레임워크_역기획서.md)
> 작성 근거: `CLAUDE.md` §1.2 (구현 방안이 2개 이상이면 비교 문서를 먼저 만든다)

## 0. 결정할 것

**"스킬 1개의 실행 로직을 무엇이 들고 있는가."**

데이터(수치·형상·쿨다운)를 데이터 테이블에 둔다는 것은 이미 정해져 있다 — 역기획서의 `FSkillRow` 스키마가 그것이다.
갈리는 것은 **"카티야 Q가 거리에 따라 피해를 보간한다"는 그 로직 자체가 어디에 사는가**뿐이다.

> ⚠ **이 문서가 만들어진 이유:** [`스킬_프레임워크_역기획서.md`](../GameDesign/Systems/스킬_프레임워크_역기획서.md) 「데이터 스키마 제안」은
> 이미 **방안 A**(`UERSkillBase` UObject 파생)를 전제로 스키마를 짜 두었다. **비교 없이 정해졌다.**
> A가 틀렸다는 뜻이 아니라, 되돌리기 비용이 큰 선택인데 근거가 남아 있지 않다는 뜻이다.

---

## 1. 전제 — 이 결정이 감당해야 하는 것

### 1.1 규모: 스킬 38개

| 구분 | 개수 | 근거 |
|---|---|---|
| 실험체 스킬 | **30** = 6인 × (P·Q·W·E·R) | [`../GameDesign/Characters/`](../GameDesign/Characters/) 6개 문서 |
| 무기 D스킬 | **8** | [`../GameDesign/Systems/무기계열_D스킬_역기획서.md`](../GameDesign/Systems/무기계열_D스킬_역기획서.md) §4.2 선별 8종 |
| F(전술) 슬롯 | **0** | 「구현 우선순위」에서 M1 범위 밖으로 잘라냄 |
| **합계** | **38** | |

### 1.2 ⭐ 가장 중요한 전제 — **"단순한 스킬"이 거의 없다**

역기획서 §8 「6인이 요구하는 스킬 형태」는 **23종의 형태**를 나열한다.
그 표를 30개 실험체 스킬에 되짚어 분류하면 이렇게 된다.

| 캐릭터 | 데이터만으로 표현 가능 | 전용 로직이 필요 |
|---|---|---|
| 카티야 | — | P(다음 평타) Q(거리 보간) W(설치물·피해 0) E(반대 방향 도약) R(채널링·다단·자동 대상) |
| 매그너스 | **Q, E** | P(스택) W(채널링·다단·**런타임 스탯 의존**) R(커스텀 이동 모드) |
| 재키 | — | P(출혈 스택) Q(돌진+리캐스트) W(다음 평타) E(도약+쿨 초기화) R(**슬롯 변형**) |
| 다니엘 | **Q** | W(표식 상태 머신) E(도약+상태) R(채널링·다단) |
| 시셀라 | **E, W** | Q(소환물 왕복) R(자기 대상 피해) |
| 레니 | — | P(표식·**제3자 발동**) Q·W·E(**아군/적 분기**) R(설치물) |
| **합계** | **5개 (약 17%)** | **25개 (약 83%)** |

> **이 분류는 §8 표를 근거로 한 판단이며, 인게임 확인값이 아니다.** 경계가 애매한 것(시셀라 W = 체력 코스트만 특이)은 데이터 쪽으로 넣었다.
>
> ⭐ **결론: 이 게임에서 "설정만 바꾸면 되는 스킬"은 6분의 1도 안 된다.**
> 아래 방안 B와 D는 전부 **"대부분의 스킬이 단순하다"는 가정 위에 서 있다.** 그 가정이 이 프로젝트에서는 성립하지 않는다.

### 1.3 복제되는 상태는 스킬이 아니라 **컴포넌트**에 있다

역기획서 §9 네트워크 설계표를 보면, 복제 대상은 **쿨다운 만료 시각 · 시전 상태 · 스킬 레벨 배열 · 코스트** 이고
전부 `UERSkillComponent`가 들고 있는 값이다. **스킬 오브젝트 자체가 복제될 이유가 없다.**

이게 중요한 이유: `UObject`를 복제하려면 `bReplicateUsingRegisteredSubObjectList`(`Engine/Classes/GameFramework/Actor.h:493`) +
`AddReplicatedSubObject()`(`:3926`), 혹은 레거시 `ReplicateSubobjects()`(`:835`) 를 다뤄야 한다.
**스킬을 UObject로 만들어도 그 비용을 치르지 않는다** — 방안 A의 가장 큰 기술적 우려가 여기서 사라진다.

### 1.4 GAS는 지금 켜져 있지 않다 — ⚠ **결정 시점 기록. 지금은 켜져 있다**

| 확인 항목 | 값 | 출처 |
|---|---|---|
| 엔진에 GAS 플러그인 존재 | O | `C:/UnrealEngine-5.4.4/Engine/Plugins/Runtime/GameplayAbilities/` |
| 기본 활성화 | **X** | `GameplayAbilities.uplugin:13` `"EnabledByDefault" : false` |
| 이 프로젝트에서 활성화 | **X** | `EternalReturn.uproject` — `Plugins` 배열에 `ModelingToolsEditorMode` 뿐 |
| 모듈 의존성 | **X** | `Source/EternalReturn/EternalReturn.Build.cs:13` — GAS 없음 |
| 켜면 따라오는 것 | `GameplayTags`, `GameplayTasks` | `GameplayAbilities.Build.cs:18-19` |

## 2. 방안 A — 스킬 1개 = 클래스 1개 (`UObject` 파생)

```cpp
// UERSkillBase : public UObject
class UERSkill_Katja_Q : public UERSkillBase
{
    virtual bool CanActivate() const override;
    virtual void ActivateSkill(const FSkillTargetData& Target) override
    {
        // 거리 비례 보간은 여기에만 존재한다
        const float Alpha = FMath::Clamp(Dist / Row->RangeMax, 0.f, 1.f);
        ...
    }
};
```
클래스 38개. 수치·형상은 `FSkillRow`에서 읽고, **행동만** 클래스가 갖는다.

**장점**
- §1.2의 83%(전용 로직 필요)를 **자연스럽게 수용**한다. 특이한 스킬이 특이한 코드를 갖는 게 이상하지 않다.
- 한 스킬을 고칠 때 **파일 하나만 열면 된다.** 다른 37개에 영향이 없다.
- **엔진 자신이 이 구조다.** `class GAMEPLAYABILITIES_API UGameplayAbility : public UObject` (`GameplayAbility.h:108`) — GAS의 어빌리티도 UObject 파생 클래스 1개다.
- 복제 부담 없음 (§1.3).

**단점**
- **클래스 파일이 38쌍(.h/.cpp) 늘어난다.** 폴더가 무거워진다.
- 공통 로직을 의식적으로 뽑지 않으면 **복붙이 번식한다.** §8이 지적한 "다음 평타 강화"가 4곳(카티야 P·재키 W·시셀라 Q·권총 D)에 흩어질 위험이 실제로 있다.
- 스킬 1개 추가 = C++ 빌드. 디자이너가 못 만진다.

**이 프로젝트 기준 비용**
- 구현 난이도: **낮음.** 특별한 기법이 없다.
- 네트워크 비용: **없음** (§1.3).
- GAS 전환 시: **구조가 1:1로 남는다.** `UERSkill_Katja_Q` → `UGA_Katja_Q`. 부모 클래스와 대기 처리(`UAbilityTask`)가 바뀌고, **`ActivateSkill()` 본문의 판단 로직은 상당 부분 그대로 옮겨간다.** 38개를 하나씩 기계적으로 옮기는 작업이 된다.

## 3. 방안 B — 데이터 테이블 + 단일 실행기

```cpp
void UERSkillComponent::Execute(const FSkillRow& Row)
{
    switch (Row.CastForm)
    {
    case ESkillCastForm::Instant:     DoInstant(Row);   break;
    case ESkillCastForm::Channeled:   DoChannel(Row);   break;
    case ESkillCastForm::MultiHit:    DoMultiHit(Row);  break;
    ...
    }
}
```
스킬 전용 클래스가 없다. 전부 데이터이고, 공용 실행기가 `CastForm`을 해석한다.

**장점**
- **클래스가 안 늘어난다.** 스킬 추가가 데이터 테이블 행 추가로 끝난다 — **이론상은.**
- 밸런스 수정에 빌드가 필요 없다.
- 모든 스킬이 **같은 경로**를 지나므로 로그·디버깅 지점이 하나다.

**단점**
- ⭐ **§1.2의 83%를 담을 자리가 없다.** 매그너스 W의 `11 + floor(추가방어력/35)`, 카티야 Q의 거리 보간, 다니엘 W의 4초 대기 → 2.5초 폭발 윈도우, 레니 P의 제3자 발동 — 전부 `CastForm` 열거형으로 표현되지 않는다.
- 결국 **`if (RowName == "Magnus_W")` 형태의 예외 분기가 실행기 안에 쌓인다.** 25개의 예외가 한 함수에 모이면 그게 `AERCharacterBase`에 스킬 로직을 박는 것과 다르지 않다 (`CLAUDE.md` §8이 금지한 것).
- ⭐ **엔진이 같은 이야기를 해 둔 곳이 있다.** GAS의 `NonInstanced` 정책 주석:
  *"a NonInstanced Ability **cannot have state**"* / *"This ability is never instanced. Anything that executes the ability is operating on the **CDO**."* (`GameplayAbilityTypes.h:40-41, 45-46`)
  이 게임의 스킬은 **상태를 가진다** — 표식(다니엘 W·레니 P), 스택(매그너스 P·재키 P), 리캐스트 윈도우(재키 Q), 채널링 진행도. **상태 없는 실행 모델이 애초에 안 맞는다.**

**이 프로젝트 기준 비용**
- 구현 난이도: 초기엔 **가장 낮고**, 스킬 10개를 넘기면서 **가장 높아진다.**
- 네트워크 비용: 없음.
- GAS 전환 시: ⭐ **가장 나쁘다.** 스킬별 코드 단위가 애초에 없었으므로, 전환은 **38개를 백지에서 다시 쓰는 작업**이 된다. 실행기는 통째로 버려진다.

## 4. 방안 C — 지금 바로 GAS

**장점**
- 나중에 버릴 코드를 **아예 만들지 않는다.** 쿨다운·코스트·대기 처리·태그 기반 CC 차단이 전부 이미 있다.
- `UAbilityTask`(채널링·몽타주 대기), `ActivationBlockedTags`(CC로 시전 차단), Cooldown/Cost `GameplayEffect` — 역기획서 GAS 대응표에서 "버려짐"으로 표시된 항목 **전부가 처음부터 완성품**이다.
- 예측(prediction)·타겟 데이터·어트리뷰트가 검증된 상태로 온다.

**단점**
- ⭐ **`CLAUDE.md` §8과 정면으로 충돌한다.** — *"지금 당장 GAS로 마이그레이션하지 않는다. 전환은 사용자가 명시적으로 지시하는 별도 작업이다."*
  **C를 고르는 것은 스킬 시스템을 정하는 게 아니라 프로젝트 규칙을 바꾸는 결정이다.**
- 학습 비용이 크다. ASC를 PlayerState에 둘지 Pawn에 둘지부터 정해야 하고([`../GameDesign/Systems/네트워크_서버아키텍처_역기획서.md`](../GameDesign/Systems/네트워크_서버아키텍처_역기획서.md) §10), 그 결정은 인벤토리 배치 미결 건과 얽힌다.
- **첫 스킬이 화면에 나오기까지 가장 오래 걸린다.** M1의 검증 기준은 "탑다운 전투가 재미있는가"인데, GAS 배선에 시간을 쓰는 동안 그 질문에 답을 못 한다.
- 플러그인 활성화 + 모듈 의존성 추가가 필요하다 (§1.4). `CLAUDE.md` §9에 따라 **보고 대상 변경**이다.

**이 프로젝트 기준 비용**
- 구현 난이도: **가장 높음.**
- 네트워크 비용: GAS 기본 복제를 그대로 쓰게 되므로 24명 규모에서 **별도 측정 필요**.
- GAS 전환 시: 전환이 없다 (이미 GAS).

## 5. 방안 D — 데이터 기본 + 예외만 클래스 (A와 B의 혼합)

단순한 스킬은 공용 `UERSkill_Generic` 하나가 데이터로 처리하고, 특이한 스킬만 전용 클래스를 만든다.

**장점**
- 이론상 클래스 수가 38 → 필요한 만큼으로 준다.
- 단순 스킬 추가가 데이터로 끝난다.

**단점**
- ⭐ **§1.2에 따르면 이 방안의 전제가 성립하지 않는다.** 데이터만으로 되는 스킬이 **30개 중 5개**다.
  38개 중 33개가 전용 클래스면, **A와 사실상 같은 구조에 "예외 판정"이라는 갈래길만 하나 더 붙은 것**이다.
- "이건 Generic으로 되나 안 되나"를 스킬마다 판단해야 한다. **경계가 흔들리면 같은 종류의 스킬이 두 방식으로 나뉜다.**

**이 프로젝트 기준 비용**
- 구현 난이도: A보다 약간 높음(분기 기준을 유지해야 함).
- GAS 전환 시: A와 동일하되, Generic으로 처리한 5개는 B처럼 다시 써야 한다.

## ⭐ 결정 (2026-09-02) — **방안 C: GAS**

사용자가 **방안 C(지금 바로 GAS)** 를 선택했다. 아래 §7의 추천(방안 A)은 **채택되지 않았다.**

**반영된 것**

| 대상 | 변경 |
|---|---|
| `CLAUDE.md` §8 | 「GAS 전환 계획」 → **「GAS 기반 개발」** 로 교체. 전환 유보 조항 삭제 |
| `EternalReturn.uproject` | `Plugins` 에 `GameplayAbilities` 추가 |
| `EternalReturn.Build.cs` | `GameplayAbilities`, `GameplayTags`, `GameplayTasks` 추가 |
| `Docs/Task` / `Docs/Checklist` | F00 신설, F02·F03 재작성, F01·F04 수정 |

**§7이 C를 추천하지 않았던 이유와 그 처리**

- *"`CLAUDE.md` §8과 정면 충돌한다"* → **§8을 고쳐서 해소했다.** 규칙 변경은 사용자 결정이었다.
- *"M1의 질문이 '탑다운 전투가 재미있는가'인데 GAS 배선에 시간을 쓰는 동안 답이 미뤄진다"* → **여전히 유효한 위험이다.** F00(기반 세팅)을 최대한 얇게 유지해 이 비용을 줄인다.
- *"ASC 배치 결정이 인벤토리 배치 미결 건과 얽힌다"* → **F00에서 먼저 정한다.** 더 미룰 수 없게 됐다.

**이 문서가 여전히 유효한 부분**

§1.2의 조사 결과 — **이 게임의 스킬은 83%가 자기만의 로직을 갖는다** — 는 GAS에서도 그대로 적용된다.
그래서 `UGameplayAbility` 를 **어빌리티마다 하나씩** 만든다. `NonInstanced` 정책으로 데이터 구동하려는 시도는 하지 않는다
(엔진 주석: *"a NonInstanced Ability cannot have state"* — `GameplayAbilityTypes.h:40`).
즉 **방안 A의 형태를 GAS 위에서 그대로 쓴다.**

## 7. 추천

### ⭐ **방안 A — 스킬 1개 = 클래스 1개.** 단, 두 가지 조건을 붙인다.

**왜 A인가 — 이유는 하나다.**
§1.2가 보여주듯 **이 게임의 스킬은 83%가 자기만의 로직을 갖는다.**
B와 D는 "대부분이 단순하다"는 전제 위에 서 있는데, **그 전제가 이 프로젝트에서 거짓**이다.
전제가 틀린 설계는 초반에만 싸고, 예외가 25개 쌓이는 시점에 반드시 다시 쓰게 된다.

**A를 뒷받침하는 두 번째 근거는 엔진이다.**
`UGameplayAbility : public UObject` (`GameplayAbility.h:108`) — **GAS도 어빌리티마다 클래스 하나다.**
즉 A는 GAS로 가는 임시방편이 아니라 **GAS와 같은 모양**이고, 전환은 부모 클래스 교체에 가까워진다.

**조건 1 — 공용 로직을 먼저 만든다.**
§8이 이미 짚었다: **"다음 기본 공격 강화"가 4곳에서 같은 구조**다(카티야 P · 재키 W · 시셀라 Q · 권총 D).
캐릭터별로 따로 짜면 무장 해제 CC 하나 넣을 때 4곳을 고쳐야 한다.
`UERSkillTargeting`(판정 형상)과 함께 **"다음 평타 강화" · "표식" · "리캐스트 윈도우"를 공용 부품으로 먼저** 만든다.

**조건 2 — 대기 상태는 한 가지 패턴으로 통일한다.**
역기획서가 이미 지적한 대로, GAS 전환에서 가장 크게 버려지는 것은 **"기다리는 코드"** 이고 `UAbilityTask`가 그걸 전부 대체한다.
채널링·리캐스트 윈도우·표식 타이머를 **각자 다르게 짜지 말고 "타이머 + 델리게이트" 한 패턴으로** 통일하면, 전환 시 패턴 하나만 치환하면 된다.

### 방안 C에 대해

**기술적으로는 C가 가장 깨끗합니다.** 다만 `CLAUDE.md` §8이 "GAS 전환은 사용자가 명시적으로 지시하는 별도 작업"이라고 못 박아 둔 상태라, **C를 고르는 것은 제 판단으로 할 수 있는 일이 아닙니다.**
C로 가겠다고 하시면 §8을 함께 고치고, 플러그인 활성화와 모듈 의존성 추가를 §9에 따라 보고하겠습니다.
다만 **M1의 질문이 "탑다운 전투가 재미있는가"라는 점**은 짚어두고 싶습니다 — GAS 배선에 시간을 쓰는 동안 그 질문은 미뤄집니다.
