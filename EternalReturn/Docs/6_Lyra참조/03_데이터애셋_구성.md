# Lyra 참조 — 데이터 애셋이 데이터 애셋을 담는 방식

읽은 파일: `Source/LyraGame/Character/LyraPawnData.h`, `AbilitySystem/LyraAbilitySet.h`,
`Input/LyraInputConfig.h`, `AbilitySystem/LyraAbilityTagRelationshipMapping.h`,
`GameFeatures/GameFeatureAction_AddAbilities.h`

> 질문 (2026-09-08): *"데이터 애셋이 다른 데이터 애셋을 포함할 수 있지?
> 캐릭터 스탯 데이터 애셋, 애니메이션 데이터 애셋, 스킬 관련 데이터 애셋 이걸 전체를 가지고 있는
> 캐릭터 데이터 애셋 이런 형식으로"*
>
> → **된다. 그리고 Lyra 가 정확히 그 구조다.**

## 1. `ULyraPawnData` 가 다른 데이터 애셋을 담는다

```cpp
// LyraPawnData.h:35-51
UPROPERTY(EditDefaultsOnly, BlueprintReadOnly, Category = "Lyra|Pawn")
TSubclassOf<APawn> PawnClass;                                            // :35

UPROPERTY(EditDefaultsOnly, BlueprintReadOnly, Category = "Lyra|Abilities")
TArray<TObjectPtr<ULyraAbilitySet>> AbilitySets;                         // :39  ← 데이터 애셋

UPROPERTY(EditDefaultsOnly, BlueprintReadOnly, Category = "Lyra|Abilities")
TObjectPtr<ULyraAbilityTagRelationshipMapping> TagRelationshipMapping;   // :43  ← 데이터 애셋

UPROPERTY(EditDefaultsOnly, BlueprintReadOnly, Category = "Lyra|Input")
TObjectPtr<ULyraInputConfig> InputConfig;                                // :47  ← 데이터 애셋

UPROPERTY(EditDefaultsOnly, BlueprintReadOnly, Category = "Lyra|Camera")
TSubclassOf<ULyraCameraMode> DefaultCameraMode;                          // :51
```

## 2. ⭐ 베이스 클래스를 갈라 쓴다 — 담긴다고 다 Primary 가 아니다

| 클래스 | 베이스 | 근거 |
|---|---|---|
| `ULyraPawnData` | `UPrimaryDataAsset` | `LyraPawnData.h:23` |
| `ULyraAbilitySet` | `UPrimaryDataAsset` | `LyraAbilitySet.h:124` |
| `ULyraInputConfig` | **`UDataAsset`** | `LyraInputConfig.h:39` |
| `ULyraAbilityTagRelationshipMapping` | **`UDataAsset`** | `LyraAbilityTagRelationshipMapping.h:42` |

**기준:** AssetManager 가 **독립적으로 찾고 로드할 대상**만 `UPrimaryDataAsset` 이다.
부모에 딸려만 가면 되는 것은 `UDataAsset` 으로 충분하다.

⚠ 전부 Primary 로 만들면 AssetManager 스캔 대상과 쿠킹 규칙만 늘어난다.

---

## 3. ⭐⭐ 결정적인 것 — 참조 종류가 로딩을 가른다

| 참조 | 동작 |
|---|---|
| `TObjectPtr<T>` | **하드.** 부모를 로드하면 **자식도 같이** 올라온다 |
| `TSoftObjectPtr<T>` / `TSoftClassPtr<T>` | **소프트.** 경로만 갖고 있다가 요청할 때 로드 |

⭐ **하드로만 엮으면 쪼갠 의미가 없다.**
`DA_Katya` 를 로드하는 순간 애니메이션·스킬·이펙트가 전부 딸려 온다.

### Lyra 가 경계를 어디에 두나

`ULyraPawnData` 안쪽은 **전부 하드**다 (`:39` `:43` `:47`).
소프트는 **게임 피처 경계**에서만 나온다:

```cpp
// GameFeatureAction_AddAbilities.h
TSoftClassPtr<UGameplayAbility>                 AbilityType;         // :25
TSoftClassPtr<UAttributeSet>                    AttributeSetType;    // :39
TSoftObjectPtr<UDataTable>                      InitializationData;  // :43
TArray<TSoftObjectPtr<const ULyraAbilitySet>>   GrantedAbilitySets;  // :65
```

**규칙:**

| | |
|---|---|
| 같은 로드 단위 **안** | **하드** (`PawnData` → `AbilitySet`) |
| 로드 단위 **사이의 경계** | **소프트** (게임 피처 → 콘텐츠) |

Lyra 는 "실험체별로 안 쓰는 것을 빼는" 문제를 **한 단계 위(Experience/게임 피처)** 에서 푼다.
우리는 캐릭터 단위라 경계 위치가 다를 수 있다 — §5 참고.

## 4. ⚠ 카테고리로 쪼개지 않는다 — 로드 단위로 쪼갠다

*"스탯 애셋 / 애니메이션 애셋 / 스킬 애셋"* 처럼 **개념 분류로 나누는 것은 함정**이다.

⭐ 판단 기준은 하나다: **"이걸 따로 로드하거나 안 로드할 일이 있나?"**

| 후보 | 따로 뺄까 | 이유 |
|---|---|---|
| **스탯** | ❌ **인라인 struct 유지** | 124 B 고, 캐릭터를 쓰는데 스탯만 빼놓을 상황이 없다. 애셋을 나누면 기획자가 파일 두 개를 연다 |
| **애니메이션** (몽타주·애님BP) | ✅ | **데디케이티드 서버는 필요 없다** · 무겁다 |
| **스킬** (어빌리티 + 이펙트) | ✅ | 스킬 단위로 재사용·교체된다 |
| **인풋 설정** | ⭕ `UDataAsset` | 여러 실험체가 공유한다 (Lyra 도 이 형태) |

## 5. 우리 프로젝트에 적용하면

### 지금 (F02)

```cpp
UCLASS(BlueprintType, Const)
class UERCharacterData : public UPrimaryDataAsset
{
    UPROPERTY(EditDefaultsOnly, Category = "스탯")
    FERCharStats BaseStats;      // 인라인. 지금은 이것뿐이다
};
```

### 최종적으로 갈 모양 (예상)

```cpp
UPROPERTY(EditDefaultsOnly, Category = "스탯")
FERCharStats BaseStats;                              // 인라인 유지

UPROPERTY(EditDefaultsOnly, Category = "연출")
TSoftObjectPtr<UERCharacterVisualData> Visual;       // 메시·애님 — 서버는 안 쓴다

UPROPERTY(EditDefaultsOnly, Category = "스킬")
TArray<TSoftObjectPtr<UERSkillData>> Skills;         // P/Q/W/E/R
```

⚠ **지금 만들지 않는다** (`CLAUDE.md` §2 — 추측성 코드 금지).
`UERCharacterData.h` 주석에 *"메시·어빌리티는 그 기능을 만들 때 여기 붙인다"* 고 적어 뒀다.

### ⭐ 실제 구성은 기능을 붙일 때 그때 정한다

사용자 방침 (2026-09-08): *"나중에 이건 구현하면서 또 따로 얘기해보자 다른 기능들 추가될 때"*

각 기능을 시작할 때 `CLAUDE.md` §1.1 대로 구조를 먼저 합의한다.
그때 물어야 할 것:

- [ ] 이 데이터를 **따로 로드/언로드할 일이 있나?** (없으면 인라인)
- [ ] **서버가 필요로 하나?** (연출은 대부분 아니다 → 소프트)
- [ ] **여러 실험체가 공유하나?** (공유하면 별도 `UDataAsset`)
- [ ] AssetManager 가 **독립적으로 찾아야 하나?** (아니면 `UDataAsset`)

관련 기능: F06(스킬) · 애니메이션 · F09(장비) · F12(야생동물)

## 6. ⚠ 소프트 참조는 그냥 쓰면 `nullptr` 이다

`TSoftObjectPtr` 는 **경로만** 들고 있다. 역참조 전에 명시적으로 로드해야 한다.

| 방법 | 쓸 곳 |
|---|---|
| `SoftPtr.LoadSynchronous()` | 간단하지만 **끊긴다.** 게임플레이 중에 쓰지 않는다 |
| `UAssetManager::GetStreamableManager().RequestAsyncLoad(...)` | 정석. 로딩 화면·매치 시작 때 |

⚠ **로딩 타이밍을 정하지 않고 소프트 참조를 넣으면**
"에디터에서는 되는데 패키징하면 안 나오는" 문제가 된다.
소프트로 바꿀 때는 **누가 언제 로드하는지**를 같이 정한다. **(현재 해당 없음 — 소프트 참조 아직 없음)**
