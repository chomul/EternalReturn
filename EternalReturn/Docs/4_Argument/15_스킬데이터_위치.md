# 15. 스킬 데이터를 어디에 둘 것인가

> F07-01 · 근거 [`스킬_프레임워크_역기획서.md`](../0_GameDesign/Systems/스킬_프레임워크_역기획서.md) §1 · §2.2 · 데이터 스키마 제안

## ⭐ 결정 — 2026-09-12

| 항목 | 결정 |
|---|---|
| 스킬 데이터 위치 | ⭐ **방안 B — 별도 `UERSkillData` 데이터 애셋** |
| 어빌리티 → 데이터 | `FGameplayAbilitySpec::SourceObject` (Lyra 와 같은 자리) |

사용자 결정: *"방안 B로 진행하자"*

## 결정할 것

**스킬의 수치(피해 · 계수 · 쿨다운 · 코스트 · 형상)를 어디에 두고, 어빌리티가 어떻게 읽는가.**

⚠ **지금 정해야 한다.** 나중에 옮기면 만들어 둔 애셋을 전부 다시 만든다.
⚠ 다만 **필드는 지금 필요한 것만** 만든다 (`CLAUDE.md` §2). 위치가 이 문서의 논점이고 필드는 아니다.

---

## ⭐ 먼저 — 역기획서가 요구하는 것

### 수치는 전부 레벨별 배열이다

> *"`FSkillRow`의 수치는 전부 `TArray<float>`(길이 5 또는 3)여야 하고, 사거리·반경·속도만 스칼라다.
> 단일 `float BaseDamage + float PerLevel` 구조로 만들면 레니 E(쿨 고정)와
> 시셀라 E(0.5초 단위)에서 즉시 깨진다."* — §2.2

### D 슬롯 데이터는 캐릭터 밖에서 온다

> *"D스킬의 데이터 출처가 **실험체 테이블이 아니다** — `FWeaponProficiencyRow::DSkillClass`"* — §1.2

⭐ 즉 **스킬 데이터는 캐릭터에만 붙어 있으면 안 된다.** 무기도 스킬을 갖는다.

### 로직과 수치를 나눈다

> *"**로직은 어빌리티에, 수치는 데이터 테이블에.**"* — 데이터 스키마 제안

⚠ "데이터 테이블" 은 [`4_스탯데이터_저장방식⭐.md`](4_스탯데이터_저장방식⭐.md) 에서
**데이터 애셋으로 바꿨다.** 역기획서의 "테이블" 은 "코드 밖의 데이터" 라는 뜻으로 읽는다.

---

## ⭐ Lyra 는 어떻게 하나

`ULyraGameplayAbility` 자체는 **정책만** 갖는다 — `ActivationPolicy`, `ActivationGroup`, `AdditionalCosts`
(`LyraGameplayAbility.h:188-197`). 피해량·사거리 같은 수치가 **없다.**

수치는 **별도 객체**에 있고 어빌리티가 참조해서 읽는다:

```cpp
// LyraGameplayAbility_RangedWeapon.cpp:356-392
ULyraRangedWeaponInstance* WeaponData = GetWeaponInstance();
InputData.EndAim = ... WeaponData->GetMaxDamageRange();
const int32 BulletsPerCartridge = WeaponData->GetBulletsPerCartridge();
```

```cpp
// LyraRangedWeaponInstance.h:100-128 — 수치는 여기
UPROPERTY(EditAnywhere, Category="Spread|Fire Params") float SpreadExponent;
UPROPERTY(EditAnywhere, Category="Spread|Fire Params") FRuntimeFloatCurve HeatToSpreadCurve;
```

⭐ **어빌리티 = 로직, 인스턴스 = 수치.** 같은 `RangedWeapon` 어빌리티 로직을 소총·권총이 공유하고
수치만 다르다.

⚠ Lyra 의 "인스턴스" 는 데이터 애셋이 아니라 **인벤토리 아이템 런타임 객체**다 — 무기가 교체되니까.
우리 캐릭터 스킬(P/Q/W/E/R)은 교체되지 않으므로 **데이터 애셋**이 맞다. D 슬롯만 무기를 따라간다(F11).

---

## 방안 A — 어빌리티 BP 클래스에 수치를 둔다

`UERGameplayAbility` 에 `EditDefaultsOnly TArray<float> Damage` 등을 두고,
캐릭터·스킬마다 **BP 서브클래스**를 만든다 (`GA_Katja_Q`, `GA_Jackie_Q` …).

**장점**
- 가장 단순하다. 어빌리티를 열면 로직과 수치가 한눈에 보인다
- 참조 관계가 없다

**단점**
- ⚠⚠ **같은 로직인데 수치만 다르면 BP 가 늘어난다.** "투사체 스킬" 로직 하나를
  6인 × 여러 스킬이 쓰면 그만큼 서브클래스가 생기고, **로직을 고치면 상속으로 퍼지지만
  수치 실수는 각 BP 를 열어야 찾는다**
- ⚠ **D 슬롯이 안 맞는다.** 무기 데이터(`FWeaponProficiencyRow`)가 스킬 수치를 갖는데,
  A 에서는 수치가 어빌리티 클래스 안에 있어서 무기가 그걸 소유할 수 없다
- ⚠ 기획자가 "카티야 Q 의 5레벨 피해" 를 보려면 **어빌리티 BP 를 열어야 한다** —
  로직 그래프와 수치가 한 화면에 섞인다

---

## 방안 B — 별도 `UERSkillData` 데이터 애셋, 어빌리티가 참조 ⭐

```
DA_Katja_Q  (UERSkillData)
  ├─ SlotTag       = Ability.Slot.Q
  ├─ AbilityClass  = GA_Projectile          ← 로직 (재사용)
  └─ (수치는 F07-02 이후 필드가 붙는다)

DA_Katja      (UERCharacterData)
  └─ Skills[]  = { DA_Katja_P, DA_Katja_Q, DA_Katja_W, DA_Katja_E, DA_Katja_R }

어빌리티는 부여될 때 자기 UERSkillData 를 받아 들고, 수치는 거기서 읽는다.
```

**장점**
- ⭐⭐ **Lyra 와 같은 구조** — 어빌리티는 로직, 데이터는 수치. 그 *이유*(로직 재사용)가 우리에게도 성립한다
- ⭐ **D 슬롯이 자연스럽다.** 무기 데이터가 `UERSkillData` 를 하나 들면 된다 (F11)
- ⭐ 기획자가 수치를 볼 때 **로직 그래프를 안 본다**
- ⭐ [`4_스탯데이터_저장방식⭐.md`](4_스탯데이터_저장방식⭐.md) 의 결정과 **같은 형태** —
  캐릭터 데이터 애셋이 하위 애셋을 묶는다 ([`6_Lyra참조/03`](../6_Lyra참조/03_데이터애셋_구성.md) §5 의 "최종 모양" 그대로)
- 스킬 단위로 **재사용·교체**된다 — Lyra 참조 03 §4 가 "로드 단위로 쪼갠다" 에서 ✅ 로 표시한 항목

**단점**
- ⚠ 어빌리티가 **자기 데이터를 어떻게 받는지** 설계가 필요하다 (아래)
- ⚠ 애셋이 하나 더 생긴다 (스킬마다)
- ⚠ 데이터 애셋이 `AbilityClass` 를 참조하고, 어빌리티가 데이터를 받는 **양방향**이 된다 —
  순환은 아니지만 어느 쪽이 주인인지 명확히 해야 한다 → **데이터가 주인**이다. 어빌리티는 받기만 한다

---

## 방안 C — `UERCharacterData` 안에 인라인 `TArray<FERSkillDef>`

별도 애셋 없이 캐릭터 데이터 안에 구조체 배열로 둔다.

**장점**
- 애셋이 안 늘어난다. 캐릭터 하나 = 애셋 하나
- 문서 4 의 "인라인" 원칙과 일치한다

**단점**
- ⚠⚠ **D 슬롯이 못 들어간다.** 무기 스킬은 캐릭터 밖에 있어야 한다 —
  같은 구조체를 무기 데이터에도 두면 **정의가 두 곳**이 된다
- ⚠ 스킬 하나를 **재사용**(다른 캐릭터가 같은 스킬을 쓴다)할 수 없다. 복사해야 한다
- ⚠ Lyra 참조 03 §4 가 "로드 단위로 쪼갠다" 에서 스킬을 **쪼개는 쪽**으로 표시했다

## ⭐ 추천 — 방안 B

**D 슬롯이 갈랐다.** 역기획서 §1.2 가 *"슬롯 교체 경로 자체는 M1 에 넣어야 한다. 나중에 붙이면
스킬 소유권 모델을 다시 짜야 한다"* 고 경고한다. A·C 는 스킬 수치가 **캐릭터에 묶여** 있어서
무기가 스킬을 소유할 수 없다. B 만 "스킬 데이터 하나" 를 캐릭터도 무기도 들 수 있다.

⭐ 그리고 **Lyra 가 같은 이유로 같은 구조**를 쓴다 — 로직 하나를 여러 무기가 수치만 바꿔 공유한다.

### 어빌리티가 데이터를 받는 방법

⭐ GAS 에 이미 자리가 있다 — `FGameplayAbilitySpec::SourceObject`.
`GiveAbility` 할 때 `SourceObject` 에 `UERSkillData` 를 넣으면,
어빌리티가 `GetCurrentSourceObject()` 로 꺼낸다. **새 필드가 필요 없다.**

⚠ Lyra 도 이 자리를 쓴다 — `LyraAbilitySet.cpp:120` 에서 `AbilitySpec.SourceObject = SourceObject`.

### 만들 것 (F07-01)

| 파일 | 역할 |
|---|---|
| `GAS/ERSkillData.h` (새로) | `UPrimaryDataAsset`. **지금은 `SlotTag` + `AbilityClass` 뿐** |
| `GAS/ERGameplayAbility.h/.cpp` (새로) | 베이스. `GetSkillData()` 로 SourceObject 를 꺼낸다 |
| `GAS/ERAbilitySet.h/.cpp` (새로) | Lyra 형태 부여 + 핸들 회수 |
| `Character/ERCharacterData.h` | `TArray<TObjectPtr<UERSkillData>> Skills` 추가 |

⚠ **수치 필드는 붙이지 않는다.** F07-02(쿨다운)·03(코스트)·05(판정)에서 각자 붙인다.
지금 `TArray<float> Damage` 를 넣으면 F07-05 에서 무엇이 필요한지 모르는 채로 정하는 게 된다.

### ⚠ 하드 참조인가 소프트인가

`UERCharacterData` → `UERSkillData` 는 **하드**(`TObjectPtr`)로 시작한다.
캐릭터를 로드하면 스킬은 **반드시** 필요하고 따로 언로드할 일이 없다
(Lyra 참조 03 §5 의 질문 — *"따로 로드/언로드할 일이 있나? 없으면 인라인 또는 하드"*).
⚠ 어빌리티 BP(`AbilityClass`)는 `TSubclassOf` 라 그 자체가 하드다. 메시·이펙트가 어빌리티에
직접 붙으면 딸려 오지만, 그건 `GameplayCue` 로 분리한다 (`CLAUDE.md` §8).
