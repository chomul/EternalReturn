# 28. 스킬 기능이 늘 때마다 `UERSkillData` 에 필드를 붙여야 하나 — 평면 필드 유지 vs 조각(Fragment) 조합 vs 스킬별 클래스

## ⭐ 결정 — 2026-09-21

**방안 B (조각 조합)** · 시점 **F11-05 D 검증 → F11 완료 판정 → F11.5 조각화** — 사용자 확인 *"D 검증부터 하고 F11 끝나면 조각화 하자"*.
메모리는 근거가 아니다 (안 쓰는 필드 71개 ≈ 애셋당 1 KB) — 근거는 유지보수: 새 방식마다 공통 파일을 건드리는 것 · 무관한 필드 노출 · 순서가 코드에 박힌 것.

## 지금 상태 (문제의 실체)

`UERSkillData` 는 UPROPERTY **71개**. F07 때 20개였던 것이 F11-05 8종을 거치며 배가 됐다 — 무기 D 하나가 평균 필드 5개를 요구했다.
`UERGameplayAbility.cpp` 는 1,320줄 · 함수 42개. 파이프라인은 `ResolveAim → 리캐스트 → 자기이동 → ExecuteSkill → 피해 → 넉백 → 적중상태 → 자기버프 → 2차판정 → 모드` 로,
**새 기능 = 필드 추가 + 이 파일에 분기 추가** 다.

이대로 실험체 33명 × 5스킬을 붙이면:
- 필드가 200개를 넘고, 애셋 하나를 열면 그 스킬과 무관한 필드 190개가 같이 보인다 (지금도 단검 D 애셋에 `Area*` `Knockback*` `Mode` 가 보인다)
- 기능끼리의 **순서** 가 코드에 박혀 있어 "넉백 뒤 2차 판정" 같은 조합은 되고 "2차 판정 뒤 넉백" 은 안 된다 — 순서를 바꾸려면 코드
- `ExecOverride` 처럼 "이번 실행은 다른 데이터" 를 흉내내는 우회가 늘어난다

반면 **데이터 애셋 하나에 다 있다** 는 장점도 실재한다: 디자이너가 한 화면에서 본다, 저장 · 복제 · CSV 대조가 쉽다, 코드가 한 파일이라 디버깅이 직선이다.

## 방안 A — 평면 유지 + 구조체로 묶기만 (지금 방식의 정리)

`Mode` · `Shape` · `SelfEffects` 처럼 기능 단위 USTRUCT 로 묶어 카테고리를 접는다. 파이프라인은 그대로.
- 장점: 코드 변화 거의 없음 · 애셋 그대로
- 단점: **성장 자체는 못 막는다.** 필드 수 · 분기 수는 똑같이 늘고, 순서도 여전히 코드. "정리" 일 뿐 "구조" 가 아니다

## 방안 B — 조각(Fragment) 조합 ⭐ 추천 (Lyra 아이템 정의 패턴)

```cpp
UCLASS(DefaultToInstanced, EditInlineNew, Abstract)
class UERSkillFragment : public UObject
{
    /** 판정 뒤(적중 대상 확정 뒤) — 피해 · 넉백 · 적중 효과 · 흡혈 */
    virtual void OnTargetsResolved(FERSkillContext& Ctx, const TArray<AActor*>& Targets) const {}
    /** 판정 전 — 자기 이동 · 자기 버프 · 모드 진입 */
    virtual void OnExecute(FERSkillContext& Ctx) const {}
    /** 끝날 때 — 리캐스트 창 · 모드 정리 */
    virtual void OnEnd(FERSkillContext& Ctx, bool bCancelled) const {}
};

// UERSkillData — 핵심(슬롯 · 클래스 · 쿨 · 코스트 · 레벨 · 형상)은 그대로 평면. 기능은 배열.
UPROPERTY(EditDefaultsOnly, Instanced, Category = "기능")
TArray<TObjectPtr<UERSkillFragment>> Fragments;
```

기능 하나 = 클래스 하나: `Fragment_Damage` · `_Knockback(+WallImpact)` · `_OnHitEffect` · `_SelfMove` · `_SelfBuff` · `_FollowUp(Delay, SkillData)` · `_Recast(Window, SkillData, bAlways)` · `_Area` · `_Mode` · `_HealFromDamage` · `_FixedCurHP`.
어빌리티는 `ResolveAim → Fragments.OnExecute → 판정 → Fragments.OnTargetsResolved → (후딜) → Fragments.OnEnd` 만 안다.
`FERSkillContext` 가 지금 어빌리티 멤버(AimPoint · AimActor · Level · ExecOverride · 어빌리티 포인터)를 든다.

- 장점
  - **새 기능 = 새 클래스 파일 1개.** `UERSkillData` · `UERGameplayAbility` 를 안 건드린다 (수술적 변경 §3 이 자연히 지켜진다)
  - 애셋에는 **그 스킬이 쓰는 조각만** 보인다. 순서는 배열 순서 — 디자이너가 정한다
  - 2차 판정 · 리캐스트가 "다른 SkillData 로 재실행" 이라 `ExecOverride` 우회가 사라진다 — 조각이 `Ctx.Execute(OtherData)` 를 부른다
  - Lyra 가 같은 이유로 아이템 정의에 쓴 패턴 (`LyraInventoryItemDefinition.h:43` `Instanced TArray<Fragment>`). GameFeatureAction 도 같은 구조. **1st-party 검증**
  - 실험체 고유 기믹(톤파 반사 · 알렉스 교체)도 조각 하나로 격리된다
- 단점
  - **이관 비용**: 기존 71개 중 기능 필드 ~35개를 조각으로 옮기고, 테스트 애셋 ~15개를 다시 찍는다 (에디터 작업 반나절 · 코드 1~2일). CSV 로 못 찍는다 (Instanced 객체)
  - 조각끼리 **의존**이 있으면 순서 규칙이 필요하다 — 예: `_Recast` 는 "적중했나" 를 `_Damage` 결과에서 읽는다 → Ctx 에 `bHitAnything` 같은 공유 상태. 지금 코드의 암묵 순서를 **문서화된 규칙**으로 바꾸는 작업
  - 검색이 한 단계 어려워진다 — "어느 스킬이 넉백을 쓰나" 는 필드 grep 이 아니라 조각 클래스 참조 검색
  - `EditInlineNew` 객체는 DataAsset 안에 서브오브젝트로 저장된다 — 복제 · 리네임 시 UE 의 Instanced 처리에 익숙해야 한다

## 방안 C — 스킬마다 어빌리티 서브클래스 (C++ 또는 BP)

`GA_Katja_E : UERGameplayAbility` 처럼 스킬당 클래스. 데이터는 수치만.
- 장점: 무엇이든 된다 · 조각 순서 문제 없음
- 단점: 33 × 5 = 165 클래스 · 공통 로직이 복붙되거나 베이스가 다시 비대해짐 · BP 로 가면 §7 (로직은 C++) 위반. Lyra 의 `GA_Weapon_Fire` 가 이 방식인데 **Lyra 는 무기 4종** 이라 성립하는 것

## 추천과 시점

⭐ **방안 B**. 단 **지금 당장은 아니다** — 이유:
1. F11-05 D 검증이 남아 있다. 검증 안 끝난 코드를 옮기면 두 가지 원인이 섞인다
2. 이관은 **애셋을 전부 다시 찍는 작업**이라 한 번에 해야 한다. 지금 테스트 애셋 15개 → 실험체를 붙이기 시작하면 수십 개. **F11 끝 · F12(실험체) 시작 전**이 가장 싸다
3. E18 의 F10 재설계(Argument 26)도 같은 시점에 예정돼 있다 — 둘 다 "데이터 구조 이관" 이라 붙여서 하는 게 맞다

**제안 순서**: F11-05 D 검증 → F11 완료 판정 → **F11.5 스킬 조각화** (Argument 28 B, 자체 태스크로 체크리스트 작성) → E18 A 항목 → F12.

이관 범위 (초안):

| 남기는 평면 필드 (핵심) | 조각으로 옮기는 것 |
|---|---|
| SlotTag · AbilityClass · Cooldowns · bIgnoreCooldownReduction · CooldownTagOverride · CostType · Costs · Shape · CastTime · RecoveryTime · bMoveCancelsCast · InitialLevel · MaxLevel · bUsesSkillPoints · MinCharacterLevel | DamageType+계수 6종 → `_Damage` · OnHit 4종 → `_OnHitEffect` · SelfMove 3종 → `_SelfMove` · SelfEffects → `_SelfBuff` · Knockback 3종 → `_Knockback` · FollowUp 2종 → `_FollowUp` · Recast 4종 → `_Recast` · Area 4종 → `_Area` · Mode → `_Mode` · HealFromDamage → `_Lifesteal` · FixedCurHP · MaxHP · TargetLostHP → `_Damage` 옵션 |

"피해" 를 조각으로 뺄지는 이관 태스크에서 다시 본다 — 거의 모든 스킬이 쓰므로 핵심에 남기는 쪽이 애셋 작업이 적다.
