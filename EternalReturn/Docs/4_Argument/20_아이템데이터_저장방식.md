# 20. 아이템 데이터를 어디에 두는가 — 데이터 테이블 vs 데이터 애셋

> F08-01 · 근거 [`장비_아이템_역기획서.md`](../0_GameDesign/Systems/장비_아이템_역기획서.md) §6.2 · [`무기계열_D스킬_역기획서.md`](../0_GameDesign/Systems/무기계열_D스킬_역기획서.md) §4.3 · §9
> 관련 [`4_스탯데이터_저장방식⭐.md`](4_스탯데이터_저장방식⭐.md) — 실험체 스탯은 **애셋**으로 정했다. ⚠ 같은 결론일 필요는 없다

## ⭐ 결정 — 2026-09-17

| 항목 | 결정 |
|---|---|
| 저장 방식 | ⭐ **방안 A — 데이터 테이블 한 개 (`DT_Items`)** |
| ⭐ 정의 / 인스턴스 분리 | **정의**(이 표, 전원 동일, 게임 중 불변) / **인스턴스**(F08-04 `FERItemInstance { ItemId, Count, … }`, 서버 권위 + `COND_OwnerOnly`). 수량 · 강화 같은 실시간 상태는 인스턴스에 — 사용자 논의로 명시 |
| 행 구조 | `FERItemRow : FTableRowBase` (CLAUDE.md 네이밍 규칙 "데이터 테이블 행은 `F~Row`") |
| 아이템 ID | 행 이름(`FName`) — 제작 재료 참조 · 인벤토리 복제 · 드롭 액터가 전부 이 이름으로 가리킨다 |
| 아이콘 · 메시 | `TSoftObjectPtr` — 수백 개가 한꺼번에 로드되면 안 된다 |
| 조회 창구 | `UERItemSettings : UDeveloperSettings` 에 테이블 소프트 참조 → `ERItem::Find(Id)` 한 함수 |

사용자 결정: *"(a) 야 A 로 진행하자"* — 논의: "서버·클라가 모든 아이템 데이터를 가져야 하고, 캐릭터마다 다른 장비를 갖고, 실시간으로 바뀐다" →
앞은 테이블도 애셋도 같다(둘 다 양쪽 빌드에 포함, 오가는 건 ID), 뒤 둘은 **정의가 아니라 인스턴스의 일**이라 그릇 선택과 무관. (a) = 인스턴스 상태로 확인

## 결정할 것

**아이템 수백 개의 수치(등급 · 슬롯 · 무기군 · 스탯 옵션)를 데이터 테이블 한 개에 두나, 아이템별 데이터 애셋에 두나.**

F02 에서 실험체 스탯은 애셋으로 갔다 (사용자 판단, [`4`](4_스탯데이터_저장방식⭐.md)). 그때 이유는 **실험체 하나가 무겁다**(메시 · 애님 · 스킬 참조가 한 애셋에 모인다)는 것이었다.
아이템은 정반대 성질이다 — 그래서 문서를 따로 쓴다.

| | 실험체 (F02) | 아이템 (F08) |
|---|---|---|
| 개수 | ~80 | **수백** (원작 400+) |
| 개당 내용 | 스탯 + 메시 + 애님 + 스킬 5개 | 스탯 몇 개 + 아이콘 |
| 전체 순회 | 없음 | ⭐ **제작 트리(F09)가 전부 훑는다** — "X 를 만들려면?" 역탐색 |
| 서로 참조 | 없음 | ⭐ **재료 A/B 가 다른 아이템을 가리킨다** (항상 2개) |
| 누가 편집 | 프로그래머 + 디자이너 | **디자이너가 표로** — 원작 위키 자체가 표다 |

## 방안 A — 데이터 테이블 한 개 (`DT_Items`, 행 = 아이템)

```
FERItemRow : FTableRowBase
  Grade (EERItemGrade) · Slot (EEREquipSlot) · WeaponType (EERWeaponType, 무기일 때만)
  StatModifiers : TMap<FGameplayAttribute, float>     ← §6.1 옵션. 어트리뷰트를 직접 가리킨다
  Icon : TSoftObjectPtr<UTexture2D>
  (F09) CraftMaterialA / B : FName                     ← 행 이름 참조
```

- 장점
  - **전체 순회가 공짜** — `GetAllRows` 한 줄. 제작 트리 역탐색 · 파밍 UI 가 이걸 쓴다
  - **행 이름 = ID** 가 곧 참조 키 — 재료 A/B · 인벤토리 슬롯(`FName` 하나 복제) · 드롭 액터가 전부 가볍다
  - 조회 `FindRow` 는 `TMap` 해시 — 수백 개여도 O(1) (체크리스트 "개수가 늘어도 느려지지 않는다")
  - CSV/구글시트 **임포트** — 원작 위키 표를 그대로 옮긴다. 디자이너가 400행을 애셋 400개로 만들지 않는다
  - CLAUDE.md 네이밍 규칙이 이미 "데이터 테이블 행은 `F~Row` + `FTableRowBase`" 를 전제한다
- 단점
  - 행 구조를 바꾸면(필드 추가) 테이블 전체가 영향 — 다만 **필드 추가는 기본값으로 안전**하고, 순서 변경만 위험 (열거형과 같은 규칙)
  - 행 하나에 로직을 붙일 수 없다 (애셋은 클래스라 함수를 가질 수 있음) → 고유 효과(격동 · 처형)는 **별도 시스템**(6순위)이라 어차피 행에 안 붙는다
  - 아이템 하나만 열어 보기가 애셋보다 불편 (표에서 찾아야 함)

## 방안 B — 아이템별 `UPrimaryDataAsset` (`DA_Item_*`) + Asset Manager

- 장점
  - 실험체(F02)와 **같은 꼴** — 한 가지 방식만 배우면 된다
  - 애셋마다 함수 · 파생 클래스 가능 (무기 애셋 / 방어구 애셋 …)
  - `TSoftObjectPtr` 참조가 자연스럽다
- 단점
  - ⚠ **전체 순회에 Asset Manager 등록이 필요** — `PrimaryAssetType` · 스캔 경로 설정 · `GetPrimaryAssetIdList` + 로드. 제작 트리가 "전부" 를 물을 때마다 애셋 로딩 관리가 끼어든다
  - 재료 참조가 `TSoftObjectPtr<UERItemData>` — 역탐색("이 재료로 뭘 만드나")은 결국 전부 로드해서 뒤진다
  - 수백 개 애셋 = 수백 파일. 위키 표 → 애셋 변환 도구를 따로 만들어야 한다
  - 인벤토리 복제에 애셋 참조(경로 문자열)가 실린다 — `FName` 보다 무겁다

## 방안 C — 테이블(수치) + 애셋(무거운 것) 하이브리드

- 아이템 수치는 테이블, 메시 · 이펙트처럼 무거운 것은 별도 애셋을 행이 소프트 참조
- 장점: A 의 순회 + B 의 무게 분리
- 단점: 지금 무거운 것이 **없다** (아이콘 하나). 필요해지면 A 의 행에 `TSoftObjectPtr` 필드를 더하는 것이 곧 C 다 — **A 가 자라서 C 가 된다**, 별도 방안이 아니다

## 비교표

| 축 | A 테이블 | B 애셋 | C 하이브리드 |
|---|---|---|---|
| 구현 난이도 | ⭐ 낮음 (구조체 1 + 설정 1) | 중 (Asset Manager 설정 · 변환 도구) | A 와 같음 |
| 확장성 (F09 제작 트리) | ⭐ 순회 · 역탐색 공짜 | 로드 관리 필요 | A 와 같음 |
| 네트워크 | ID = `FName` | 애셋 경로 | `FName` |
| GAS 정합성 | `TMap<FGameplayAttribute,float>` 가 표에서 편집됨 | 같음 | 같음 |
| 성능 | `FindRow` O(1) · 테이블 1개 로드 | 애셋 N개 개별 로드 | A |
| 디자이너 편집 | ⭐ 표 · CSV 임포트 | 애셋 400개 | 표 |

## 추천 — **방안 A**

F02 가 애셋으로 간 이유("실험체 하나가 무겁다")가 아이템에는 **성립하지 않고**, 반대로 아이템에만 있는 요구("전부 훑는다 · 서로 가리킨다 · 표로 편집한다")는 전부 테이블 쪽이다.
**"같은 프로젝트니 같은 방식"** 은 근거가 아니다 — 데이터의 성질이 다르면 그릇도 달라야 한다.

⚠ A 에서 지킬 것 둘:
1. **행 구조에 필드를 더할 때는 끝에, 열거형은 순서 고정** — 테이블 · 애셋에 저장된 값이 어긋난다 (CLAUDE.md §3)
2. **행 이름이 ID** 이므로 이름을 바꾸면 재료 참조 · 저장 데이터가 끊긴다. 이름은 영문 스네이크(`sniper_rifle_t1`)로 처음부터 안정적으로

## ⭐ 후속 판단 (2026-09-17, 사용자 질문 "장비와 재료를 같은 DT 에?")

**ID 공간은 하나여야 한다** — 가방 칸 · 드롭 · 습득 · 제작 재료 참조가 전부 "아이템 하나" 로 다루므로 정체성 + 공통 필드(이름 · 등급 · 아이콘 · MaxStack · 슬롯)는 한 테이블.
**종류별 필드는 열을 늘리지 않는다** — 지금은 장비 전용이 `WeaponType` · `StatModifiers` 둘뿐이라 재료 행에서 비워 두면 된다.
소비(회복량 · 지속) · 특수(효과 ID) 아이템이 생기는 단계(F09 / F15)에서 **같은 행에 `TInstancedStruct<FERItemPayload>` 하나**로 종류별 구조체를 싣는다
(장비 → `FEREquipmentPayload`, 소비 → `FERConsumablePayload`). 보조 테이블 조인(B)은 ID 를 두 곳에 맞춰야 해서 안 한다.
지금 미리 바꾸지 않는 이유: 종류가 하나(장비)일 때 variant 를 넣는 것은 추측 설계 (CLAUDE.md §2). 5행이라 그때 옮겨도 싸다.

## 이번에 안 하는 것

- `CraftMaterialA/B` — F09. 테이블에 필드 추가는 안전하므로 그때 붙인다
- 고유 효과 ID — 6순위 (트리거형 별도 시스템)
- 무기 계열 테이블(`FWeaponClassRow`, 23종 D스킬) — F11. 여기서는 **`EERWeaponType` 열거형(23종 자리)만** 만든다 — 장착 제한(F08-02)이 쓴다
