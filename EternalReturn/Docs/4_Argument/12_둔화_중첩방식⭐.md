# 12. 둔화가 여러 개 겹치면 어떻게 되는가

> F06-02 · 근거 [`전투판정_상태이상_역기획서.md`](../0_GameDesign/Systems/전투판정_상태이상_역기획서.md) §3.3 · §4

## 결정할 것

**둔화 2개 이상이 동시에 걸렸을 때 이동속도를 어떻게 계산할 것인가.**

⚠ 역기획서가 이 규칙을 **(미확인)** 으로 남겼다 —
*"CC 동시 중첩: 동일/이종 CC 동시 적용 시의 갱신 규칙 **(미확인)**"* (§4)

---

## ⭐ 원작 조사 (2026-09-10) — 먼저 찾아봤다

결정하기 전에 원작 규칙을 검색했다. **3회 검색 + 위키 2곳 확인.**

### ✅ 확인된 것 — 하한이 원작에도 있다

> *"Movement speed decreases by a percentage. **It does not go below a certain level.**"*
> — [나무위키 이터널 리턴/가이드](https://en.namu.wiki/w/%EC%9D%B4%ED%84%B0%EB%84%90%20%EB%A6%AC%ED%84%B4/%EA%B0%80%EC%9D%B4%EB%93%9C)

⭐⭐ **원작에도 이동속도 하한이 있다.** 정확한 값은 공개돼 있지 않지만,
우리 `MinMoveSpeed = 1.0` 클램프(`ERStatCapSettings.h:79`)는 **원작 재현이지 임의 장치가 아니다.**

→ 이것이 아래 추천의 근거를 강화한다. "다중 둔화로 완전 정지" 는 원작에서도 일어나지 않는다.

### ✅ 확인된 것 — 이동 방해 ≠ 이동 불가

> *"움직이긴 하는데 느리게 움직이는 **둔화, 춤**은 **이동 방해**에 들어가고,
> 우클릭을 해도 안 움직이는 **기절, 속박, 에어본, 도발, 제압, 매혹, 공포, 넉백, 경직**은
> **이동 불가**에 들어간다"*
> — [아카라이브: 간단하게 알아보는 이동 방해와 이동 불가](https://arca.live/b/bser/129146888)

⭐ **우리 설계와 정확히 대응한다.**

| 원작 | 우리 |
|---|---|
| 이동 **불가** | `State.Block.Movement` → CMC `GetMaxSpeed()` = 0 |
| 이동 **방해**(둔화) | `MoveSpeed` 어트리뷰트 감소 (이 문서) |

→ 둔화를 축 태그가 아니라 어트리뷰트로 처리하기로 한 F06-02 의 전제가 **원작과 맞다.**

### ⚠ 못 읽은 것 — 중첩 규칙 (⭐ 유력한 단서는 찾았다)

**둔화 여러 개가 동시에 걸렸을 때의 계산은 위키에 없다.**
공식 위키(Statistics) · 나무위키(가이드) · Steam 데미지 공식 가이드 전부 언급이 없다.

⭐⭐ 그러나 커뮤니티에서 **제목만으로도 방향을 시사하는 글**을 찾았다:

| 글 | URL |
|---|---|
| ⭐⭐ **"머야 둔화 가장높은것만 적용임?"** | https://arca.live/b/bser/95340123 |
| "이동속도 정리해놓은곳 없냐?" | https://arca.live/b/bser/150030626 |

⚠⚠ **arca.live 가 봇을 차단한다 (HTTP 403).** 본문과 댓글을 읽을 수 없었고,
검색 스니펫도 제목만 노출한다. **여러 각도로 5회 검색했으나 본문 확보 실패.**

⭐ **제목이 사실이라면 방안 B(가장 강한 것 1개)가 원작이다.**

### ⭐⭐ LoL 규칙으로 보강 — 같은 방향을 가리킨다

사용자 제안 (2026-09-10): *"미정의 규칙은 lol 데이터로 가져올 수 있니
어차피 비슷한 류의 게임이라 이런 규칙들은 거의 동일할 거라서"*

[LoL 공식 위키 — Slow resist](https://wiki.leagueoflegends.com/en-us/Slow_resist) 확인 결과:

| 항목 | LoL 규칙 |
|---|---|
| ⭐⭐ **다중 둔화** | *"Only the slow with the **highest value** is taken into movement speed calculations. All additional slows are **ignored until** the higher-valued slow wears off."* |
| ⭐ **Slow resist** | *"reduces the **strength** of multiplicative (= percentage) slows"* — **강도**. 지속시간 아님 |
| ⭐ **하한** | *"Slows based on a percentage value cannot reduce a target below **110 movement speed**"* |
| 둔화 "종류" 구분 | **없다.** 퍼센트 값만 비교한다 |

### ⭐⭐ 이것이 방안 B 의 최대 단점을 없앤다

아래 방안 B 의 단점으로 *"지속시간이 다르면 약한 둔화를 제거해야 해서 문제"* 라고 적었는데,
**LoL 은 제거하지 않는다. 무시할 뿐이다.**

```
60% 둔화 1초  +  30% 둔화 5초
  → 1초 동안 60% 적용 (30% 는 붙어 있지만 무시)
  → 1초 뒤 60% 가 만료되면 30% 가 남은 4초 동안 적용
```

⭐ **제거가 아니라 "계산에서 빼는 것"** 이다. 지속시간은 각자 정상적으로 흐른다.
→ 내가 B 의 결정적 결함으로 본 것은 **B 를 잘못 구현했을 때의 문제**였다.

### 세 출처가 일치한다

| 출처 | 다중 둔화 | 하한 |
|---|---|---|
| ER 나무위키 가이드 | (없음) | ⭐ *"일정 수준 이하로 내려가지 않는다"* |
| ER 아카라이브 (제목) | ⭐ *"둔화 가장높은것만 적용임?"* | (없음) |
| LoL 공식 위키 | ⭐ **가장 높은 것만, 나머지는 무시** | ⭐ **110 MS 하한** |

⚠ **arca 본문은 여전히 못 읽었다** (403). 하지만 **독립된 두 출처가 같은 방향**이고,
LoL 쪽은 공식 위키의 명시적 서술이다.

### ⚠ LoL 을 가져올 때의 원칙

**"LoL 이 그러니까" 는 근거가 아니다** — `CLAUDE.md` §11 이 Lyra 에 대해 정한 것과 같다.
가져올 수 있는 것과 없는 것을 구분한다.

| 가져온다 | 가져오지 않는다 |
|---|---|
| ⭐ **저수준 관례** — 중첩·우선순위·하한의 *형태* | 구체적 수치 (110 MS, 저항 공식) |
| 두 게임 다 MOBA 계보라 관례가 굳어진 영역 | ER 고유 시스템 (실험체 스탯 33개, 제작·매치) |

⚠ **수치는 안 가져온다.** LoL 의 110 MS 하한은 LoL 의 이동속도 체계(325~400) 기준이다.
우리는 m/s 단위(기본 3.5)라 **값이 아니라 "하한이 있다"는 구조만** 가져온다.
우리 하한은 `ERStatCapSettings` 의 `MinMoveSpeed` 로 이미 있다.

⭐ **가져온 항목은 문서에 "LoL 관례에서 가져옴 (ER 원작 미확인)" 으로 표시한다.**
나중에 ER 실측이 나오면 그 표시를 단서로 다시 본다.

### ⚠⚠ 함께 발견 — 역기획서와 상충하는 정보 (F06-05 소관)

**이동속도 감소 저항(`SlowResist`)이 무엇을 줄이는지에 대해 출처가 갈린다.**

| 출처 | 내용 |
|---|---|
| 우리 역기획서 §4 | *"둔화 **지속시간**을 감소"* |
| [나무위키 가이드](https://en.namu.wiki/w/%EC%9D%B4%ED%84%B0%EB%84%90%20%EB%A6%AC%ED%84%B4/%EA%B0%80%EC%9D%B4%EB%93%9C) | *"Duration of the effect ... **decreases**"* — 지속시간 |
| ⚠ [공식 위키 Statistics](https://eternalreturn.fandom.com/wiki/Statistics) | *"diminish the **potency**"* — **강도** |
| ⚠ 한국어 검색 결과 | 20% 저항 + 40% 둔화 → 8%p 경감 (→ 32% 둔화). **강도** 기반 |

⚠ **2:2 로 갈린다.** 지금 정하지 않는다 — `SlowResist` 는 **F06-05** 소관이고,
그때 인게임 툴팁이나 실측으로 확정한다. **여기서는 상충 사실만 기록한다.**

## ⭐ 먼저 — GAS 의 Multiply 는 곱이 아니다

이걸 모르면 방안 비교가 성립하지 않는다.

```cpp
// GameplayEffectAggregator.cpp:78
return ((InlineBaseValue + Additive) * Multiplicitive) / Division;
```

```cpp
// GameplayEffectAggregator.cpp:194-207
float FAggregatorModChannel::SumMods(const TArray<FAggregatorMod>& InMods, float Bias, ...)
{
    float Sum = Bias;
    for (const FAggregatorMod& Mod : InMods)
        if (Mod.Qualifies())
            Sum += (Mod.EvaluatedMagnitude - Bias);
    return Sum;
}
```

```cpp
// GameplayEffectTypes.cpp:106  — Additive=0, Multiply=1, Division=1, Override=0
static const float ModifierOpBiases[EGameplayModOp::Max] = {0.f, 1.f, 1.f, 0.f};
```

⭐⭐ **Multiply 모디파이어가 여러 개면 `1 + Σ(값 - 1)` 로 합산된다.**

60% 둔화(Multiply 0.4) 두 개:

```
Multiplicitive = 1 + (0.4-1) + (0.4-1) = -0.2      ← ⚠ 음수
MoveSpeed = 3.5 × (-0.2) = -0.7                    → 클램프가 1.0 으로 자른다
```

⚠ **"곱해지겠지" 라고 생각하면 틀린다.** 감소율이 더해진다.

## ⭐ 이미 있는 안전장치

`MoveSpeed` 는 `PreAttributeChange` 에서 `[MinMoveSpeed, MaxMoveSpeed]` 로 잘린다
(`ERAttributeSet.cpp:70-73`, 기본 **1.0 ~ 12.0** — `ERStatCapSettings.h:70,79`).

⭐ **그래서 어떤 방안을 골라도 완전 정지(0)는 나오지 않는다.**
최악의 경우도 **1.0 m/s** 로, 기본 이동속도 3.5 의 **28.6%** 다.

⚠ 이 하한이 실질적으로 "다중 둔화 상한" 역할을 하고 있다.

## 방안 A — GAS 기본 그대로 (Multiply 합산) ⭐

GE 애셋에 `MoveSpeed` `Multiply` 모디파이어를 두고, 값은 `SetByCaller` 로 받는다.

**장점**

- ⭐⭐ **추가 코드가 0 이다.** 애셋만 만들면 된다
- ⭐ 하한 클램프가 이미 있어 **완전 정지가 안 된다** (최소 1.0 m/s)
- F06-01 과 같은 구조 — GE 애셋 + `SetByCaller`
- ⭐ **나중에 B 로 갈 수 있다.** 애셋은 그대로 두고 부여 경로에 비교만 추가하면 된다

**단점**

- ⚠ 둔화 2개면 사실상 **하한에 붙는다.** 60%+60% 이 120% 감소가 된다
- ⚠ 중간 계산이 **음수**가 된다. 클램프가 없으면 뒤로 걷는다
  (지금은 클램프가 있으니 실제 문제는 아니다)
- 원작이 이렇게 동작하는지 **(미확인)**

## 방안 B — 가장 강한 둔화 1개만

치유 감소와 같은 정책 (사용자 결정: *"치유감소는 가장 높은 양 기준으로 1개만 적용"*).

**장점**

- ⭐ **예측 가능하다.** 둔화를 아무리 겹쳐도 최대 감소율이 정해져 있다
- ⭐ 치유 감소 정책과 **일관된다**
- CC 체인으로 정지시키는 플레이가 막힌다

**단점**

- ⚠⚠ **지속시간이 서로 다르면 문제가 생긴다.** 치유 감소는 *피해 계산 시점*에 1회
  판정이라 단순했지만, 둔화는 **지속된다.**

  ```
  60% 둔화 1초  +  30% 둔화 5초
    → 강한 것만 남기려고 30% 를 제거하면
    → 1초 뒤 둔화가 완전히 풀린다 (30% 가 4초 더 남아야 하는데)
  ```

  → 제대로 하려면 약한 둔화를 **제거하지 않고 무효화만** 해야 한다.
  GAS 에 그 개념(`bIsInhibited`)이 있지만 **우리가 직접 제어하는 API 가 아니다**
- ⚠ 구현이 A 보다 확실히 크다. 부여·만료 양쪽에서 재계산이 필요하다

---

## 방안 C — 진짜 곱연산 (0.4 × 0.4 = 0.16)

**장점**

- 겹칠수록 효과가 체감 감소한다. 이론적으로 0 이 되지 않는다
- Dota 계열이 쓰는 방식

**단점**

- ⚠⚠ **GAS 로 직접 표현할 수 없다.** Multiply 도 Division 도 **합산**이다
  (`GameplayEffectAggregator.cpp:194-207`)
- `GameplayModEvaluationChannel` 로 순차 계산이 가능하지만 **채널 수가 고정**이고
  둔화 개수는 가변이라 맞지 않는다
- 별도 어트리뷰트에 곱을 누적하는 구현이 필요하다 — B 보다 복잡하다
- ⚠ 표의 계산대로 **결과가 A 와 크게 다르지 않다** (둘 다 하한에 붙는다).
  복잡도를 지불하고 얻는 것이 적다

---

## 방안 D — 감소율 합산 + 총량 상한 (예: 80%)

**장점**

- 하한 클램프와 별개로 **둔화 총량**에 명시적 상한이 생긴다
- A 보다 예측 가능하다

**단점**

- ⚠ 상한을 **어디서 강제할지**가 문제다. `PreAttributeChange` 는 최종값만 보고
  "이 중 얼마가 둔화 때문인지" 를 모른다
- → 결국 별도 어트리뷰트나 집계 코드가 필요하다. **B 와 비슷한 복잡도**
- ⚠ 상한값 80% 에 **근거가 없다** (미확인). 임의값을 하나 더 만든다

## ⭐⭐ 결정 — 방안 B (가장 강한 둔화 1개만)

> 2026-09-10 · LoL 관례 + 아카라이브 단서로 **A 에서 B 로 변경**

### 왜 B 인가

1. ⭐⭐ **독립된 두 출처가 일치한다** — ER 커뮤니티 글 제목(*"둔화 가장높은것만 적용임?"*)과
   LoL 공식 위키(*"Only the slow with the highest value ... All additional slows are ignored"*)
2. ⭐ **B 의 결정적 결함이 사라졌다.** "지속시간이 다르면 문제" 는 **제거 방식**의 문제였고,
   올바른 구현은 **제거가 아니라 계산에서 무시**하는 것이다 (위 조사)
3. ⭐ **예측 가능하다.** 둔화를 아무리 겹쳐도 최대 감소율이 정해져 있어
   CC 체인으로 묶는 플레이가 구조적으로 막힌다
4. 치유 감소 정책(*"가장 높은 양 기준으로 1개만"*)과 **일관된다**

### 구현 규칙

```
걸린 둔화들 중 감소율이 가장 큰 것 하나만 MoveSpeed 계산에 넣는다.
나머지는 제거하지 않는다 — 지속시간은 각자 흐르고, 계산에서만 빠진다.
가장 강한 것이 만료되면 남은 것 중 가장 강한 것이 자동으로 적용된다.
```

⚠ 하한 클램프는 **그대로 유지한다** (`PreAttributeChange`, F02-03).
B 로 가면 하한에 닿는 일이 줄어들지만, 다른 경로(아이템·지형)로도 이동속도가 깎일 수 있다.

### ⚠ 출처 표시 — 이건 자체 결정값이다

- ⚠ "이동속도가 얼마인가" 를 알려면 **두 값을 조합**해야 한다. 디버그·UI 가 번거로워진다

### 방안 ③ — 서버가 "현재 최강 둔화" GE 하나를 유지한다 ⭐

```
둔화 GE (애셋)         : State.CC.Slow 태그 + SetByCaller.SlowPercent 만.
                        ⭐ MoveSpeed 모디파이어를 **걸지 않는다**
UERSlowEffect (네이티브): MoveSpeed 에 Multiply 모디파이어 하나. Infinite.
                        값은 SetByCaller 로 받는다

서버: 둔화 GE 가 붙거나 떨어질 때마다
      → 활성 둔화들의 SetByCaller 값 중 최대를 구한다
      → UERSlowEffect 를 그 값으로 다시 적용한다 (기존 것은 제거)
      → 둔화가 하나도 없으면 UERSlowEffect 를 제거한다
```

**장점**
- ⭐⭐ **`MoveSpeed` 어트리뷰트가 실제로 깎인다** → **기존 하한 클램프를 그대로 탄다.**
  클램프를 두 곳에서 관리하지 않는다 (F06-02 Task 의 *"여기서 클램프하지 않는다"* 를 지킨다)
- ⭐ 어트리뷰트를 **늘리지 않는다** (33개 유지)
- ⭐ 복제가 자동이다 — `MoveSpeed` 는 이미 복제되는 어트리뷰트다
- ⭐ 디버그·UI 가 단순하다. `MoveSpeed` 하나만 보면 된다
- ⭐ `UERSlowEffect` 는 **조정 대상 수치가 0개**라 네이티브가 맞다 —
  `UERLifestealEffect` 와 **같은 논리**다 ([`9_CC효과_표현방식.md`](9_CC효과_표현방식.md))

**단점**
- ⚠ GE 를 하나 더 관리한다. 붙이고 떼는 타이밍을 우리가 책임진다
- ⚠ 둔화가 바뀔 때마다 GE 재적용이 일어난다 (⚠ 빈도는 낮다 — 둔화 부여·만료 시점뿐)
- ⚠⚠ **제거를 먼저 해야 한다.** `Multiply` 모디파이어는 **합산**되므로(파트 1)
  두 개가 동시에 있으면 값이 틀린다. 같은 함수 안에서 제거→적용하므로
  프레임 경계를 넘지 않아 속도가 튀지는 않는다
- ⚠⚠ **재진입에 주의한다.** `UERSlowEffect` 를 적용·제거하는 것도 GE 델리게이트를 발동시킨다.
  콜백에서 **`UERSlowEffect` 자신은 무시**해야 무한 루프가 안 생긴다
