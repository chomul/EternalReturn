# 34. 낮/밤 시계를 어디에 둘까 — F12-03 스폰이 먼저 필요로 한다

> F12-03 · 제기: 2026-09-23 — 늑대 "낮마다" · 곰 "밤마다" 재생성과 "1일차 02:20" 최초 생성이 **페이즈 카운트다운**에 묶여 있다 (사용자 확인)
> 관련 [`매치진행_게임모드_역기획서.md`](../0_GameDesign/Systems/매치진행_게임모드_역기획서.md) §1 (페이즈 표 · 1~6일차 사용자 확인) · F14 매치 진행(미착수)

## 결정할 것

야생동물 스케줄러는 "지금 몇 일차 · 낮/밤 · 남은 몇 초" 를 알아야 한다. 이 시계는 원래 **F14 매치 진행**의 몫인데 F14 는 아직 없다.
F12-03 에서 시계를 **어디에, 얼마나** 만들까.

## 방안 A — 최소 매치 시계를 지금 `AERGameState` 에 만든다 ⭐ 추천

```cpp
// Core/ERGameState — 복제 (UI · 클라 표시용)
UPROPERTY(ReplicatedUsing=OnRep_Phase) int32 Day = 1;
UPROPERTY(ReplicatedUsing=OnRep_Phase) bool bNight = false;
UPROPERTY(Replicated) float PhaseEndServerTime;          // 남은 시간 = 이 값 − 서버 시각 (매 틱 복제 안 함)
FOnPhaseChanged OnPhaseChanged;                           // (Day, bNight) — 서버 · 클라 모두
float GetPhaseRemaining() const;                          // "1일차 02:20" 표기와 같은 값

// Core/ERGameMode — 서버 타이머로 페이즈를 넘긴다 (Tick 없음)
// 페이즈 길이 표 = UERMatchSettings.PhaseSeconds[] (DeveloperSettings · ini) — 1~6일차 [확인] · 7~8일차 역기획서 값
```
- 장점: F14 가 **그대로 이어받는다** (금지구역 · 부활 · 보스 스폰도 같은 `OnPhaseChanged` 를 구독). 시계가 한 곳이라 두 번 만들 일이 없다
- 장점: 복제 비용 ≈ 0 (페이즈가 바뀔 때만 3개 값)
- 단점: F14 범위를 조금 먼저 당긴다 (시계 + 디버그 명령만. 금지구역 · 부활은 여전히 F14)

## 방안 B — 야생동물 스케줄러 안에 자체 시계

- 장점: F12 안에서 끝남
- 단점: F14 에서 **시계를 다시 만들고 옮겨야** 한다. 옮기기 전까지 시계가 둘 (보스 스폰 · 금지구역이 어느 쪽을 볼지 갈린다)

## 방안 C — 시계 없이 디버그 주입만 (`ER.Wild.SetPhase 1 밤`)

- 장점: 가장 적은 코드
- 단점: 실제 흐름(1일차 02:20 에 닭 → 80초 뒤 늑대 → 밤에 곰)을 **PIE 에서 볼 수 없다**. 고정 주기 재생성과 낮/밤 재생성이 섞이는 순간을 검증 못 한다

## 비교표

| | A GameState 최소 시계 | B 스케줄러 자체 시계 | C 디버그 주입 |
|---|---|---|---|
| 구현 | 중 (GameState · GameMode · 설정) | 중 | 소 |
| F14 재사용 | ✅ 그대로 | ❌ 옮겨야 함 | ❌ 새로 |
| 실제 흐름 검증 | ✅ | ✅ | ❌ |
| 네트워크 | 페이즈 전환 때만 3값 | 같음 (단, 어디 둘지 또 정해야) | 없음 |

## 추천

⭐ **A**. 시계는 매치 전체의 척추라 한 곳에 있어야 하고, 그 자리는 `GameState`(복제) + `GameMode`(서버 진행)가 엔진 관례다.
디버그로 `ER.Match.Skip <초>` · `ER.Match.Phase <일> <낮|밤>` 를 같이 넣어 26분을 기다리지 않고 검증한다.
