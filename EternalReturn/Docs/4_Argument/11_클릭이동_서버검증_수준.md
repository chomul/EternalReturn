# 11. 클릭 이동의 서버 검증을 어디까지 할 것인가

> F05-02 · 계기 [`E08`](../5_ErrorReport/E08_멀티에서_클릭이동_안됨.md) 이후 받은 외부 피드백
> 관련 [`E07`](../5_ErrorReport/E07_클릭이동_서버구동_충돌.md)

## 결정할 것

**클라가 경로를 계산하고 CMC 예측으로 움직이는 현재 구조에서, 서버가 무엇을 어디까지 검증할 것인가.**

---

## ⭐ 먼저 — 현재 구조를 정확히 표현하면

옛 주석과 문서가 이 부분을 부정확하게 적고 있었다. 정확한 표현은 이렇다.

```
❌ 서버가 클라의 경로를 신뢰한다

⭕ 서버는 경로를 알지도, 신뢰하지도 않는다.
   서버는 CMC 가 전달한 movement input(Acceleration)을 authoritative 하게 처리한다.
   클라의 NavPath 는 그 입력을 만들어내는 **로컬 로직**일 뿐이다.
```

즉 `SimpleMoveToLocation` 은 **"경로 계산기 + 입력 생성기"** 로만 쓰이고,
실제 네트워크 이동 계층은 전부 CMC 다.

흐름:

```
[클라] 클릭 → NavMesh 경로 계산 → PathFollowing → AddMovementInput → Acceleration
                                                          ↓ ServerMove RPC
[서버] 받은 Acceleration 을 authoritative 하게 재생 · 위치 검증 · 보정
```

---

## ⚠⚠ 현재 상태의 실제 문제 — 목적지 RPC 가 아무것도 안 한다

`AERPlayerController::ServerSetDestination_Implementation` 은
거리와 네비를 검증한 뒤 **`Resolved` 를 로그만 찍고 버린다.**
서버가 목적지를 저장하는 멤버가 **아예 없다.**

⭐ 그래서 이 RPC 는 "참고값" 조차 아니다. **값이 남지 않으므로 이후 무엇과도 비교할 수 없다.**

그리고 코드 주석이 틀려 있었다:

```cpp
//   → 서버의 권위는 **목적지 검증**과 CMC 의 ServerMove 검증에 있다.
//     이게 텔레포트를 막는 실제 방어선이다.     ← ⚠ 앞의 "목적지 검증" 은 아니다
```

텔레포트를 막는 것은 **CMC 의 `ServerMove` 위치 검증뿐**이다.

---

## ⭐ 위협 정리 — 무엇이 이미 막히고 무엇이 안 막히나

| 위협 | 막히나 | 무엇이 막나 |
|---|---|---|
| 속도 핵 | ✅ | CMC `GetMaxSpeed()` — **서버에서도 호출된다** |
| 순간이동 | ✅ | CMC `ServerMove` 위치 검증 · 보정 |
| 벽 통과 | ✅ | 서버가 재생하며 콜리전 처리 |
| CC 중 이동 | ✅ | F06 의 `GetMaxSpeed()` → 0 (⚠ RPC 필터는 없음) |
| ⭐⭐ **네비메시 밖 지형으로 걸어가기** | ❌ **못 막는다** | — |

### ⚠ 네비메시 이탈이 진짜 허점이다

**CMC 는 네비메시를 모른다. 콜리전만 본다.**

→ **콜리전은 있지만 네비메시가 없는 곳**(맵 경계 경사면, 의도적으로 네비를 뺀 지역)으로
클라가 걸어가면 **서버도 그대로 재생한다.**

`ProjectPointToNavigation` 은 **클릭 지점만** 검사하고 **이동 경로 중간은 아무도 안 본다.**

---

## 방안 A — 현행 유지

목적지 RPC 에서 거리·네비를 검증하고 버린다. CMC 가 나머지를 막는다.

**장점**
- 추가 비용 0
- ⭐ 실제로 속도·텔레포트·벽 통과는 이미 막힌다

**단점**
- ⚠ 목적지 RPC 가 **아무 역할도 안 한다.** 있으면서 없는 코드다
- ⚠ CC·사망 중에도 RPC 가 통과한다 (CMC 가 막으므로 결과는 정상이지만, 걸러야 할 것을 안 거른다)
- ⚠ 틀린 주석이 남아 다음 사람을 오해시킨다

---

## 방안 B — 최소 강화 ⭐

1. 서버가 목적지를 **저장**한다 (`ServerDestination`)
2. `ServerSetDestination` 에 **상태 검증** 추가 — CC(`State.Block.Movement`) · 사망
3. 틀린 주석 정정

```cpp
// ServerSetDestination_Implementation 안
if (IsMovementBlockedByCC()) { return; }   // F06 태그를 그대로 쓴다
// ... 검증 통과 후
ServerDestination = Resolved;              // 버리지 않고 남긴다
```

**장점**
- ⭐ **오탐이 0 이다.** 상태 검증은 판정이 명확하다
- ⭐ 목적지가 서버에 남아 **이후 검증·디버그·리플레이의 토대**가 된다
- F06 이 만든 태그를 재사용한다. 새 개념이 없다
- 변경량이 작다 (20줄 내외)

**단점**
- ⚠ 저장 자체는 **방어가 아니다.** 토대일 뿐
- 네비 이탈은 여전히 못 막는다

---

## 방안 C — B + 이동 방향 sanity check (Dot)

목적지 방향과 실제 `Acceleration` 방향의 내적을 보고 지나치게 어긋나면 거부한다.

```cpp
const float Dot = FVector::DotProduct(
    Acceleration.GetSafeNormal2D(),
    (ServerDestination - Location).GetSafeNormal2D());
if (Dot < 임계값) { /* 거부 */ }
```

**장점**
- 목적지와 실제 이동의 관계를 처음으로 연결한다
- 매 프레임 네비 경로를 재계산하지 않아도 된다

**단점**
- ⚠⚠ **오탐이 구조적이다.** 방향이 크게 어긋나는 것이 **정상인 상황**이 많다

  | 상황 | 실제 Dot |
  |---|---|
  | 코너를 돌아 우회 | 90° 이상 벌어짐 |
  | 좁은 통로 우회 | 같음 |
  | ⭐ **넉백 · 그랩** (F06-04) | **완전히 반대** |
  | 감속 구간 | 0 근처 |

  → 느슨하게(`Dot > -0.5`) 잡으면 방어 의미가 거의 없고,
    조이면(`Dot > 0.5`) **정상 플레이가 막힌다.**

- ⚠⚠ **막으려는 치트의 동기가 없다.** 목적지 RPC 는 **이동을 구동하지 않는다.**
  거짓 목적지를 보내서 얻는 이득이 없다 — 원하는 목적지를 그냥 보내면 된다.
  실제 이동은 `Acceleration` 이 정하고 그건 CMC 가 이미 검증한다.

---

## 방안 D — B + 네비메시 이탈 주기 감지

서버가 주기적으로(예: 1초) 폰 위치를 네비에 투영해 벗어났는지 본다.

```
ProjectPointToNavigation(폰 위치, 작은 Extent) 실패가 N회 연속
  → 로그 · 텔레메트리 (초기)
  → 마지막 정상 위치로 되돌림 (검증 후)
```

**장점**
- ⭐⭐ **실제 허점(네비 밖 이동)을 정면으로 막는다**
- ⭐ 오탐 판정이 Dot 보다 훨씬 명확하다 — "지금 서 있는 곳이 네비 위인가" 는 이진 판정이다
- 주기 검사라 매 프레임 비용이 아니다

**단점**
- ⚠ **오탐 원인이 F13 에 걸려 있다.** 네비메시가 안 깔린 정상 지형이 있으면
  결백한 플레이어가 잡힌다 — `AgentMaxStepHeight` 불일치가 바로 그런 경우였다
- ⚠ 24명 × 1초 쿼리의 비용을 **측정해야 한다** (`ER_Level` 규모)
- ⚠ 되돌리기를 구현하면 **정상 플레이를 망가뜨릴 위험**이 생긴다.
  로그·텔레메트리부터 시작해야 한다

---

## 방안 E — 서버도 경로를 계산한다

⚠ **E07 에서 이미 배제했다.** 서버가 PathFollowing 을 돌리면 클라의 `ServerMove` 재생과
서로를 덮어써서 튄다. 기록으로만 남긴다.

## ⭐ 추천 — **지금 B, D 는 과제로 등록, C 는 채택하지 않음**

### 지금 B 를 한다

오탐이 없고 변경량이 작으며, **목적지가 서버에 남는 것 자체가 D 의 전제**다.
지금 값을 버리고 있으니 나중에 D 를 하려 해도 비교할 대상이 없다.

### D 는 F13 이후로 미룬다

⭐ D 가 **실제 허점을 막는 유일한 방안**이지만, 오탐의 원인이 네비메시 설정에 있다.
`ER_Level` 에서 네비 설정을 확정하기 전에 켜면 **결백한 플레이어를 잡는다.**
(`AgentMaxStepHeight` 35 vs 45 불일치가 정확히 그런 사례였다 — F13 참조)

→ F13 에서 네비를 확정한 뒤, **로그·텔레메트리부터** 시작한다. 되돌리기는 그 다음이다.

### ❌ C 는 채택하지 않는다 — 근거를 남긴다

두 가지 이유 모두 단독으로 충분하다.

1. ⚠ **오탐이 구조적이다.** 우회·넉백·감속에서 방향이 어긋나는 것이 정상이다.
   특히 **넉백·그랩(F06-04)은 목적지와 정반대**로 움직인다
2. ⚠ **막으려는 치트에 동기가 없다.** 목적지 RPC 가 이동을 구동하지 않으므로
   거짓 목적지를 보낼 이유가 없다. 실제 이동은 `Acceleration` 이 정하고 CMC 가 검증한다

⭐ 나중에 누가 다시 제안하면 **이 절을 먼저 읽는다.** 재논의 비용을 줄이기 위해 남긴다.
⚠ 단, 전제가 바뀌면 다시 본다 — 목적지 RPC 가 이동을 구동하게 되면 1·2 가 모두 무효다.

## ⭐ 함께 채택 — 고핑 테스트

피드백에서 받은 것으로, 지금 검증 절차에 **빠져 있던 항목**이다.

```
Net PktLag=100
Net PktLagVariance=30
Net PktLoss=2
```

| 시나리오 | 왜 |
|---|---|
| ① 긴 직선 | 기본 |
| ② 코너 여러 개 | 경로 갱신이 보정 뒤에도 유지되나 |
| ③ 좁은 통로 | 보정으로 경로를 벗어나면 끼는가 |
| ④ 이동 중 방향 급변경 | SavedMove 재생이 꼬이나 |
| ⑤ 이동 중 스킬 · CC | ⭐ F06 의 `GetMaxSpeed()` 0 이 보정과 싸우지 않나 |
| ⑥ 서버 correction 발생 | 경로 추종이 복구되나 |

⚠ **`PathFollowingComponent` 가 서버 보정 이후에도 경로 추종을 유지하는지**가 핵심이다.
지금까지 저지연 로컬 PIE 에서만 봤기 때문에 **(미확인)** 이다.

→ 절차는 [`../3_EditorTasks/F05_입력_카메라_이동.md`](../3_EditorTasks/F05_입력_카메라_이동.md) 에 넣는다.
