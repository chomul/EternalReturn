## ⚠⚠ 초판 측정의 오류 — Yaw 를 0 으로 가정했다 (2026-09-09 정정)

### 어떻게 드러났나

`ER_Level` 의 **`테스트2.png` 와 거의 같은 위치**에서 찍은 우리 화면(`ERYoutube/비교군.png`)을
원본과 나란히 놓으니 차이가 명확했다.

| | `테스트2.png` (원작) | 비교군 (우리, Yaw 0) |
|---|---|---|
| 도로 방향 | **대각선** (좌하→우상, 약 50°) | **수평** |
| 노란 중앙선 · 연석 | 화면에서 **수렴한다** | **평행하다** |

⭐ 지면의 평행선이 화면에서 **수렴하면** 카메라가 그 선을 따라 비스듬히 보는 것이고,
**평행하면** 정확히 직각으로 보는 것이다.

→ **원작 카메라는 월드 축에 대해 비스듬하다. Yaw ≠ 0 이다.**

### 무엇이 무효가 되나

| 측정 | 영향 |
|---|---|
| 방법 ① 원의 타원 비율 → 피치 | ⭕ **영향 적음** — 원은 회전해도 원이다. 다만 화면 중앙에서 벗어난 정도만큼 오차 |
| 방법 ② 도로 소실점 | ❌ **무효** — Yaw 0 을 가정하고 지평선 위치를 계산했다 |
| ①×② 교차로 구한 **FOV 63°** | ❌ **무효** — ②에 의존한다 |
| FOV 로 역산한 **거리 1600** | ❌ **무효** — FOV 에 의존한다 |

⭐ **살아남은 것은 피치의 대략적 크기(40°대)뿐이고, FOV·거리는 근거가 무너졌다.**

### 왜 놓쳤나

세 스크린샷 모두 **같은 Yaw** 로 찍혀 있어서 서로 비교해도 드러나지 않았다.
**우리 화면과 나란히 놓고 나서야** 보였다.

⚠ **교훈: 절대값을 재기 전에 좌표계 가정을 먼저 확인한다.**
"카메라가 월드 축과 정렬돼 있다" 는 검증하지 않은 가정이었다.

### ⭐ 다시 재는 순서 — 얽힘을 끊는 방법

⚠ 도로 각도만 보면 Yaw 와 피치가 얽혀서 안 풀린다 (미지수 2, 식 1).
**바닥 원이 그 얽힘을 끊는다** — 원의 타원 비율은 **피치에만** 의존한다.

| 순서 | 무엇을 | 방법 |
|---|---|---|
| 1 | **Yaw 방향** | 도로 기울기 **+ 장면 배치** 를 원작과 대조 (⚠ 배치를 꼭 본다) |
| 2 | ⭐ **피치** | 우리 게임에 **바닥 원**을 그려 타원 비율을 잰다 — Yaw·FOV 무관 |
| 3 | **Yaw 크기** | 피치를 식에 넣고 도로 각도(원작 약 52°)로 역산 |
| 4 | **FOV** | 피치·Yaw 가 정해지면 소실점 계산이 유효해진다 |
| 5 | **거리** | 마지막. 스크린샷 크기 비교 |

⭐ **2번에 쓸 도구가 이미 있다** — F04 의 디버그 커맨드가 바닥 원을 그린다:

```

ER.Targeting.Test Sphere 10 all
```

`ERTargetingDebug.cpp:335` 의 `DrawGroundCircle` 이 캐릭터 발밑에 노란 원을 그린다.
⚠ 캐릭터를 **화면 중앙 근처**에, **평평한 바닥**에서, 원이 **화면 안에 다 들어오게** 찍는다.

# 파트 1 — 각도 · 거리 · FOV 측정

> ⚠⚠ **아래 측정은 Yaw = 0 을 가정한 것이라 FOV · 거리가 무효다.**
> 방법 자체는 유효하므로 재측정 때 그대로 쓴다. 위의 「초판 측정의 오류」를 먼저 읽는다.

## 측정 자료

원작 스크린샷 3장 (2026-09-09 제공):
`C:/Sung Unreal Project/Eternal Return/ERYoutube/테스트.png` · `테스트2.png` · `테스트3.png`
전부 1919×1079 (16:9).

## ⭐ 방법 ① — 바닥 원의 타원 비율 (FOV 무관)

바닥 평면에 그려진 **원**은 화면에서 **타원**이 된다.

> **단축 / 장축 = sin(피치)**

⭐ **이 관계는 FOV 를 몰라도 성립한다.** 원이 화면 중앙 근처에 있고 카메라에서 충분히 멀면
투시 왜곡이 작아 근사가 잘 맞는다.

`테스트.png` 의 큰 시야 원:

| | 값 |
|---|---|
| 가로(장축) | 약 **920 px** |
| 세로(단축) | 약 **640 px** |
| 비율 | **0.696** |
| → 피치 | **arcsin(0.696) = 44.1°** |

⚠ 원의 경계가 흐려(페이드) 픽셀 측정에 ±20px 오차가 있다. → **피치 ±4°**

## 방법 ② — 도로 평행선의 소실점 (피치 × FOV 관계식)

`테스트2.png` 는 도로가 있어 **월드에서 평행한 선 두 개**를 준다:
노란 중앙 차선과 잔디/도로 경계선.

화면에서 두 선을 연장하면 **y ≈ -950** (화면 위쪽 바깥)에서 만난다.
그 지점이 **지평선**이고, 화면 중앙(y ≈ 538)에서 **1491 px** 위다.

이걸 각도로 바꾸면:

```
tan(피치) = (지평선까지 픽셀) / (화면 절반 높이) × tan(수직FOV / 2)
          = 1491 / 538 × tan(수직FOV / 2)
          = 2.77 × tan(수직FOV / 2)
```

⚠ **이 식만으로는 각도가 안 정해진다.** FOV 에 따라 답이 달라진다:

| 수평 FOV | 수직 FOV (16:9) | 나오는 피치 |
|---|---|---|
| 90° (UE 기본) | 58.7° | **57°** |
| 65° | 39.0° | **45°** |
| 60° | 36.0° | **42°** |

## ⭐⭐ 두 방법을 교차하면 FOV 가 풀린다

방법 ①의 **피치 44°** 를 방법 ②의 식에 넣으면:

```
tan(44°) = 0.966 = 2.77 × tan(수직FOV/2)
tan(수직FOV/2) = 0.349  →  수직FOV = 38.4°
16:9 환산  →  수평 FOV ≈ 63°
```

### 독립적인 뒷받침 — 수직선이 수렴하지 않는다

세 장 모두에서 **전화부스 · 가로등 기둥 · 벽 모서리** 같은 월드 수직선이
화면에서 **거의 수렴하지 않는다.**

⭐ FOV 90° 였다면 화면 가장자리의 수직선이 눈에 띄게 기울어야 한다.
**좁은 FOV** 라는 증거이고, 63° 라는 계산 결과와 방향이 맞는다.

⚠ MOBA 카메라가 좁은 FOV 를 쓰는 것은 흔하다 — 넓으면 화면 가장자리 왜곡이 커진다.

## 거리 — 캐릭터를 기준자로

`테스트.png` 의 캐릭터가 화면에서 약 **125 px** 높이.

```
화면 1079px 이 수직 FOV 38.4°(0.670 rad) 를 덮는다
→ 1610 px/rad
캐릭터 각크기 = 125 / 1610 = 0.0776 rad
수직 물체의 각크기 ≈ 높이 × cos(피치) / 거리
0.0776 = 1.75m × cos(44°) / d
d ≈ 16.2 m = 1620 cm
```

⚠ **가장 불확실한 값이다. ±25%.** 두 가지에 민감하다:
- 캐릭터 키 **1.75m 가정** — 원작 확인값이 아니다 **(미확인)**
- FOV — FOV 가 5° 틀리면 거리가 10% 넘게 움직인다

## 결과 · 오차

| 항목 | 값 | 오차 | 근거 |
|---|---|---|---|
| **피치** | **-44°** | ±4° | 방법 ① (FOV 무관) |
| **수평 FOV** | **63°** | ±5° | ①×② 교차 |
| **거리** | **1600 cm** | ⚠ **±25%** | 캐릭터 키 가정 |

## ⭐ 적용 순서 — FOV 를 먼저 고정한다

거리 · FOV · 화면 크기가 **한 방정식에 묶여 있어** 동시에 맞추면 수렴하지 않는다.

1. **FOV 를 63° 로 고정** (가장 근거가 단단하다)
2. **피치를 -44° 로 고정**
3. **거리만** 스크린샷과 비교하며 조정

⚠ 이 순서를 지키지 않으면 "거리를 줄였더니 FOV 를 넓힌 것과 같아 보이는" 상태에 빠진다.

# 파트 1-B — 카메라 Yaw (2026-09-09 추가)

## 근거

`비교군.png` 와 `테스트2.png` 의 **같은 도로**를 비교한 결과 (위 「초판 측정의 오류」 참조):

- 원작: 도로가 화면에서 **수평 기준 약 50°** 기울어 있고 평행선이 **수렴**한다
- Yaw 0: 도로가 **수평**이고 평행선이 **평행**하다

→ **Yaw ≈ -45°** 로 시작한다.

## ⭐ 찾아낸 과정 — 세 번 틀렸다

| 시도 | 화면에서 본 것 | 판정 |
|---|---|---|
| **0** | 도로가 **수평**. 원작은 대각선 | Yaw ≠ 0 |
| **-45** | 도로가 **좌상→우하**. 원작은 좌하→우상 | 부호 반대 |
| **+45** | 기울기는 맞는데 **장면 전체가 정반대** | 180° 부족 |
| **-135** | 기울기 유지 + 장면 방향 정상 | ⬜ 확인 대기 |

## ⚠⚠ 함정 — 기울기만 보면 180° 틀린 걸 못 잡는다

지면의 **선은 방향이 없다.** 그래서 `tan` 의 주기(180°)만큼 **같은 기울기**가 나온다:

```
tan(월드각 - Yaw - 180°) = tan(월드각 - Yaw)
```

⭐ `+45` 에서 도로 기울기가 원작과 맞았지만, **장면 전체가 180° 돌아 있었다.**
잔디·건물의 좌우 배치를 봐야 잡힌다.

⚠ **기울기 하나만 보고 "맞았다" 고 판단하면 안 된다.**
반드시 **장면의 배치**(어디에 무엇이 있는지)를 같이 본다.

> ⭐ 이건 사용자가 에디터 화면을 보고 잡았다 — *"완전 정반대여야 할 것 같은데 각도는 괜찮은데"*.
> 스크린샷의 선만 재던 나는 `+45` 에서 멈췄을 것이다.

## ⚠ 크기(135)는 아직 미확정이다

방향은 정해졌지만 **크기에는 근거가 없다.** 눈으로 그럴듯한 것뿐이다.

```
tan(화면각) = tan(월드각 - Yaw) × sin(피치)
```

미지수가 **Yaw 와 피치 둘**인데 식이 하나다.
→ **피치를 먼저 확정**해야 Yaw 크기가 계산으로 나온다.

값은 `Source/EternalReturn/Character/ERCharacterBase.h` 의 `CameraYaw` 상수 하나다.

## ⭐ 코드가 Yaw 변경을 견디게 만들어 뒀다

가장자리 스크롤이 처음에는 화면 방향을 **월드 축으로 하드코딩**했다
(*"화면 위쪽은 월드 +X"*). Yaw 가 0 이 아니면 **엉뚱한 방향으로 밀린다.**

→ `AERPlayerController::UpdateEdgeScroll` 이 **카메라 회전에서 축을 계산**하도록 고쳤다.

```cpp
const FRotator YawOnly(0.f, Yaw, 0.f);
const FVector GroundForward = FRotationMatrix(YawOnly).GetUnitAxis(EAxis::X);
const FVector GroundRight   = FRotationMatrix(YawOnly).GetUnitAxis(EAxis::Y);
```

⭐ 이제 `CameraYaw` 를 아무 값으로 바꿔도 스크롤 코드는 안 고쳐도 된다.

⚠ 이건 코드 주석에 *"카메라 Yaw 를 바꾸게 되면 이 대응도 같이 바꿔야 한다"* 고
경고를 남겨 뒀던 항목이 **실제로 발동한 사례**다. 경고로 남기는 대신 구조로 막았다.

# 파트 2 — 소유 주체

## 문제

캐릭터에 붙은 카메라는 **부활하면 사라진다.** 폰이 새로 생기기 때문이다.
잠금 여부 · 스크롤 위치 같은 **상태**를 어디에 둘 것인가.

## 방안 A — 캐릭터가 전부 소유 (현재 구조)

**장점** — 지금 구조 그대로다. F01 에서 만든 SpringArm + Camera 를 안 건드린다.

**단점**
- ⚠ **부활하면 잠금 상태 · 스크롤 위치가 초기화된다**
- ⚠ 사망 중 관전할 카메라가 없다

## 방안 B — PlayerController 가 전부 소유

컨트롤러에 SpringArm + Camera 를 붙이고 폰을 따라가게 한다.

**장점** — 부활 · 관전에 영향받지 않는다

**단점**
- ⚠ **F01 에서 만든 리그를 버리고 다시 만든다** (`CLAUDE.md` §3 — 망가지지 않은 것을 리팩터링하지 않는다)
- ⚠ 언리얼의 기본 카메라 흐름(`ViewTarget` = 폰)에서 벗어난다
- 컨트롤러는 액터라 위치 개념이 어색하다

## ⭐ 방안 C — 리그는 캐릭터, 상태는 컨트롤러 (채택)

```
AERCharacterBase   : SpringArm + Camera  (F01 그대로, 안 건드린다)
AERPlayerController: bCameraLocked, FreeCameraOffset  (상태만)
```

컨트롤러가 상태를 갖고, 캐릭터의 `SpringArm->TargetOffset` 에 반영한다.

**장점**

- ⭐ **F01 리그를 그대로 쓴다.** 다시 만들지 않는다
- ⭐ **상태가 부활에 살아남는다** — 컨트롤러는 폰과 수명이 다르다
- 언리얼 기본 흐름(`ViewTarget` = 폰)을 유지한다
- 카메라는 여전히 **로컬 전용**이다 (복제하지 않는다)

**단점**

- 상태와 리그가 두 클래스에 나뉜다 — 연결 지점을 주석으로 남겨야 한다
- ⚠ 폰이 없는 순간(사망 직후 ~ 부활 전)에는 반영할 곳이 없다.
  관전 카메라는 **F14 에서** 별도로 다룬다
