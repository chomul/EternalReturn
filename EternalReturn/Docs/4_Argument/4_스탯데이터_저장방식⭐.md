## ⭐ 결정 (2026-09-07)

| | |
|---|---|
| **결정할 것** | 실험체별 기본 스탯을 **데이터 테이블 한 개**에 두나, **실험체별 데이터 애셋**에 두나 |
| **결정** | ⭐ **실험체별 데이터 애셋** (`UERCharacterData : UPrimaryDataAsset`) |

| **언제** | F02-05 구현 직후, **에디터 애셋을 만들기 전** |

> ⚠ 이 문서는 **이미 구현한 것을 되돌린 기록**이다.
> F02-05 를 데이터 테이블로 먼저 구현했고, 애셋을 만들기 전에 사용자 지적으로 전환했다.
> 되돌린 이유와 비용을 아래 §5 에 적는다.

## 1. 무엇을 정하는 건가

실험체는 각자 다른 기본 스탯을 갖는다 (`MaxHP`, `AttackPower`, `Defense`, ... 31개).
이 값들이 **어떤 애셋 모양으로** 저장되는가.

⚠ **"어떻게 어트리뷰트에 넣는가"는 이 문서의 주제가 아니다.**
그건 [`3_어트리뷰트셋_구조⭐.md`](3_어트리뷰트셋_구조⭐.md) C 절에서 이미 정했다
(Instant GE + SetByCaller, GE 는 애셋 + C++ 검사기).
**이 문서는 그 GE 에 넣을 숫자가 어디서 오는가**만 다룬다.

## 2. 방안 1 — 데이터 테이블 하나

```
/Game/DataTable/DT_ERCharStat        (애셋 1개)
  RowName    MaxHP  AttackPower  Defense  ...
  Katya       1000        100        50
  Magnus      1200         90        70
  ... 실험체 80명 ...
```

```cpp
USTRUCT(BlueprintType)
struct FERCharStatRow : public FTableRowBase { ... 31개 필드 ... };

// 캐릭터가 행을 가리킨다
UPROPERTY(EditDefaultsOnly) FDataTableRowHandle StatRow;
```

**장점**

- ⭐ **밸런싱용 스프레드시트 뷰가 기본 제공된다.** 실험체 80명의 공격력을 한 화면에서 비교할 수 있다. MOBA 밸런싱에 크다
- ⭐ **CSV 임포트·익스포트가 된다.** 외부 스프레드시트에서 작업하고 되돌릴 수 있다
- 행 추가가 싸다. 새 실험체 = 행 하나
- 참조가 하나뿐이라 관리가 단순하다

**단점**

- ⚠ **애셋이 하나다.** 여러 명이 서로 다른 실험체를 만져도 **같은 바이너리 파일**을 고친다. `.uasset` 은 머지가 안 된다
- ⚠ **로드·언로드 단위가 아니다.** 행 하나만 불러올 수 없다
- ⚠ 행 구조체가 커지면 **전부 커진다** (§4 참고)
- 행 구조체 필드를 바꾸면 **모든 행**의 값이 영향을 받는다

## 3. 방안 2 — 실험체별 데이터 애셋 ⭐ 채택

```
/Game/Characters/Katya/DA_Katya       (애셋 1개)
/Game/Characters/Magnus/DA_Magnus     (애셋 1개)
... 실험체마다 하나 ...
```

```cpp
USTRUCT(BlueprintType)
struct FERCharStats { ... 31개 필드 ... };      // FTableRowBase 상속 없음

UCLASS(BlueprintType, Const)
class UERCharacterData : public UPrimaryDataAsset
{
    UPROPERTY(EditDefaultsOnly, Category = "스탯")
    FERCharStats BaseStats;
    // 나중에 메시·애님BP·어빌리티가 여기 붙는다
};

// 캐릭터가 애셋을 가리킨다
UPROPERTY(EditDefaultsOnly) TObjectPtr<UERCharacterData> CharacterData;
```

**장점**

- ⭐ **작업 단위가 파일 단위와 일치한다.** 기획자 둘이 서로 다른 실험체를 만져도 충돌하지 않는다
- ⭐ **`UPrimaryDataAsset` 이라 AssetManager 가 비동기 로드·언로드 단위로 다룰 수 있다**
- ⭐ **커져도 안전하다.** 메시·어빌리티가 붙어도 다른 실험체에 영향이 없다
- 실험체별 폴더에 관련 애셋을 모을 수 있다
- Lyra 선례가 있다 (§6)

**단점**

- ⚠ **일괄 비교 뷰가 기본 제공되지 않는다** → Property Matrix 로 대체 (§7)
- ⚠ **CSV 임포트가 안 된다.** 대량 입력이 필요하면 커맨드릿을 따로 만들어야 한다
- 새 실험체마다 애셋을 하나 만들어야 한다 (행 추가보다 무겁다)
- 애셋이 80개가 되면 콘텐츠 브라우저에서 폴더 정리가 필요하다

## 4. ⭐ 결정을 가른 것 — 로딩

사용자 논거:
*"캐릭터별 몬스터별 등 데이터 애셋으로 먼저 한번 만든 다음에 그걸 모아서 관리하는 형식이 좋지 않을까?
그래야지 만약 나중에 사용되지 않는 캐릭터가 존재한다면 그 캐릭터의 데이터 애셋은 로드 안 해도 되니까?"*

**이 논거가 결정적이다.** 아래는 실측이다.

> ⚠ **기록:** 이 문서의 초판은 위 논거를 *"지금 규모에서는 약하다"* 고 적었다. **잘못된 요약이었다.**
> 사용자는 **"캐릭터별로 들어가는 데이터"** 전체와 **"나중에"** 를 말했는데,
> 내가 그걸 **스탯 31개 float 로 좁혀놓고** 반박했다.
> 사용자 정정: *"저게 지금 스탯 데이터만 있어서 그렇게 느끼는 거라고 생각해.
> 메시 데이터 애님 몽타주 데이터 이펙트 등등 캐릭터별로 들어가는 데이터들을 더 넣게 된다면 충분히 영향이 있다."*
> 아래는 그 정정을 반영해 다시 쓴 것이다.

### 실측 — 이 프로젝트의 `Content/` 기준

측정 방법: `du -sh` / `find -printf "%s"` 로 **디스크 크기**를 쟀다 (2026-09-08).

`Content/Characters/Mannequins/` 에 캐릭터 **2인분**(Manny, Quinn)이 들어 있다.

| 구성 | 크기 |
|---|---|
| `Textures/` | **245 MB** |
| `Meshes/` | **105 MB** (`SKM_Quinn.uasset` 한 개가 **34.8 MB**) |
| `Rigs/` | 33 MB |
| `Animations/` | 6.8 MB (16개) |
| `Materials/` | 0.3 MB |
| **합계 (2인)** | **402 MB** |

→ **캐릭터 1인분 ≈ 200 MB.**
그리고 이건 **스킬 이펙트·몽타주·음성·아이콘이 하나도 없는 상태**다.

### 비교

| | 크기 | 비고 |
|---|---|---|
| `FERCharStats` (스탯 31개) | **124 B** | float 31개 |
| 캐릭터 1인분 애셋 | **약 200 MB** | 실측. 스킬 연출 제외 |

**약 160만 배 차이다.** 스탯은 이 판단에서 **반올림 오차**다.

실험체 80명이면 대략 **16 GB**. 전부 올릴 수 있는 양이 아니다.

⚠ **디스크 크기지 런타임 메모리가 아니다.** 텍스처는 스트리밍되고 메시는 LOD 가 있어
실제 상주량은 더 작다. 다만 **자릿수의 방향은 바뀌지 않는다.**

### 그래서 무엇이 중요한가

로드 여부를 실제로 가르는 건 **참조 종류**(하드/소프트)와 **로드 단위**다.

- 데이터 테이블은 **애셋 하나**라 로드·언로드 단위로 못 쪼갠다
- `UPrimaryDataAsset` 은 **AssetManager 가 다루는 단위**다. 안 쓰는 실험체는 애초에 올라오지 않는다
- 실험체별 애셋이면 **메시·몽타주·이펙트 참조가 그 애셋 안에** 모인다.
  참조를 소프트로 둘지 하드로 둘지도 **실험체 단위로** 정할 수 있다

⭐ 즉 사용자 논거는 **"지금 스탯이 작다"와 무관하게 성립한다.**
스탯은 이 애셋에 들어갈 것 중 가장 작은 조각일 뿐이고,
**구조를 정하는 기준은 가장 큰 조각**이어야 한다.

### 두 번째 이유 — 협업 시 한 파일은 병목이다

`.uasset` 은 바이너리라 **머지가 안 된다.**
데이터 테이블이 애셋 하나라는 건, 기획자 둘이 서로 다른 실험체를 만져도
**같은 파일을 놓고 다툰다**는 뜻이다.

⭐ 사용자가 GE 를 애셋으로 하자고 할 때 든 논거와 **똑같다**
(*"나중에 모델러나 기획자랑 작업했을 때"*). 그때 맞았으면 여기서도 맞다.

### ⚠ 교훈 — 규모를 볼 때는 "지금"이 아니라 "다 붙었을 때"

내가 틀린 지점이 정확히 이거다. **현재 필드만 보고 규모를 판단했다.**
데이터 구조를 정할 때는 **그 구조에 최종적으로 무엇이 들어오는지**를 먼저 세워야 한다.

## 5. ⚠ 되돌린 비용 — 무엇을 버렸나

**버린 코드는 없다.** 전환 비용이 작았던 이유를 기록해 둔다.

| 파일 | 무슨 일이 있었나 |
|---|---|
| `GAS/ERAttributeTypes.h` | `FTableRowBase` 상속을 떼고 이름을 `FERCharStatRow` → `FERCharStats` 로. **필드 31개는 그대로** |
| `Character/ERCharacterData.h` | **신규.** `UPrimaryDataAsset` + `FERCharStats BaseStats` |
| `Character/ERCharacterBase.h/.cpp` | `FDataTableRowHandle StatRow` → `TObjectPtr<UERCharacterData> CharacterData`. 행 조회 코드가 사라져 **오히려 짧아졌다** |
| `GAS/ERAttributeInit.h/.cpp` | 타입 이름만 교체. **로직 변경 없음** |
| `GE_ERInitStats` | **변경 없음** — 모디파이어 33줄은 그대로 |

⭐ **애셋을 아직 하나도 만들지 않았기 때문에 공짜였다.**
데이터 테이블을 먼저 만들었다면 구조체 이름을 못 바꾼다 (`CLAUDE.md` §3).

⚠ **교훈:** 애셋을 만들기 전이 마지막 무료 구간이다.
`Docs/3_EditorTasks/` 문서를 쓰는 시점이 **되돌릴 수 있는 마지막 순간**이다.

## 6. 근거 — Lyra

```cpp
// LyraPawnData.h:22-23
UCLASS(BlueprintType, Const, Meta = (DisplayName = "Lyra Pawn Data", ShortTooltip = "Data asset used to define a Pawn."))
class LYRAGAME_API ULyraPawnData : public UPrimaryDataAsset
```

- `UPrimaryDataAsset` 을 쓰는 파일이 **10개 이상** (`LyraPawnData`, `LyraAbilitySet`, `LyraExperienceDefinition`, `LyraGameData`, ...)
- ⭐ **스탯용 데이터 테이블이 하나도 없다** — `grep "public FTableRowBase" Source/` → **0건**
  (`Plugins/` 에 1건 있으나 업적 정의용이고 스탯이 아니다)

상세: [`../6_Lyra참조/02_어빌리티셋_부여.md`](../6_Lyra참조/02_어빌리티셋_부여.md)

⚠ **다만 Lyra 를 그대로 따르는 것이 근거는 아니다** (`CLAUDE.md` §11).
Lyra 는 캐릭터별 스탯 차이가 아예 없어서 이 문제를 겪지 않는다.
Lyra 가 데이터 애셋을 쓴 건 **폰 구성(메시·어빌리티) 때문**이고,
그 이유가 §4 에서 우리한테도 성립한다고 판단한 것이다.

## 7. 잃는 것을 어떻게 메우나

### 일괄 비교 → **Property Matrix**

콘텐츠 브라우저에서 애셋 여러 개를 선택 → 우클릭 → **Bulk Edit via Property Matrix**.
행=애셋, 열=프로퍼티인 표가 열리고 거기서 바로 편집된다.

근거:
- `Engine/Source/Editor/PropertyEditor/Public/DetailsViewArgs.h:83-84`
  — *"True if the Open Selection in Property Matrix button should be shown"*
- `Engine/Source/Editor/PropertyEditor/Public/PropertyEditorModule.h:431`
  — `GetCanUsePropertyMatrix()`

### CSV 왕복 → **지금은 포기한다**

데이터 테이블만큼 편하지 않다. 대량 임포트가 실제로 필요해지면
데이터 애셋에서 CSV 를 뽑는 커맨드릿을 만든다.

⚠ **지금 만들지 않는다** (`CLAUDE.md` §2 — 추측성 코드 금지).
필요해진 시점에 이 문서에 추가한다.

| 축 | 1. 데이터 테이블 | **2. 캐릭터별 데이터 애셋** |
