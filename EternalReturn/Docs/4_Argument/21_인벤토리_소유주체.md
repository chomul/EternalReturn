## 결정할 것

**인벤토리 컴포넌트(가방 + 장착 슬롯 + 장비 GE 핸들)를 Pawn 에 두나, PlayerState 에 두나.**
네트워크 역기획서 §2.3 이 "미결" 로 남겼고, 사망 시 드롭은 확인됐지만(§7.1) **부활 시 인벤토리 유지 여부가 (미확인)** 이라 Q1("죽으면 사라지나") 이 애매하다.

⚠ F08-03 이 F08-04 보다 먼저인데, 장착 상태와 GE 핸들을 둘 곳이 필요하다 → 여기서 정한다.

---

## 방안 A — Pawn (`AERCharacterBase`) 에 컴포넌트

- 장점: "죽으면 떨군다" 가 자연스럽다 (폰 파괴 = 인벤토리 소멸) · 릴리번시가 캐릭터를 따라간다
- 단점
  - ⚠ **부활 때 서버가 인벤토리를 명시적으로 복원**해야 한다 — 죽는 순간 어딘가(PlayerState)에 복사해 두고 새 폰에 되돌리는 코드. 결국 PlayerState 에 사본이 생긴다
  - ⚠ **장비 GE 는 PlayerState 의 ASC 에 걸린다.** 폰이 죽어도 ASC 는 살아 있으니 GE 핸들을 폰이 들고 있으면 폰 파괴와 함께 핸들만 사라지고 **GE 는 남는다** → 부활한 캐릭터가 장비 없이 장비 스탯을 갖는다. 폰 `EndPlay` 에서 전부 지워야 하고, 그 순서를 항상 지켜야 한다
  - 재접속 복원(§8)도 따로

## 방안 B — PlayerState 에 컴포넌트

- 장점
  - ⭐ **ASC 와 같은 곳** — 장비 GE 를 거는 ASC 와 핸들을 드는 컴포넌트의 수명이 같다. 폰이 몇 번 죽고 살아도 GE ↔ 핸들이 어긋날 수 없다
  - 부활 · 재접속에 인벤토리가 **그냥 있다.** "부활 시 유지" 가 확인되면 아무것도 안 하고, "초기화" 로 확인되면 부활 시점에 `Clear()` 한 줄 — **어느 쪽이 확인되든 대응이 한 줄**
  - "죽으면 떨군다" 는 폰 파괴가 아니라 **사망 이벤트에서 서버가 드롭 액터를 만드는 것**(§7.3)이라 어디에 있든 같은 코드
  - 프로젝트의 기존 판단 기준 §2.2 Q2 와 같은 답: "나만 알아야 하나" → PlayerState + `COND_OwnerOnly`
- 단점
  - ⚠ `APlayerState` 는 `bAlwaysRelevant` — 24명분이 전원에게 간다. **가방은 반드시 `COND_OwnerOnly`.** 장착 5칸은 작고 남도 봐야 하니 전원 복제
  - 릴리번시 컬링이 없다 — 가방이 OwnerOnly 면 실제 트래픽은 본인 1명분이라 문제 아님

## 비교표

| 축 | A Pawn | B PlayerState |
|---|---|---|
| 구현 난이도 | 중 (부활 복원 · EndPlay 정리) | ⭐ 낮음 |
| 확장성 (부활 규칙 미확인) | 유지면 복원 코드 · 초기화면 그대로 | 유지면 그대로 · 초기화면 Clear 한 줄 |
| 네트워크 | 릴리번시 컬링 | OwnerOnly 로 동등 |
| GAS 정합성 | ⚠ GE(ASC=PlayerState) 와 핸들(Pawn) 수명 불일치 | ⭐ 같은 액터 |
| 성능 | 무시 | 무시 |

## 추천 — **방안 B (PlayerState)**

결정적인 근거는 **ASC 가 이미 PlayerState 에 있다**는 것이다 (Argument 3). 장비 스탯은 그 ASC 의 Infinite GE 이고, 핸들은 GE 와 같은 수명을 가진 곳에 있어야 한다. Pawn 에 두면 "폰이 죽을 때 GE 를 반드시 정리" 라는 규칙이 하나 더 생기고, 어기면 증상이 "부활했는데 스탯이 이상하다" 로만 보인다 (F02-05 의 Instant/Infinite 함정과 같은 부류).

## 이번에 안 하는 것
- 부활 시 인벤토리 — ⭐ 사용자 확인 (2026-09-17): **전부 유지, 영웅 재료만 소멸.** 시체 드롭은 **복사**(영웅 장비 + 재료만, 전설·초월 장비 제외)라 원본 인벤토리를 건드리지 않는다 — PlayerState 배치가 정확히 이 규칙과 맞는다. F14 부활 경로에서 영웅 재료 칸만 비운다
- 가방 · 드롭 액터 · 습득 경쟁 — F08-04 · 05 (같은 컴포넌트에 붙는다)
