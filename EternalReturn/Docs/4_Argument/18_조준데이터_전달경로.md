# 18. 조준 데이터(마우스 위치)를 클라 → 서버로 어떻게 넘기는가

## 결정할 것

**클라가 누른 순간의 마우스 월드 좌표를 서버 어빌리티가 어떻게 받는가.** 전제: 우리는 `ServerInitiated` (예측 없음, 17번).

---

## 방안 A — 발동 요청에 실어 보낸다 (`FGameplayEventData.TargetData`)

```cpp
// 클라 ERPlayerController::OnSkillSlotPressed — 인스턴스에서 선판정(헛클릭 방지) 뒤
FGameplayAbilityTargetDataHandle Aim = 마우스 좌표를 FGameplayAbilityTargetData_LocationInfo 로
ServerActivateSkill(SlotTag, Aim);                       // PC 의 Server RPC (ServerSetDestination 과 같은 자리)

// 서버 ERPlayerController::ServerActivateSkill_Implementation
FGameplayEventData Payload; Payload.TargetData = Aim;
ASC->TriggerAbilityFromGameplayEvent(Spec.Handle, ActorInfo, ERTags::Event_Skill_Aim, &Payload, *ASC);
// -> 서버 ActivateAbility(..., TriggerEventData) 에 도착
// -> 클라 인스턴스에는 ClientActivateAbilitySucceedWithEventData 로 같은 데이터가 간다 (:1810-1812)
```

⚠ **엔진이 클라에서 이걸 직접 못 하게 막아 둔 두 곳** (조사 결과):
- `TriggerAbilityFromGameplayEvent` 는 클라에서 ServerInitiated 어빌리티를 **거부**한다 — `HasNetworkAuthorityToActivateTriggeredAbility` 가 권위만 허용 (`:2567-2579`)
- 이벤트 데이터를 싣는 RPC `ServerTryActivateAbilityWithEventData` 는 **protected** (`AbilitySystemComponent.h:1753`) 이고, 엔진이 이걸 부르는 곳은 **LocalPredicted 분기뿐**이다 (`:1855-1863`). ServerInitiated 의 클라 경로(`TryActivateAbility :1586-1591`)는 `CallServerTryActivateAbility` — 데이터 없음
→ 그래서 **PC 의 Server RPC 가 `FGameplayAbilityTargetDataHandle` 을 싣고**, 서버(권위)에서 `TriggerAbilityFromGameplayEvent` 를 부른다.
  RPC 는 PC 에 있지만 **그릇은 GAS 것**이다 — CLAUDE.md §8 "조준 데이터 = FGameplayAbilityTargetData" 를 지킨다. (ASC 를 서브클래스해서 protected RPC 를 여는 방법도 있으나 클래스 하나를 래퍼 하나 때문에 만드는 것이라 안 한다)

- 장점: **RPC 한 번**(발동 요청 = 조준). 서버 어빌리티가 시작할 때 이미 조준을 안다 → 대기 태스크 없음 · 클라 인스턴스도 같은 데이터를 받는다(연출) · `ServerSetDestination` 과 같은 "입력 → PC Server RPC" 패턴
- 단점: 조준을 **누른 순간**에 고정 — 선딜 중 마우스를 옮겨도 반영 안 됨 (원작 (미확인). 카티야 R 은 어차피 조준이 없다) · 클라 선판정을 PC 가 손으로 부른다 (`TryActivateAbility` 가 하던 것을 대신) — E10 의 스펙 순회에 한 줄 추가

## 방안 B — 서버 어빌리티가 기다리고, 클라가 따로 보낸다 (Lyra 방식)

```cpp
// 서버: AbilityTargetDataSetDelegate(Handle, Key).AddUObject(OnTargetDataReady)
// 클라: CallServerSetReplicatedTargetData(Handle, Key, Data, Tag, ScopedPredictionKey)
//        (LyraGameplayAbility_RangedWeapon.cpp:446-492)
```

- 장점: 선딜 끝에 다시 보내면 **선딜 종료 시점의 조준** 사용 가능 · Lyra 와 같은 API
- 단점: ⚠ Lyra 는 **LocalPredicted** 라 클라가 먼저 활성화되어 곧바로 보낸다. 우리는 ServerInitiated 라 **서버 → 클라 활성화 → 클라 전송 → 서버 수신** 왕복이 하나 더 생긴다 · 서버가 데이터를 **기다리는 동안** 어빌리티가 떠 있다(타임아웃 처리 필요) · 예측 키 없이 `AbilityTargetDataSetDelegate` 를 키로 매칭하는 것은 엔진이 상정한 용도 밖(`FPredictionKey()` 로 통일해야 함)

## 비교표

| 축 | A 발동에 실음 | B 별도 전송 |
|---|---|---|
| 구현 난이도 | ⭐ 낮음 (PC 10줄 + 서버 읽기) | 중 (대기 태스크 · 키 매칭 · 타임아웃) |
| 확장성 | 선딜 중 재조준 불가 (필요해지면 B 를 **추가**로 붙일 수 있다) | 재조준 가능 |
| 네트워크 | RPC 1 | RPC 2 + 왕복 1 |
| GAS 정합성 | 표준 (`ServerTryActivateAbilityWithEventData`) | 표준이나 LocalPredicted 전제 |
| 성능 | 무시 | 무시 |

## 추천 — **방안 A**

ServerInitiated 에서는 "발동 요청" 과 "조준" 이 같은 순간이다. 둘을 하나의 RPC 로 보내는 게 자연스럽고, 대기·타임아웃이 없다.
선딜 중 재조준이 원작에 있다고 확인되면 그때 B 를 **선딜 종료 시점에만** 덧붙인다 — A 를 걷어내지 않아도 된다.
