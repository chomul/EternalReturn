# A. 콜리전 채널

## A-1. 방안 1 — 기존 오브젝트 채널 재사용 (`OverlapMultiByObjectType`)

```cpp
FCollisionObjectQueryParams ObjParams;
ObjParams.AddObjectTypesToQuery(ECC_Pawn);
World->OverlapMultiByObjectType(Overlaps, Center, FQuat::Identity, ObjParams, Shape, Params);
```
`ECC_Pawn` 오브젝트 타입인 것만 긁는다. 채널을 새로 파지 않는다.

**장점**
- ⭐ **`.ini` 를 안 건드린다.** 설정 변경 보고도, 애셋 재설정도 없다
- 캐릭터가 이미 `Pawn` 프로파일이라 **아무것도 안 하고 바로 동작**한다
- 채널 18개를 아낀다

**단점**
- ⭐ **"판정에 걸리는가"를 액터별로 끌 수 없다.** 폰이면 무조건 걸린다 — 관전자·유령·연출용 더미를 나중에 제외하려면 코드에 예외 목록이 쌓인다
- 야생동물·설치물이 `Pawn` 이 아니면 **질의를 하나 더 돌려야** 한다 (F12 소환물·레니 발판 등)
- 벽 차폐 판정에는 어차피 별도 트레이스가 필요하다

**이 프로젝트 비용**
- 구현 난이도: **가장 낮음.** 지금 당장 코드만 쓰면 된다
- GAS 정합성: 무관
- F16 시야 영향: 없음 (시야는 자기 채널을 판다)

## A-2. 방안 2 — 커스텀 트레이스 채널 신설 (`OverlapMultiByChannel`)

`Config/DefaultEngine.ini` 에 채널 하나를 추가한다.

```ini
[/Script/Engine.CollisionProfile]
+DefaultChannelResponses=(Channel=ECC_GameTraceChannel1,DefaultResponse=ECR_Ignore,bTraceType=True,Name="SkillTarget")
```

```cpp
World->OverlapMultiByChannel(Overlaps, Center, FQuat::Identity,
    ECC_GameTraceChannel1 /*SkillTarget*/, Shape, Params);
```
각 액터가 이 채널에 **Block/Overlap/Ignore 로 응답**한다.

**장점**
- ⭐ **액터별로 "스킬에 맞는가"를 켜고 끌 수 있다.** 관전자·유령·연출 더미를 데이터로 제외한다 — 코드 예외가 안 쌓인다
- 캐릭터·야생동물·설치물·구조물을 **한 번의 질의**로 긁는다
- 판정 대상 집합이 **애셋 설정으로 보이므로** 디자이너가 확인 가능

**단점**
- ⭐ `.ini` 변경 → **`CLAUDE.md` §9 보고 대상**
- **모든 대상 액터의 콜리전 응답을 설정해야 한다.** 하나 빠뜨리면 그 액터만 조용히 안 맞는다 — ⚠ 디버깅이 어려운 종류의 버그다
- 에디터 작업이 늘어난다 (BP마다 응답 설정)
- 채널 1개 소모 (18 → 17)

**이 프로젝트 비용**
- 구현 난이도: 중간. 코드는 같고 **설정 작업**이 붙는다
- 에디터 작업: `BP_ERCharacterBase` + 이후 모든 대상 액터
- F16 시야 영향: 없음 (별도 채널)

## A-3. 방안 3 — 커스텀 **오브젝트** 채널 신설

대상 액터를 `SkillTargetable` 이라는 오브젝트 타입으로 바꾼다.

**장점**
- 질의가 명확하다 (`ObjectType == SkillTargetable`)

**단점**
- ⭐ **오브젝트 타입은 액터당 하나뿐이다.** 캐릭터를 `SkillTargetable` 로 바꾸면 **`Pawn` 이 아니게 된다** —
  `CharacterMovementComponent` 의 폰 회피, 네비게이션, 다른 폰과의 충돌이 전부 영향을 받는다
- 되돌리기 가장 비싸다

> ❌ **검토 대상에서 제외한다.** 이동 시스템을 건드리는 대가가 얻는 것보다 크다.

## A-5. 추천 — **A-2 (커스텀 트레이스 채널)**

**이유는 대상 종류가 많아지는 것이 이미 확정돼 있기 때문이다.**

판정에 걸려야 하는 것: 실험체 · 야생동물 · 보스 · 설치물(레니 발판, 카티야 드론, 시셀라 윌슨) · 구조물.
A-1 로 가면 이들이 `Pawn` 이 아닐 때마다 **질의를 하나씩 늘리거나 클래스 검사를 넣게 된다.**
그건 F04가 F12(야생동물)에 의존하게 만드는 길이고, 상향식 원칙을 깬다.

A-2 는 **초기 비용(설정 작업)을 한 번 치르고 그 문제를 없앤다.**

> ⚠ **A-2 의 위험을 그대로 인정한다.** 응답 설정을 빠뜨린 액터는 **조용히 안 맞는다.**
> 이걸 줄이기 위해 F04 에서 **판정 결과가 0인데 대상이 있어야 할 상황이면 경고 로그**를 남기도록 하겠다.
> 그래도 완전히 막지는 못한다 — 이건 A-2 를 고르는 대가다.

**A-1 을 고르는 것도 합리적이다.** *"지금은 캐릭터밖에 없으니 나중에 필요할 때 판다"* 는 `CLAUDE.md` §2(추측성 코드 금지)에 더 가깝다.
다만 **채널을 나중에 파면 그때 모든 액터의 응답을 설정해야 하는 것은 똑같고**, 그 사이에 쌓인 코드 예외를 걷어내는 작업이 추가된다.

# B. 판정 기준점

## B-0. 무엇을 정하는 건가

"카티야 Q 사거리 10m" 를 잴 때 **액터의 어느 점**부터 어느 점까지인가.

`ACharacter` 는 **캡슐이 루트**이므로(`Character.cpp:65`) `GetActorLocation()` 은 **캡슐 중심**을 준다 — 발밑이 아니다.
발밑은 `GetActorLocation() - FVector(0, 0, CapsuleHalfHeight)` 다 (`Character.cpp` `GetNavAgentLocation()` 구현이 정확히 이 식을 쓴다).

## B-1. 방안 1 — 캡슐 중심 (`GetActorLocation()`)

**장점**
- ⭐ **추가 계산이 없다.** `GetActorLocation()` 그대로
- 액터 종류를 안 가린다 — 야생동물·설치물·구조물 전부 동작
- 캡슐 높이가 달라도(곰 vs 닭) 코드가 안 바뀐다

**단점**
- ⭐ **키가 다르면 수평 거리가 같아도 3D 거리가 다르다.** 곰(큰 캡슐)과 닭(작은 캡슐)이 같은 자리에 있어도 중심 간 거리가 다르다
- 경사면에서 오차가 커진다

## B-2. 방안 2 — 발밑 (`GetNavAgentLocation()` 상당)

**장점**
- ⭐ **탑다운에서 직관과 일치한다.** 플레이어가 보는 것은 지면 위의 위치다
- 키 차이의 영향이 없다 — 곰이든 닭이든 발밑끼리 잰다
- 네비게이션·이동 시스템과 기준이 같다 (`GetNavAgentLocation`)

**단점**
- 캡슐이 없는 액터(설치물·구조물)는 **발밑을 따로 정의해야 한다**
- 매번 반높이를 빼는 계산이 붙는다 (무시할 수준)

## B-3. 방안 3 — 수평 거리만 (Z 무시)

중심이든 발밑이든 **Z를 아예 빼고** XY 평면에서만 잰다.

**장점**
- ⭐ **키·경사·기준점 문제가 통째로 사라진다.** 탑다운 MOBA 의 통례다
- 계산이 가장 단순하고 결과가 예측 가능하다

**단점**
- **높이차가 큰 지형에서 이상해진다.** 절벽 위아래가 "사거리 안"이 된다
- 이 맵에 그런 지형이 있는지 **(미확인)** — 루미아 섬에 높이차 있는 지역이 있으나 스킬 사거리에 영향을 줄 정도인지 확인 못 했다

## B-4. 비교표

| 평가축 | B-1 캡슐 중심 | B-2 발밑 | B-3 수평 거리 |
|---|---|---|---|
| **구현 난이도** | ⭕ 가장 낮음 | 🔺 캡슐 없는 액터 처리 필요 | ⭕ 낮음 |
| **키 차이 영향** | ❌ 있음 (곰 vs 닭) | ⭕ 없음 | ⭕ 없음 |
| **탑다운 직관** | 🔺 보통 | ⭕ 일치 | ⭕ 일치 |
| **높이차 지형** | ⭕ 반영됨 | ⭕ 반영됨 | ❌ 무시됨 |
| **이동 시스템과 기준 일치** | ❌ 다름 | ⭕ 같음 (`GetNavAgentLocation`) | 🔺 부분 |
| **확장성** (설치물·구조물) | ⭕ 그대로 | 🔺 발밑 정의 필요 | ⭕ 그대로 |

## B-5. 추천 — **B-2(발밑) + 수평 판정 기본**

**둘을 조합한다.** 배타적이지 않다.

```
기준점 = 발밑 (캡슐 있으면 GetActorLocation() - HalfHeight, 없으면 GetActorLocation())
거리   = 수평(XY) 거리 기본. FTargetQuery 에 bIgnoreZ 플래그를 두고 기본 true
```

이유:
- **발밑을 기준점으로 삼으면** 키 차이 문제가 사라지고 이동 시스템(`GetNavAgentLocation`)과 기준이 같아진다
- **수평 판정을 기본으로 두면** 탑다운 직관과 맞는다
- ⭐ **`bIgnoreZ` 를 플래그로 빼두면** 높이차 지형 문제가 실제로 생겼을 때 **스킬 단위로** 끌 수 있다. 지금 결정을 미룰 수 있는 형태다

캡슐이 없는 액터는 `GetActorLocation()` 을 그대로 쓴다 — **자체 결정값**이며 주석에 남긴다.
