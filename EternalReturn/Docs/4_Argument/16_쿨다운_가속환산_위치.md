# 16. 쿨다운 — 스킬 가속 환산을 어디서 하는가

| 항목 | 결정 |

## 결정할 것

**`최종 쿨다운 = 기본 × 100 / (100 + SkillHaste)` 를 어빌리티(C++)가 계산해서 넘기는가, GE 의 MMC 가 계산하는가.**

---

## 전제 — 논점이 아닌 것 (GAS 가 정해 둔 것)

### 쿨다운 GE 는 하나, 슬롯은 동적 태그

`CheckCooldown` 은 `GetCooldownTags()` 가 돌려준 태그를 ASC 가 **갖고 있는지**만 본다
(`GameplayAbility.cpp:940-963`). 그리고 기본 `GetCooldownTags()` 는 **GE 클래스의 GrantedTags** 를 돌려준다 (`:1076-1080`).

→ 스킬마다 GE 애셋을 따로 만들면 30개 GE 가 생긴다 ([`15`](15_스킬데이터_위치.md) 방안 B 의 "로직 : 데이터 = 1 : N" 위반).
→ 하나의 네이티브 GE 를 쓰면 GrantedTags 가 비어서 **`CheckCooldown` 이 항상 통과**한다 — 그대로는 안 된다.

**해법 (GASDocumentation 의 표준 패턴):** `UERGameplayAbility` 가 두 함수를 오버라이드한다.

```cpp
// GetCooldownTags: 이 슬롯의 쿨다운 태그를 돌려준다 (Cooldown.Slot.Q 등)
// ApplyCooldown:   스펙을 만들고 DynamicGrantedTags 에 같은 태그를 심어 적용한다
```

`FGameplayEffectSpec::DynamicGrantedTags` — *"Tags that are granted and that did not come from the UGameplayEffect def"* (`GameplayEffect.h:1180`). 적용되면 ASC 소유 태그가 된다.
슬롯 → 태그 매핑은 `ERTags` 에 `Cooldown.Slot.*` 6개를 선언하고 `ERSkill::CooldownTagForSlot()` 한 함수로 푼다. 문자열 조합 금지 (`CLAUDE.md` §8).

⚠ **P 슬롯 어빌리티 하나에 태그 하나** = 같은 ASC 에서 슬롯당 쿨다운 하나. 재키 R→학살(슬롯 변형)은 두 스펙이 R 쿨다운을 **공유**하게 되는데, 원작에서도 학살은 R 쿨 중에만 나오는 변형이라 맞다 (F07-04 에서 재확인).

### 쿨다운은 CommitAbility 시점에 걸린다

`CommitAbility → CommitExecute → ApplyCooldown` (`GameplayAbility.cpp:465` → `:557-561`). 취소돼도 GE 는 남는다 → "채널링 취소돼도 쿨 유지" 는 공짜.

## 방안 A — 어빌리티가 계산해서 SetByCaller 로 넘긴다

```cpp
void UERGameplayAbility::ApplyCooldown(...) const
{
	const UERSkillData* Data = GetSkillData();
	float Duration = Data->GetCooldown(GetAbilityLevel());
	if (!Data->bIgnoreCooldownReduction)
	{
		const float Haste = ASC->GetNumericAttribute(UERAttributeSet::GetSkillHasteAttribute());
		Duration = Duration * 100.f / (100.f + FMath::Max(Haste, 0.f));
	}
	Spec->DynamicGrantedTags.AddTag(CooldownTag);
	Spec->SetSetByCallerMagnitude(ERTags::SetByCaller_Cooldown, Duration);
	ApplyGameplayEffectSpecToOwner(...);
}
```

- 장점
  - 파일 2개(`ERCooldownEffect.h/.cpp`) + 오버라이드 2개. **가장 적은 코드**
  - `bIgnoreCooldownReduction` 이 `if` 한 줄
  - 환산식이 **한 곳**(어빌리티)에 있고 로그를 같이 남길 수 있다
  - 나중에 "재키 E 처치 시 초기화 · 아야 E 다른 슬롯 쿨감" 같은 **런타임 조작**도 같은 클래스에서 태그로 찾아 처리한다
- 단점
  - GE 만 보면 "SetByCaller 를 받는다" 만 있고 **어떻게 계산됐는지 안 보인다**
  - 어빌리티가 SkillHaste 어트리뷰트를 **직접 읽는다** — `ERGameplayAbility.h` 주석 "대상 스탯을 읽지 않는다" 는 **대상**(적) 얘기라 위반은 아니지만 경계가 흐려질 수 있다

## 방안 B — MMC 가 SkillHaste 를 캡처해서 계산한다 (F06-05 와 같은 꼴)

```cpp
// UERCooldownCalc : UGameplayModMagnitudeCalculation
//   Source SkillHaste 캡처, SetByCaller.Cooldown 읽어서 × 100/(100+Haste)
// UERCooldownEffect.DurationMagnitude = FCustomCalculationBasedFloat(UERCooldownCalc)
```

- 장점
  - [`14_저항_적용방식.md`](14_저항_적용방식.md) 와 **같은 구조** — "기본값은 SetByCaller, 스탯 반영은 MMC"
  - GE 가 자기 완결적: 어디서 적용하든 가속이 붙는다
- 단점
  - 파일 4개(GE + MMC). 방안 A 의 2배
  - ⚠ **`bIgnoreCooldownReduction` 을 MMC 가 알 방법이 없다.** 어빌리티가 SetByCaller 로 플래그를 하나 더 넘기거나(`SetByCaller.IgnoreHaste = 1`), GE 를 **두 클래스**로 나눠야 한다(가속 적용 / 미적용). 어느 쪽이든 방안 A 의 `if` 한 줄보다 무겁다
  - F06-05 가 MMC 였던 **이유**는 "저항이 **상대**(Target) ASC 에 있어서 어빌리티가 직접 못 읽는다" 였다 (`14` §추천). 여기선 SkillHaste 가 **자기** ASC 에 있다 — 그 이유가 성립하지 않는다
  - "GE 가 자기 완결적" 의 이득은 **쿨다운 GE 를 어빌리티 밖에서 적용할 때**만 생기는데, 그런 곳이 없다

## 비교표

| 축 | A 어빌리티 계산 | B MMC |
|---|---|---|
| 구현 난이도 | ⭐ 낮음 (2파일 + 오버라이드 2개) | 중 (4파일 + 플래그 전달 문제) |
| 확장성 (런타임 쿨 조작) | 어빌리티가 태그로 GE 를 찾아 조작 — **같은 곳** | 같음 (MMC 는 적용 시 1회라 조작과 무관) |
| 네트워크 | 동일 — 서버가 Duration 확정, 활성 GE 가 복제 | 동일 |
| GAS 정합성 | Cooldown GE + SetByCaller — 표준 (GASDocumentation §4.7) | MMC 도 표준. 다만 플래그 우회가 비표준 |
| 성능 | 무시 | 무시 |
| `bIgnoreCooldownReduction` | `if` 1줄 | ⚠ 플래그 SetByCaller 또는 GE 2종 |

## 추천 — **방안 A**

**B 의 유일한 근거("F06-05 와 같은 꼴")가 여기서 성립하지 않는다.** 14번이 MMC 였던 이유는 저항이 상대 ASC 에 있기 때문이고, 가속은 내 ASC 에 있다. 이유가 다르면 답도 달라도 된다 (`CLAUDE.md` §11 — "Lyra 가 그렇게 했으니까" 는 근거가 아니다 — 같은 원칙).
그리고 `bIgnoreCooldownReduction` 이 A 에서는 `if` 한 줄인데 B 에서는 구조를 흔든다.

⚠ A 의 단점("GE 만 보면 계산이 안 보인다")은 `UERCooldownEffect` 클래스 주석에 **"길이는 UERGameplayAbility::ApplyCooldown 이 계산한다"** 한 줄로 막는다.
