# E. 캐릭터 고유 리소스 — 이 문서의 핵심

## E-0. 무엇을 정하는 건가

에키온의 **VF 의수 게이지**처럼 **한 캐릭터만 쓰는 리소스**가 있다.
90명까지 늘어나면 이런 게 수십 개가 된다. 어디에 둘 것인가.

## E-1. 방안 1 — 공통 세트 하나에 전부 넣는다

```cpp
class UERAttributeSet : public UAttributeSet
{
    FGameplayAttributeData Health, MaxHealth, AttackPower, ... ;
    FGameplayAttributeData VFGauge;        // 에키온만 씀
    FGameplayAttributeData SomeOtherThing; // 다른 캐릭터만 씀
};
```

**장점**
- ASC에 세트가 하나뿐이라 조회가 단순하다
- GE가 어떤 캐릭터에게 적용되든 어트리뷰트가 항상 존재한다

**단점**
- ⭐ **모든 액터가 안 쓰는 필드를 들고 다닌다.** 닭도 곰도 VF 게이지를 갖는다
- 90명이면 고유 리소스 필드가 수십 개 쌓인다
- 복제 대상이 늘어난다 — 24명 매치에서 낭비

## E-2. 방안 2 — 상속

```cpp
class UERAttributeSet      : public UAttributeSet { /* 공통 */ };
class UERAttributeSet_Aya  : public UERAttributeSet { FGameplayAttributeData VFGauge; };
```

**장점**
- 공통 어트리뷰트를 물려받으므로 중복 선언이 없다
- 캐릭터별로 클래스가 분명하다

**단점 — ⚠ 엔진 동작 때문에 위험하다**

ASC의 세트 조회가 **`IsA()`** 다.

```cpp
// Engine/Plugins/Runtime/GameplayAbilities/Source/GameplayAbilities/Private/AbilitySystemComponent.cpp
const UAttributeSet* UAbilitySystemComponent::GetAttributeSubobject(const TSubclassOf<UAttributeSet> AttributeClass) const
{
    for (const UAttributeSet* Set : GetSpawnedAttributes())
    {
        if (Set && Set->IsA(AttributeClass))   // ← 정확 매칭이 아니다
        {
            return Set;
        }
    }
    return nullptr;
}
```

- 부모(`UERAttributeSet`)를 요청하면 **자식(`_Aya`)도 매칭된다**
- 부모와 자식을 **둘 다 등록하면 배열 순서에 따라 아무거나 반환**된다
- ⚠ 컴파일도 되고 에러도 없다. **조용히 틀린 세트를 쓴다**

즉 "같은 계층에서 정확히 하나만 등록한다"는 규칙을 **사람이 지켜야** 한다.
캐릭터가 90명이 되면 언젠가 깨진다.

## E-3. 방안 3 — 별도 세트를 병렬로 추가 ⭐

```cpp
class UERAttributeSet   : public UAttributeSet { /* 공통 30개 */ };
class UERVFAttributeSet : public UAttributeSet { FGameplayAttributeData VFGauge; };
//                               ^^^^^^^^^^^^ 공통 세트를 상속하지 않는다 — 계층이 다르다
```

에키온의 ASC에만 두 세트를 등록한다. 다른 캐릭터는 공통 세트만 갖는다.

**엔진이 원래 이걸 전제로 만들어져 있다.**

```cpp
// AbilitySystemComponent.h
const TArray<UAttributeSet*>& GetSpawnedAttributes() const;   // :210
void AddSpawnedAttribute(UAttributeSet* Attribute);           // :213
```

**장점**
- ⭐ **안 쓰는 캐릭터에겐 그 어트리뷰트가 아예 존재하지 않는다.** 복제 비용 0
- 계층이 다르므로 **`IsA()` 모호성이 없다**
- 고유 리소스를 쓰는 캐릭터가 늘어도 **그 세트만 추가**하면 된다
- GE는 어트리뷰트 단위로 참조하므로 세트가 나뉘어도 문제없다

**단점**
- 공통 어트리뷰트를 물려받지 않으므로, 고유 세트에서 공통 값을 쓰려면 **ASC를 통해 따로 조회**해야 한다
- 세트 클래스 수가 늘어난다 (다만 **고유 리소스를 쓰는 캐릭터만큼**이고, 캐릭터 수만큼은 아니다)

## E-4. 비교표

| 평가축 | E-1 전부 공통 | E-2 상속 | E-3 병렬 추가 |
|---|---|---|---|
| **구현 난이도** | ⭕ 가장 낮음 | 🔺 중간 | 🔺 중간 |
| **확장성** (90 캐릭터) | ❌ 필드가 무한 증식 | 🔺 클래스가 캐릭터 수만큼 | ⭕ 고유 리소스 수만큼만 |
| **복제 비용** | ❌ 전원이 안 쓰는 필드를 소유 | ⭕ 필요한 것만 | ⭕ 필요한 것만 |
| **조회 안전성** | ⭕ 모호성 없음 | ❌ **`IsA()` 로 조용히 틀릴 수 있음** | ⭕ 계층이 달라 모호성 없음 |
| **엔진 설계 의도와 일치** | 🔺 가능하지만 의도는 아님 | ❌ 권장되지 않음 | ⭕ `SpawnedAttributes` 가 이걸 위한 것 |

## E-5. 결정 — **E-3 (병렬 추가)**

사용자 판단: *"상속보다는 어차피 여러 개 가질 수 있으니 공통 부분 한 개, 특이 쪽은 별도로 해서 넣는 방식"*

⚠ **지금 고유 세트를 만들지는 않는다.** 에키온은 선행 구현 6인에 없고 VF 수치도 전부 **(미확인)** 이다.
F02 에서는 **공통 세트만** 만들고, 구조가 병렬 추가를 전제한다는 것을 주석으로 남긴다.
실제 고유 세트는 그 캐릭터를 만들 때 붙인다 (`CLAUDE.md` §2 — 추측성 코드 금지).

### ⭐ 미확인이었던 것 — 확인 완료 (2026-09-07)

*"고유 세트가 **없는** 캐릭터에게 그 세트를 건드리는 GE를 적용하면 어떻게 되나?"*

→ **경고 없이 조용히 건너뛴다.**

```cpp
// GameplayEffect.cpp:4238
// skip over any modifiers for attributes that we don't have
if (!Owner || Owner->HasAttributeSetForAttribute(ModInfo.Attribute) == false)
{
    continue;
}
```

같은 가드가 `GameplayEffect.cpp:3404` 에도 있다.

⚠ **이건 양날이다.** 크래시가 안 나는 건 좋지만 **로그도 안 남는다.**
세트를 등록하는 걸 빠뜨리면 "GE는 걸렸는데 값만 안 변하는" 증상이 되고, 원인을 찾기 어렵다.
고유 세트를 붙일 때 **등록 여부를 로그로 확인**하는 절차를 EditorTasks 에 넣는다.

## E-6. 야생동물도 같은 33개를 써야 하나 — **쓴다 (현행 유지)**

사용자 질문 (2026-09-07): *"몬스터 같은 경우 실제로 다른 수치를 안 가지고 있는 것들도 많은데
그냥 통일하는 게 좋은 거야? 메모리 낭비는 아닐까?"*

### 실제 비용 — 재보면

| 항목 | 값 |
|---|---|
| `FGameplayAttributeData` | **8 B** (`BaseValue` + `CurrentValue`, float 2개) |
| 33개 | 264 B |
| + `UObject` 오버헤드 | 약 **320~360 B / 액터** |
| 야생동물 200마리 | 약 **64 KB** |

**메모리는 판단 근거가 못 된다.** 64KB 는 무시 가능한 양이다.

### 진짜 비용은 복제다 — 그런데 이미 막혀 있다

어트리뷰트 33개 = **복제 프로퍼티 33개**. 200마리면 비교 대상이 6,600개다.

그런데 [`../0_GameDesign/Systems/몬스터_야생동물_역기획서.md`](../0_GameDesign/Systems/몬스터_야생동물_역기획서.md) 가
**비전투 야생동물을 `DORM_DormantAll` 로 재우기로** 이미 정해 뒀다.
**잠든 액터는 복제를 아예 하지 않는다.** 어그로가 걸린 소수만 깨어난다.

### ⚠ 그런데도 지금 정해야 했던 이유

`FGameplayAttribute` 는 **소유 클래스 + 프로퍼티**로 식별된다.
어트리뷰트를 다른 세트로 옮기면 **그걸 참조하는 GE 애셋이 전부 끊긴다.**
→ **쪼갤 거면 GE 애셋을 만들기 전인 지금이 가장 싸다.** 그래서 F02 도중에 물었다.

### 검토한 대안 — Core / Combat 분리

`UERCoreAttributeSet`(HP·공격력·방어력·이속 등 ~12개) + `UERCombatAttributeSet`(치명타·증폭·관통·흡혈 등 ~21개).
야생동물은 Core 만 등록한다.

| | 장점 | 단점 |
|---|---|---|
| **1. 현행 (공통 33개)** | 데미지 Execution 의 캡처가 **항상 성립**한다 · 코드가 하나 · 경계 고민 없음 | 야생동물이 안 쓰는 프로퍼티를 들고 있다 |
| **2. Core / Combat 분리** | 야생동물 복제 프로퍼티가 준다 | ⭐ **캡처 실패가 조용하다**(아래) · 경계를 **추측으로** 그어야 한다 · 나중에 되돌리면 GE 애셋이 깨진다 |

⭐ **2번의 결정적 위험:**

```cpp
// GameplayEffect.cpp:2214
bool FGameplayEffectAttributeCaptureSpec::AttemptCalculateAttributeMagnitude(...) const
{
    FAggregator* Agg = AttributeAggregator.Get();
    if (Agg) { OutMagnitude = Agg->Evaluate(InEvalParams); return true; }
    return false;   // <- 대상에 그 어트리뷰트가 없으면 false
}
```

데미지 Execution(F03)이 Target 에서 `DamageDown` · `MaxHP` 등을 캡처한다.
대상에 없으면 **`false` 를 반환할 뿐 로그가 없다.** 호출자가 반환값을 무시하면 초기값이 그대로 쓰인다.

### 결정 — **1번 (현행 유지)**

사용자 판단: *"일단 지금 그대로 진행해보자"*

근거:

1. 메모리는 실측상 무시 가능(64KB)
2. 복제는 **도먼시로 이미 막았다** — 몬스터 역기획서의 기존 결정
3. ⭐ **야생동물이 실제로 뭘 쓰는지는 F12 를 만들어 봐야 안다.** 지금 쪼개면 경계를 추측으로 긋게 된다
   (`CLAUDE.md` §2 — 추측성 코드 금지)

⚠ **재검토 조건:** F12(야생동물) 구현 후 **프로파일링으로 복제 비용이 실제로 문제**로 나오면 다시 본다.
그때는 GE 애셋이 이미 있으므로 **분리 비용이 지금보다 비싸다**는 것을 감안한다.

# C. 초기값 주입 방식

## C-1. 엔진 내장 경로 — ❌ 쓸 수 없다

`UAttributeSet::InitFromMetaDataTable(const UDataTable*)` (`AttributeSet.h:238`) 이 있고
행 구조체 `FAttributeMetaData`(`:268`)에 `BaseValue / MinValue / MaxValue` 가 이미 들어 있다.
언뜻 딱 맞아 보인다.

**그런데 행 이름이 고정이다.**

```cpp
// AttributeSet.cpp — UAttributeSet::InitFromMetaDataTable
FString RowNameStr = FString::Printf(TEXT("%s.%s"),
    *Property->GetOwnerVariant().GetName(), *Property->GetName());
//  -> "ERAttributeSet.MaxHealth"
FAttributeMetaData* MetaData = DataTable->FindRow<FAttributeMetaData>(FName(*RowNameStr), Context, false);
```

행 이름이 **어트리뷰트 이름**이다. 즉 테이블 하나에 `ERAttributeSet.MaxHealth` 행이 **딱 하나**뿐이다.
**카티야용 값과 매그너스용 값을 같이 둘 수 없다.**

실험체별로 다르게 하려면 **실험체마다 테이블을 따로** 만들어야 한다(6개 → 90개).
게다가 `SetBaseValue` 를 직접 호출하므로 **클램프(`PreAttributeChange`)와 `PostGameplayEffectExecute` 를 우회**한다.

## C-2. Instant `UGameplayEffect` + SetByCaller ⭐ 채택

실험체 이름을 행 이름으로 하는 데이터 테이블(`FCharStatRow`)을 하나 두고,
읽은 값을 GE Spec의 SetByCaller로 넘겨 적용한다.

**장점**
- 실험체별 값이 **테이블 하나**에 모인다 (`CLAUDE.md` §0의 `F~Row` 규약과도 맞는다)
- ⭐ **GE 경로를 타므로 클램프가 확실히 걸린다**
- 레벨 성장(F10)도 같은 방식으로 Base 를 올리게 되어 **경로가 하나로 유지**된다

**단점**
- 초기화용 GE 애셋을 만들어야 한다 (에디터 작업)
- 어트리뷰트가 30개면 SetByCaller 태그도 30개다


## C-3. GE 를 **애셋으로 만드나, C++ 클래스로 만드나** — 결정 필요

C-2 에서 "Instant GE + SetByCaller" 까지는 정했다. 남은 갈림길은 **그 GE 를 어디에 두느냐**다.

어느 쪽이든 GE 는 **어트리뷰트 33개짜리 모디파이어 목록**을 들고 있어야 한다.

⚠ **모디파이어 33개, 표 컬럼 31개다.** `HP`/`VP` 도 GE 가 세팅하지만(모디파이어 O)
그 값은 표에서 오지 않고 `MaxHP`/`MaxVP` 에서 온다(컬럼 X) — C-4 참고.

### 방안 1 — 에디터에서 `GE_ERInitStats` 블루프린트로 만든다

```
Content/GAS/GE_ERInitStats  (부모: GameplayEffect)
  Duration Policy = Instant
  Modifiers[0] : MaxHP        Override  SetByCaller "MaxHP"
  Modifiers[1] : HP           Override  SetByCaller "MaxHP"
  ... 33줄을 손으로 ...
```

- **장점**
  - 애셋이라 디자이너가 열어 볼 수 있다
  - GAS 의 일반적인 사용 방식이다
- **단점**
  - ⭐ **33줄을 손으로 만들어야 한다.** 에디터 작업이 길고 오타가 난다
  - ⭐ **어트리뷰트를 하나 추가할 때마다 애셋을 손으로 고쳐야 한다.**
    빠뜨리면 그 스탯만 조용히 0 이 된다 (`GameplayEffect.cpp:4238` — 없는 건 경고 없이 건너뛴다)
  - ⭐ **순서가 애셋 안에 있다.** `MaxHP` 가 `HP` 보다 뒤로 밀리면 체력이 0 으로 클램프된다.
    코드 리뷰로 못 잡는다
  - 애셋이라 diff 가 안 된다

### 방안 2 — C++ 네이티브 GE 클래스 ⭐

```cpp
// 스탯 목록을 한 곳에 둔다. 순서가 곧 적용 순서다.
#define ER_INIT_STAT_LIST(X)     X(MaxHP) X(MaxVP)          /* ⭐ 최대치가 먼저다 */     X(HP)    X(VP)             /* 최대치로 채운다 */     X(HPRegen) X(VPRegen) X(AttackPower) X(Defense) ...

UERInitStatsEffect::UERInitStatsEffect()
{
    DurationPolicy = EGameplayEffectDurationType::Instant;
#define X(Name) AddOverrideMod(UERAttributeSet::Get##Name##Attribute(), TEXT(#Name));
    ER_INIT_STAT_LIST(X)
#undef X
}
```

- **장점**
  - ⭐ **목록이 하나뿐이다.** 모디파이어 정의와 런타임 `SetSetByCallerMagnitude` 가
    **같은 매크로 목록**에서 나오므로 **둘이 어긋날 수 없다**
  - ⭐ **적용 순서가 코드에 보인다.** `MaxHP` 가 `HP` 앞이라는 게 한눈에 읽힌다
  - 어트리뷰트 추가 = 목록에 한 줄. 에디터 작업 0
  - 텍스트라 diff 가 된다
  - `ERAttributeSet.cpp` 가 이미 같은 기법(`ER_REP` / `ER_ONREP`)을 쓰고 있다 — 스타일이 일관된다
- **단점**
  - 디자이너가 GE 를 못 본다 (⚠ 다만 **디자이너가 만질 값은 GE 가 아니라 데이터 테이블**에 있다)
  - C++ 빌드를 해야 바뀐다

### ⚠ 어느 쪽이든 행 구조체는 손으로 쓴다

`FERCharStatRow` 의 `UPROPERTY` 필드 31개(모디파이어 33개에서 `HP`/`VP` 제외)는 **매크로로 만들 수 없다.**
UnrealHeaderTool 은 헤더를 텍스트로 파싱하고 **사용자 매크로를 펼치지 않는다** —
매크로로 만든 `UPROPERTY` 는 리플렉션에 등록되지 않아 데이터 테이블에 컬럼이 안 생긴다.
그래서 **행 구조체만은 31줄을 그대로 쓴다.**

## C-4. `HP` / `VP` 는 표의 컬럼으로 두지 않는다

시작 체력은 **항상 최대치**다. 표에 `HP` 컬럼을 따로 두면
`MaxHP` 와 어긋난 값이 들어갈 수 있고, 그게 밸런스 버그로 보인다.

→ 표는 `MaxHP` 만 갖고, GE 가 `HP` 를 **`MaxHP` 값으로** 채운다
(런타임에 `SetByCaller("MaxHP")` 하나를 `HP` 모디파이어도 같이 쓴다).

⚠ **부활 시 절반만 채우는 식**이 필요하면 그건 F14 에서 별도 GE 로 한다. **(미확인)**

### ⭐ 순서 근거

`Instant` GE 의 모디파이어는 **배열 순서대로** 즉시 적용된다.

```cpp
// GameplayEffect.cpp:3004  FActiveGameplayEffectsContainer::ExecuteActiveEffectsFrom
for (int32 ModIdx = 0; ModIdx < SpecToUse.Modifiers.Num(); ++ModIdx)
{
    ...
    ModifierSuccessfullyExecuted |= InternalExecuteMod(SpecToUse, EvalData);
}
```

그래서 `MaxHP` 를 `HP` 보다 **앞에** 두면 `HP` 클램프(`FMath::Clamp(NewValue, 0.f, GetMaxHP())`)가
이미 갱신된 `MaxHP` 를 본다. 뒤집으면 **체력이 0 으로 잘린다.**



## C-5. ⭐ 재검토 — 사용자 지적: *"나중에 기획자랑 작업하면 데이터 애셋이 낫지 않나"*

**맞는 지적이다.** C-3 의 추천(네이티브)을 그대로 두지 않고 다시 본다.

### 내 원래 논거가 약한 곳

C-3 에서 *"디자이너가 만질 값은 데이터 테이블에 있으니 GE 는 코드에 둬도 된다"* 고 했다.
**이 GE 하나에 대해서는 지금도 맞다** — 초기화 GE 에는 조정할 숫자가 하나도 없다.
값은 전부 `SetByCaller` 구멍이고 실제 숫자는 데이터 테이블에서 온다.

⚠ **그런데 이건 이 GE 에만 해당된다.** 앞으로 만들 GE 대부분은 정반대다:

| GE | 성격 | 어디에 |
|---|---|---|
| 초기 스탯 세팅 (F02-05) | 값이 **없다**. 어트리뷰트 목록의 거울 | 논의 중 |
| 스킬 피해·계수 | 기획자가 **계속 만진다** | **반드시 애셋** |
| 쿨다운 · 코스트 | 기획자가 **계속 만진다** | **반드시 애셋** |
| CC 지속시간 · 둔화율 | 기획자가 **계속 만진다** | **반드시 애셋** |
| 장비 옵션 | 기획자가 **계속 만진다** | **반드시 애셋** |

**팀이 커지면 애셋이 기본이어야 한다.** 여기에 이견 없다.

그리고 논거가 하나 더 있다 — **일관성.** 프로젝트 규칙이 "GE 는 애셋"인데
초기화 GE 하나만 C++ 이면, 새로 온 사람이 그 예외를 배워야 한다.
예외는 그 자체로 비용이다.

### 그래도 남는 문제 — 조용한 어긋남

애셋으로 가면 **33줄짜리 목록이 애셋과 코드 두 곳에** 있게 된다.
(코드 쪽은 `SetSetByCallerMagnitude` 를 부르는 부분이다. 이건 없앨 수 없다.)

둘이 어긋나도 **경고가 없다:**

```cpp
// GameplayEffect.cpp:4238
// skip over any modifiers for attributes that we don't have
if (!Owner || Owner->HasAttributeSetForAttribute(ModInfo.Attribute) == false) { continue; }
```

애셋에서 모디파이어 한 줄이 빠지면 **그 스탯만 0 으로 시작하고 아무 로그도 안 남는다.**
순서가 뒤집혀도 마찬가지다 (`MaxHP` 가 `HP` 뒤로 가면 체력이 0 으로 잘린다).

## C-6. 방안 3 — **애셋으로 만들고, C++ 이 검사한다** ⭐ 새 추천

두 요구를 다 만족시킨다. 기획자가 애셋을 소유하고, 어긋남은 시끄럽게 잡힌다.

```cpp
// GE 를 적용하기 직전, 애셋이 기대한 모양인지 검사한다.
#if !UE_BUILD_SHIPPING
static void ValidateInitStatsEffect(const UGameplayEffect* GE)
{
    // 코드가 아는 정답 목록. 순서까지 포함한다.
    static const TArray<FName> Expected = { TEXT("MaxHP"), TEXT("MaxVP"), TEXT("HP"), ... };

    if (GE->Modifiers.Num() != Expected.Num())
    {
        UE_LOG(LogER, Error, TEXT("GE_ERInitStats 모디파이어 %d개. %d개여야 한다."),
            GE->Modifiers.Num(), Expected.Num());
    }
    // 어트리뷰트 이름 · 순서 · SetByCaller 키를 한 줄씩 대조하고
    // 틀린 줄마다 인덱스와 이름을 찍는다.
}
#endif
```

| | |
|---|---|
| **장점** | 기획자·모델러가 애셋을 연다 (사용자 요구) · GE 는 전부 애셋이라 **예외가 없다** · 어긋나면 **인덱스와 이름을 찍고 시끄럽게 실패**한다 · 애셋 diff 문제는 검사기가 대신 잡는다 |
| **단점** | 정답 목록이 코드에 하나 더 생긴다 (⚠ 다만 이건 `SetByCaller` 호출부와 **같은 목록**이라 실질 추가가 아니다) · 에디터에서 33줄을 한 번은 만들어야 한다 |

⚠ **검사 시점:** 스폰마다 도는 건 낭비가 아니다 — 캐릭터 하나당 한 번, 33줄 비교다.
`!UE_BUILD_SHIPPING` 으로 감싸 배포 빌드에서는 빠진다.

### 비교표 (최종)

| 축 | 1. 애셋 | 2. 네이티브 | **3. 애셋 + 검사** |
|---|---|---|---|
| 기획자 접근 | ✅ | ❌ | ✅ |
| 다른 GE 와 일관성 | ✅ | ❌ 예외 | ✅ |
| 어긋남 검출 | ❌ **조용함** | ✅ 불가능 | ✅ **시끄럽게** |
| 순서 실수 | ❌ 조용함 | ✅ 코드에 보임 | ✅ 검사가 잡음 |

| 어트리뷰트 추가 | 애셋 수정 (누락 시 조용함) | 목록 한 줄 | 애셋 + 목록 (누락 시 **로그**) |

### ⭐ 결정 — **방안 3 (애셋 + C++ 검사기)** · 확정 2026-09-07

사용자 판단: *"3번으로 가자"*

C-3 의 추천(방안 2 네이티브)은 **철회한다.**

**결정 이유** — 사용자 지적: *"나중에 모델러나 기획자랑 작업했을 때는 데이터 애셋으로 관리하는 게 더 좋지 않니?"*

   그것들이 애셋인데 초기화 GE 만 C++ 이면 **예외를 하나 만드는 것**이고, 예외는 그 자체로 비용이다

   **검사기가 없앤다.** 로그로 시끄럽게 잡히면 애셋이어도 안전하다

# D. 체력 하한 — 어트리뷰트에 두지 않는다 ⭐

## D-0. 시셀라의 두 가지는 서로 다르다

⚠ 처음에 이 둘을 섞어서 이해했다. 정정한다.

| | 무엇 | 하한 | 경로 |
|---|---|---|---|
| **Q · W** | HP를 **코스트로 소모** (Q 40 고정 / W 50~90) | **1** | Cost |
| **R** | 자기 자신에게 **피해** | **100** | Damage |

**코스트와 피해는 다른 경로이고 하한값도 다르다.** 하나의 규칙으로 묶으면 안 된다.

## D-1. 왜 어트리뷰트에 두면 안 되는가

`UERAttributeSet` 에 "체력 하한" 필드를 두거나 데미지 파이프라인에 하한 파라미터를 흘리면:

- **모든 피해 경로가 하한 값을 들고 다녀야 한다**
- ⭐ **실수로 하한이 남아 있으면 죽어야 할 때 안 죽는다** — 이게 훨씬 위험한 버그다
- 하한이 필요한 스킬은 6인 중 **하나뿐**인데 전체 경로가 그 비용을 진다

사용자 판단: *"체력 하한을 여기서 두면 안 된다고 생각함. 잘못하면 코드 꼬임. 죽긴 죽어야 함."*

## D-2. 대신 어떻게 하는가

**어트리뷰트는 `0` 하한만 안다.** 하한이 필요한 쪽이 **미리 깎아서 넘긴다.**

```
시셀라 Q/W (코스트) : 실제 소모 = min(코스트,  현재HP - 1)
시셀라 R  (자기 피해): 실제 피해 = min(계산된 피해, max(0, 현재HP - 100))
```

규칙이 하나로 통일된다 — **하한을 아는 쪽이 클램프한다.**
데미지 Execution 과 AttributeSet 은 하한이라는 개념 자체를 모른다.

⚠ **원작이 실제로 이렇게 동작하는지는 확인하지 못했다 (미확인).**
"하한 1 / 하한 100" 이라는 값만 역기획서에 있고, 코스트가 부족할 때 발동이 막히는지
1까지 깎이며 발동되는지는 인게임 계측이 필요하다.
