# 6. 흡혈을 어디서 적용할 것인가

> 작성일 2026-09-08 · 대상 기능 [`../1_Task/F03_데미지_ExecutionCalc/05_흡혈.md`](../1_Task/F03_데미지_ExecutionCalc/05_흡혈.md)

## ⭐ 결정 요약 (2026-09-08)

| # | 결정할 것 | 결정 |
|---|---|---|
| **주** | 공격자를 어디서 회복시키나 | **Execution 이 Source ASC 에 회복 GE 를 적용** (방안 1) |
| **①** | 회복을 메타 어트리뷰트로 받나 | **받는다.** `IncomingHealing` 을 `UERAttributeSet` 에 추가 (Lyra 형태) |
| **②** | 치유 감소가 겹치면 | ⭐ **가장 높은 것 하나만.** 곱하지 않는다 |
| **③** | 고정 피해에도 흡혈이 붙나 | **붙는다** (`OmniLifesteal` = "모든 유형") |
| **④** | `Lifesteal` vs `OmniLifesteal` | 기본공격만 / 모든 유형. **합산** |

사용자 판단: *"1 B 3 A"*, *"치유감소는 가장 높은양 기준으로 1개만 적용되도록"*

⚠ **용어**: 이 문서는 흡혈 회복량이 줄어드는 것을 **"치유 감소"** 로 부른다.
F03-06 의 **"보스 피해 감쇠"** 와는 다른 것이다 — 그쪽은 피해량이 줄고, 이쪽은 회복량이 준다.

## 결정할 것

**공격자를 회복시키는 코드를 어디에 둘 것인가.**

## ⚠ 먼저 — Task 문서의 스케치는 동작하지 않는다

Task 문서는 이렇게 제안했다:

```cpp
// 같은 Execution 안에서 Source 의 Health 를 올린다
OutExecutionOutput.AddOutputModifier(FGameplayModifierEvaluatedData(
    FERDamageStatics::Get().IncomingHealProperty, EGameplayModOp::Additive, HealAmount));
```

**출력 수정자는 언제나 Target 에 적용된다.**

```cpp
// GameplayEffect.cpp:3809-3821  InternalExecuteMod
bool FActiveGameplayEffectsContainer::InternalExecuteMod(FGameplayEffectSpec& Spec, FGameplayModifierEvaluatedData& ModEvalData)
{
    check(Owner);
    ...
    AttributeSet = const_cast<UAttributeSet*>(Owner->GetAttributeSubobject(AttributeSetClass));
```

`Owner` 는 **이 컨테이너의 소유자 = 피격자**다. 출력 수정자로 공격자를 회복시킬 방법이 없다.
→ Task 문서의 `(미확인)` 항목 **"Source 회복의 구현 방식"** 은 여기서 확정한다.

## 방안 1 — Execution 이 Source ASC 에 회복 GE 를 적용한다 ⭐ 추천

```cpp
// ERDamageExecution::Execute_Implementation 안
if (HealAmount > 0.f)
{
    if (UAbilitySystemComponent* SourceASC = ExecParams.GetSourceAbilitySystemComponent())
    {
        // Instant GE 하나로 Source 의 HP 를 올린다
        SourceASC->ApplyGameplayEffectToSelf(HealEffectCDO, 1.f, SourceASC->MakeEffectContext());
    }
}
```

`GetSourceAbilitySystemComponent()` 는 공개 API 다 (`GameplayEffectExecutionCalculation.h:40`).

**장점**

- ⭐ **흡혈 코드가 한 곳에만 있다.** Execution 은 이미 피해량·흡혈률·채널 태그·대상 태그를 **전부** 알고 있다
- ⭐ **어빌리티가 흡혈을 모른다.** 스킬이 40개가 되어도 흡혈 코드는 하나다
- 치유 감소 조건(AoE / 야생동물)이 태그로 오므로 Execution 이 그대로 읽는다
- `AttributeSet` 을 건드리지 않는다 — F02 의 재사용성이 유지된다

**단점**

- ⚠ **Execution 이 "계산만 하고 출력만 한다"는 순수성이 깨진다.** 다른 액터에 부수 효과를 낸다
- ⚠ 피격자의 GE 실행 도중에 **공격자에게 GE 를 적용**한다.
  컨테이너가 서로 달라 재진입은 아니지만, 순서에 의존하는 버그가 생기면 추적이 한 단계 깊어진다
- 회복용 GE 클래스가 하나 필요하다

## 방안 2 — Target 의 Meta 어트리뷰트로 받아 AttributeSet 이 가해자에게 돌려준다

`IncomingLifesteal` 메타를 Target 에 두고, `PostGameplayEffectExecute` 가 가해자를 찾아 회복시킨다.

```cpp
// UERAttributeSet::PostGameplayEffectExecute
if (Data.EvaluatedData.Attribute == GetIncomingLifestealAttribute())
{
    AActor* Instigator = Data.EffectSpec.GetEffectContext().GetOriginalInstigator();
    // Instigator 의 ASC 를 찾아 회복...
}
```

**장점**

- 모든 피해가 `IncomingDamage` 와 같은 통로를 탄다 — 일관성
- Execution 은 출력만 한다 (순수성 유지)

**단점**

- ⚠⚠ ⭐ **`UERAttributeSet` 에 "가해자를 찾아 회복시키는" 로직이 들어간다.**
  F02-04 에서 *"사망 처리를 하지 않는다 — 알리기만 한다"*, *"캐릭터 전용 로직이 없다 —
  야생동물이 같은 AttributeSet 을 쓸 수 있다"* 를 지키려고 일부러 뺐던 종류의 코드다.
  근거: [`../2_Checklist/F02_어트리뷰트셋/04_체력처리_사망알림.md`](../2_Checklist/F02_어트리뷰트셋/04_체력처리_사망알림.md)
- ⚠ **어트리뷰트가 하나 늘어난다** (메타라 복제는 안 되지만 클래스는 커진다)
- ⚠ 결국 **AttributeSet 도 다른 ASC 에 GE 를 적용**하게 된다 — 방안 1 의 단점을 그대로 갖는다.
  위치만 옮긴 것이고, 옮긴 곳이 더 나쁘다

## 방안 3 — 어빌리티가 후처리한다

역기획서의 구현 메모가 이 형태다:
*"흡혈은 피해 계산의 일부가 아니라 **피해 적용 이후의 후처리**다.
`CalculateDamage()` 가 반환한 최종 피해량과 `bIsAoE` / `bTargetIsWildlife` 플래그를 받아
별도 함수 `ApplyLifesteal()` 이 처리한다."* (§1.4)

**장점**

- 원 설계 의도에 가장 가깝다
- Execution 이 완전히 순수해진다

**단점**

- ⚠⚠ ⭐ **어빌리티가 최종 피해량을 모른다.** Execution 이 계산한 값을 돌려받을 경로가 없다.
  (GE 적용 결과로 나온 피해량은 어빌리티에 반환되지 않는다)
- ⚠ **스킬마다 흡혈 호출이 복제된다.** F03 의 존재 이유(*"계산식이 캐릭터마다 복제되는 것을 막는다"*)와 정면 충돌
- ⚠ 이 메모는 **자체 구현 기준**이다. GAS 에서는 Execution 이 Source·Target 을 둘 다 알기 때문에
  "함수의 순수성이 깨진다"는 원래 이유가 성립하지 않는다

## 비교표

| 축 | 1. Execution → Source | 2. Meta + AttributeSet | 3. 어빌리티 후처리 |
|---|---|---|---|
| 구현 난이도 | 낮음 | 중간 | ❌ **최종 피해량을 못 얻는다** |
| 확장성 (스킬 40개) | ⭐ 코드 1곳 | 코드 1곳 | ❌ 스킬마다 복제 |
| 네트워크 | 서버 전용, 동일 | 동일 | 동일 |
| GAS 정합성 | 공개 API 사용 | 메타 관례에 맞음 | ❌ 경로 없음 |
| F02 재사용성 | ⭐ **AttributeSet 안 건드림** | ❌ **야생동물 재사용이 깨진다** | 영향 없음 |
| 부수 효과 위치 | Execution | AttributeSet | 어빌리티 |

## ⭐ 결정 — **방안 1** (확정 2026-09-08)

방안 3 은 **최종 피해량을 어빌리티가 알 수 없어 실현 불가능**하다.
방안 2 는 부수 효과를 Execution 에서 AttributeSet 으로 옮길 뿐인데, **옮긴 곳이 더 나쁘다** —
야생동물·보스가 공유하는 클래스에 가해자 참조 로직이 들어간다.

방안 1 의 단점(순수성)은 실질 비용이 작다. Execution 은 이미 서버 전용이고
Source·Target 을 모두 아는 자리다.

## 함께 정해야 할 것 — 4가지

### ① 회복을 메타 어트리뷰트로 받을 것인가

| | |
|---|---|
| A. `HP` 를 직접 Additive | 지금 필요한 최소. 클램프는 F02-03 이 한다 |
| **B. `IncomingHealing` 메타 추가** ⭐ **채택** | `HealAmp`(회복량 증폭)를 한 곳에서 적용할 수 있다. Lyra 가 이 형태 (`LyraHealthSet.h:97`) |

⭐ **사용자 판단으로 B 채택.** 근거: **B 가 결국 필요해진다.**
회복 스킬·아이템이 생기면 `HealAmp`(회복량 증폭)를 적용할 자리가 있어야 하고,
나중에 옮기면 이미 만든 회복 GE 를 전부 고쳐야 한다.
⚠ 이 결정으로 **`UERAttributeSet` 에 메타 어트리뷰트가 하나 늘어난다** (`IncomingDamage` 와 같은 형태 — 복제하지 않는다).

### ② 치유 감소가 겹치면 — ⭐ **가장 높은 것 하나만** (확정)

사용자 판단: *"치유감소는 가장 높은양 기준으로 1개만 적용되도록"*

```cpp
float HealCut = 0.f;                                  // 치유 감소율
if (bAoE)      { HealCut = FMath::Max(HealCut, 0.5f); }   // 광역 50% 감소
if (bWildlife) { HealCut = FMath::Max(HealCut, 0.6f); }   // 야생동물 60% 감소
HealAmount *= (1.f - HealCut);                        // 곱하지 않는다. 최댓값 하나만
```

**흡혈 20%, 피해 100 기준:**

| 상황 | 치유 감소 | 배수 | 회복 |
|---|---|---|---|
| 단일 · 플레이어 | 0% | ×1.0 | **20** |
| 광역 | 50% | ×0.5 | **10** |
| 야생동물 | 60% | ×0.4 | **8** |
| **광역 + 야생동물** | **max(50, 60) = 60%** | ×0.4 | **8** |

**곱셈 중복을 안 쓰는 이유:** 감소 원인이 늘어날수록 회복이 기하급수로 0 에 수렴한다.
치유 감소가 셋만 겹쳐도 흡혈이 사실상 사라진다. 상한이 예측 가능한 쪽이 밸런싱하기 쉽다.
⚠ **(미확인)** — 원작 확인 불가. 자체 결정값으로 주석에 남긴다.

### ⚠⚠ 표기 함정 — 반드시 배수로 박는다

역기획서 §1.4 의 원문은 *"광역 피해 **50%**, 야생동물 대상 **60%**"* 다.
**둘 다 "깎는 비율"** 이지만, 읽는 사람이 "남는 비율"로 오해하기 쉽다.

⭐ 실제로 이 문서 초판이 야생동물을 `×0.6` 으로 잘못 적었다.
Task 문서의 검증 표(회복 **8**)와 대조해서 발견했다.

→ **코드에는 `0.5` / `0.6` 을 "감소율"로 박고, 곱하는 값은 `1 - HealCut` 으로 쓴다.**
   퍼센트를 그대로 곱하지 않는다.

### ③ 고정 피해에도 흡혈이 붙는가 — ⭐ **붙는다** (확정)

사용자 판단: *"3 A"*

| | |
|---|---|
| **A. 붙는다** ⭐추천 | `OmniLifesteal` 은 *"**모든 유형**의 피해"* 다 (§1.4) |
| B. 안 붙는다 | — |

§1.4 의 정의가 "모든 유형" 이라 A 가 문면에 맞다. **(미확인)** 로 주석에 남긴다.

### ④ `Lifesteal` 과 `OmniLifesteal` 의 관계

문서 §1.4 가 명확하다 — **(미확인) 아니다.**

| 스탯 | 적용 범위 |
|---|---|
| `Lifesteal` (생명력 흡수) | **기본 공격** 피해만 |
| `OmniLifesteal` (모든 피해 흡혈) | **모든 유형**의 피해 |

→ 기본 공격에서는 **둘 다** 적용된다. 합으로 처리한다:
`유효흡혈률 = (기본공격이면 Lifesteal : 0) + OmniLifesteal`

⚠ 상한은 둘 다 **(미확인)** 이다. F02-03 에 캡이 없다 — 필요해지면 그때 추가한다.

## 검증 (방안 1 기준)

| 입력 | 기대 회복 |
|---|---|
| 피해 100, `OmniLifesteal` 20%, 단일, 캐릭터 | **20** |
| 피해 100, `Lifesteal` 20%, **스킬** 채널 | **0** (기본 공격 전용) |
| 피해 100, `Lifesteal` 20%, **기본 공격** | **20** |
| ⭐ 피해 100, 20%, **AoE 태그** | **10** |
| 피해 100, 20%, **야생동물 태그** | **8** |
| AoE + 야생동물 동시 | **8** (가장 높은 60% 하나만 — ②) |
| 피해 0 | **0** |
| ⭐ 회복이 **공격자**에게 간다 | 피격자 HP 는 안 오른다 |

## 새로 필요한 태그

| 태그 | 누가 붙이나 |
|---|---|
| `Damage.Shape.AoE` | **스킬(어빌리티)** 이 GE Spec 에 붙인다 — 판정 형상을 Execution 이 추측하지 않는다 |
| `Actor.Type.Wildlife` | **야생동물 액터**가 갖는다 — `Cast<>` 로 클래스를 검사하지 않는다 |

⭐ 태그로 판별하는 이유: Execution 이 `Cast<ABossActor>` 를 하면 **F03 이 F12 에 의존**하게 된다.
태그면 야생동물이 나중에 생겨도 Execution 을 안 고친다.
