# 13. 강제 이동(넉백 · 그랩)을 어떻게 구현할 것인가

> F06-04 · 근거 [`전투판정_상태이상_역기획서.md`](../0_GameDesign/Systems/전투판정_상태이상_역기획서.md) §3.5
> 관련 [`E08`](../5_ErrorReport/E08_멀티에서_클릭이동_안됨.md)

## 결정할 것

**서버가 "3m 뒤로 밀어낸다" 를 정했을 때, 그 이동을 어떻게 실행할 것인가.**

역기획서가 이 절을 **"반드시 읽을 것"** 으로 표시했다:

> *"강제 이동은 **유일하게 캐릭터 위치를 바꾸는 CC**이고, 언리얼에서 가장 깨지기 쉬운 부분이다.
> `CharacterMovementComponent`는 소유 클라이언트가 이동을 예측하고 서버가 교정하는 구조라,
> 서버가 위치만 바꾸면 **클라가 원래 자리로 되돌리려 하면서 러버밴딩이 난다.**"*

---

## ⭐ 먼저 확인한 사실 세 가지

### ① RootMotionSource 는 네트워크 동기화가 **엔진에 내장**돼 있다

```cpp
// CharacterMovementComponent.h — FSavedMove_Character 멤버
FRootMotionSourceGroup SavedRootMotion;      // :2945
```

```cpp
// 서버가 클라의 루트모션 위치를 교정하는 RPC
ClientAdjustRootMotionSourcePosition(...)    // :2481, :2569
ConvertRootMotionServerIDsToLocalIDs(...)    // :2708 — 서버/클라 ID 매칭
```

⭐⭐ **E08 에서 문제였던 것이 여기서는 이미 풀려 있다.**
E08 은 `RequestedVelocity` 가 `FSavedMove_Character` 에 **없어서** 서버로 안 갔다.
`SavedRootMotion` 은 **있다.**

### ② 그러나 서버가 추가한 소스가 클라로 **자동 복제되지는 않는다**

```cpp
// CharacterMovementComponent.h:2677-2678
UPROPERTY(Transient)                    // ⚠ Replicated 가 아니다
FRootMotionSourceGroup CurrentRootMotion;
```

→ 서버에서 `ApplyRootMotionSource()` 만 부르면 **클라는 모른다.**
→ 서버만 움직이고 클라를 교정 → **역기획서가 경고한 러버밴딩.**

### ③ GAS 태스크가 이걸 어떻게 피하나

```cpp
// AbilityTask_ApplyRootMotionMoveToForce.cpp:77
RootMotionSourceID = MovementComponent->ApplyRootMotionSource(MoveToForce);
```

⭐ **어빌리티가 서버·클라 양쪽에서 실행되면서 각자 소스를 추가한다.** 그리고 ID 로 매칭한다.

⚠⚠ **우리는 어빌리티가 없다** (F07). 그래서 "양쪽에서 실행" 을 **직접 만들어야 한다.**
이것이 이 문서의 논점이다.

### ④ 거리 보장은 `MoveToForce` 가 해준다

```cpp
// RootMotionSource.h:536-548
struct FRootMotionSource_MoveToForce : public FRootMotionSource
{
    FVector StartLocation;
    FVector TargetLocation;      // ⭐ 목표 지점을 직접 지정한다
```

→ *"정확히 3m"* 이 표현된다. 임펄스처럼 마찰·중력에 좌우되지 않는다.

## 방안 A — `LaunchCharacter` / `AddImpulse` (서버)

**장점**
- 가장 단순하다. 한 줄이다
- 엔진 기본 기능이다

**단점**
- ⚠⚠ **거리 보장이 안 된다.** 마찰·중력·지형에 따라 실제 이동 거리가 달라진다.
  매그너스 E 는 *"3m"* 로 정의돼 있다
- ⚠ `LaunchCharacter` 는 복제되지 않는다. 서버만 움직이고 클라는 교정당한다 → **러버밴딩**
- ⚠ 벽 충돌 시점을 알기 어렵다 (언제 멈췄는지 판정 필요)

---

## 방안 B — RootMotionSource + `NetMulticast` 로 양쪽에서 추가 ⭐

```
[서버] 넉백 결정 (방향 · 거리 · 시간)
   ├─ 자기 CMC 에 FRootMotionSource_MoveToForce 추가
   └─ NetMulticast(시작위치, 목표위치, 시간) 로 뿌린다
                  ↓
[각 클라] 같은 파라미터로 **같은 소스**를 자기 CMC 에 추가
   → CMC 가 각자 계산. 소유 클라는 예측이 되고, 어긋나면
     엔진의 ClientAdjustRootMotionSourcePosition 이 교정한다
```

**장점**
- ⭐⭐ **거리가 정확하다** (`TargetLocation` 지정)
- ⭐⭐ **CMC 의 정규 경로를 탄다** — 콜리전·지형·계단 처리가 전부 따라온다
- ⭐ 소유 클라가 **예측**하므로 러버밴딩이 최소다.
  어긋나도 엔진의 루트모션 교정 RPC 가 처리한다
- ⭐ 넉백·그랩이 **방향만 다른 같은 함수**가 된다 (역기획서 요구)
- ⭐ F07 에서 어빌리티가 생기면 **`UAbilityTask_ApplyRootMotionMoveToForce` 로 갈아탈 수 있다** —
  같은 `FRootMotionSource` 를 쓰므로 개념이 그대로다

**단점**
- ⚠ `NetMulticast` RPC 를 하나 만들어야 한다
- ⚠ 벽 충돌로 **중단**할 때 서버가 소스를 제거하고 그것도 알려야 한다
- ⚠ 늦게 접속한 클라(또는 관련성 밖에 있다 들어온 클라)는 RPC 를 놓친다
  → 넉백은 1초 미만이라 실질적 문제가 아니다. ⚠ 다만 기록해 둔다

---

## 방안 C — 커스텀 `EMovementMode` (역기획서 "권장")

> *"커스텀 `EMovementMode` + 복제된 CC 파라미터를 보고 **서버·클라가 같은 계산**을 수행.
> 정합성 최상, 구현 비용 높음"*

**장점**
- ⭐ 정합성 최상. 파라미터가 복제되므로 RPC 를 놓칠 일이 없다
- 넉백 중 다른 이동을 **구조적으로** 배제할 수 있다

**단점**
- ⚠⚠ **구현 비용이 크다.** `PhysCustom` 오버라이드, 네트워크 직렬화,
  `FSavedMove_Character` 확장(`FNetworkPredictionData_Client_Character` 파생)까지 필요하다
- ⚠ RootMotionSource 가 이미 제공하는 것을 **다시 만드는 것**이다 (`CLAUDE.md` §1)
- ⚠ 넉백 하나 때문에 CMC 예측 파이프라인을 건드리면 **F05 의 클릭 이동까지 영향**을 받는다

---

## 방안 D — `NetMulticast` 로 파라미터 뿌리고 각자 **직접 보간** (역기획서 "간이")

> *"서버가 시작점·방향·거리·시간을 `NetMulticast`로 뿌리고 각 머신이 보간,
> 종료 시 서버가 최종 위치를 확정. 구현 쉬움, 소유 클라 위치 튐 가능"*

**장점**
- 구현이 가장 쉽다

**단점**
- ⚠⚠ **콜리전을 우리가 처리해야 한다.** 보간으로 위치를 밀면 **벽을 뚫는다**
- ⚠ CMC 와 싸운다 — CMC 는 자기가 위치를 관리한다고 생각한다
- ⚠ 역기획서도 *"소유 클라 위치 튐 가능"* 을 인정한다

## ⭐ 추천 — 방안 B

**역기획서의 "권장"(C)과 "간이"(D) 사이에 더 나은 선택지가 있다.**

역기획서가 C 를 권한 이유는 *"서버·클라가 같은 계산을 수행"* 이다.
⭐ **RootMotionSource 가 정확히 그것을 제공한다** — 그리고 예측·교정까지 엔진이 한다.
C 의 목표를 D 에 가까운 비용으로 달성한다.

⚠ **C 를 배제하는 결정적 이유**: 커스텀 `EMovementMode` 는 `FSavedMove_Character` 확장이
필요하고, 그건 **F05 의 클릭 이동이 쓰는 예측 파이프라인을 건드린다.**
E08 로 방금 안정시킨 부분이다. 넉백 하나 때문에 그걸 다시 흔들지 않는다.

### 만들 것

| 파일 | 역할 |
|---|---|
| `Combat/ERForcedMove.h/.cpp` (새로) | 공용 함수 `ApplyForcedMove(Target, Direction, Distance, Duration)` |
| ⚠ `NetMulticast` RPC 위치 | **(미정)** — `AERCharacterBase` 가 유력. 구현하며 확정 |

⭐ **넉백과 그랩은 같은 함수**다. `Direction` 부호만 다르다 (역기획서 요구).

### ⚠ 함께 정해야 하는 것

| 항목 | 결정 |
|---|---|
| 벽 충돌 판정 | ⭐ **서버만.** 이동 중 매 틱 트레이스 (역기획서 §3.5) |
| 벽 충돌 시 | 서버가 소스 제거 + 추가 피해 · 기절 → 연출은 `NetMulticast` |
| 이동 입력 차단 | `State.Block.Movement` (F06-01) 를 그대로 쓴다 |
| `State.CCImmune` | ⏸ **F06-05** |
| 넉백 **속도 곡선** | ⚠ **(미확인)** — 등속인지 감속인지. 일단 `MoveToForce` 기본값 |
| 벽 충돌 **추가 피해량** | ✅ **찾았다** — 아래 |

## ⭐ 원작 조사 — 매그너스 E (2026-09-10)

구현 전에 검색했다 (메모리 방침). **수치를 찾았다.**

> 시즌 8에서 매그너스의 **강타(E)** 피해량이 `40/75/110/145/180`
> (+추가 공격력 50%)(+스킬 증폭 50%)(**+대상 최대 체력 8%**)로 조정되고,
> ⭐ **벽 충돌 시** `20/40/60/80/100`
> (+추가 공격력 30%)(+스킬 증폭 20%)(**+대상 최대 체력 4%**) **추가 피해**.
> 전방의 적 1명을 **자신의 왼쪽으로 3.0m** 날리고, 벽에 부딪치면 **스턴**.
> 기절 지속은 **0.7초 + 레벨당 0.15 → 최대 1.3초**.
> — [나무위키 매그너스](https://namu.wiki/w/%EB%A7%A4%EA%B7%B8%EB%84%88%EC%8A%A4(%EC%9D%B4%ED%84%B0%EB%84%90%20%EB%A6%AC%ED%84%B4))

### 이 조사가 확인해 준 것

| 항목 | 결과 |
|---|---|
| 넉백 거리 | ⭐ **3.0m** — Task 문서와 일치 |
| 벽 충돌 추가 피해 | ⭐ **확인.** 레벨 스케일 + 계수 + **최대 체력 비례 4%** |
| 벽 충돌 기절 | ⭐ **0.7 ~ 1.3초** — 역기획서 §3.1 의 *"0.5~1.3초"* 와 맞물린다 |
| ⚠ 넉백 **방향** | *"자신의 **왼쪽**으로"* — 시전자→대상이 아니라 **시전자 기준 방향**이다 |

⭐⭐ **추가 피해가 "대상 최대 체력의 4%" 를 포함한다** → F03 의 **비례 피해**를 그대로 탄다.
새로 만들 것이 없다 ([`7_비례피해_감쇠판별.md`](7_비례피해_감쇠판별.md)).

### ⚠ 그런데 이건 **F07 소관이다**

수치는 **스킬 데이터**다. F06-04 는 **구조**(공용 함수 · 전파 · 벽 판정)만 만든다.
⭐ 위 수치는 F07 에서 매그너스 E 를 만들 때 쓴다. **여기 기록해 두는 것이 목적이다.**

⚠ **방향 인자의 의미가 바뀔 수 있다.** 지금은 `Direction` 을 월드 방향으로 받는데,
원작이 *"시전자의 왼쪽"* 이면 **시전자 기준 계산**이 필요하다.
→ 공용 함수는 **월드 방향을 받는 채로 두고**, 시전자 기준 변환은 **스킬이 한다**.
그래야 넉백(시전자→대상) · 그랩(반대) · 매그너스 E(왼쪽)를 **같은 함수**로 처리할 수 있다.
