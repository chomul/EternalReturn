## 0. 이 시스템의 정체

**D 슬롯은 캐릭터의 것이 아니다. 무기의 것이다.**

P / Q / W / E / R 다섯 슬롯은 실험체가 소유한다. **D 하나만 장착한 무기 계열이 소유한다.**
그래서 같은 실험체라도 **무기를 바꾸면 스킬 1개가 통째로 교체된다** (`이터널리턴_역기획서.md` §5.2).

이것이 이 게임의 IP인 이유는 산술이다.

```
캐릭터 90명 × 평균 2~3 무기군 ≈ 200개 이상의 "플레이 경험"
그런데 만든 것은 캐릭터 90개 + 무기 계열 23개 = 113개의 애셋뿐이다.
```

D는 **캐릭터 애셋 하나 늘리지 않고 곱셈으로 콘텐츠를 늘리는 장치**다.
동시에 이것이 **밸런싱 단위를 "캐릭터"에서 "캐릭터 × 무기"로 바꿔 버리는 원인**이기도 하다.
장비 문서의 표현대로 **"캐릭터가 무기를 고르는 게 아니라 무기가 캐릭터를 고른다"**
([`장비_아이템_역기획서.md`](장비_아이템_역기획서.md) §2).

> **구현 관점의 결론:** D를 `AERCharacterBase`의 여섯 번째 스킬 슬롯으로 만들면 안 된다.
> **`장착 무기 계열 → D스킬 데이터` 는 파생값**이어야 하고, 캐릭터가 들고 있는 것은
> **무기 계열 ID 하나뿐**이어야 한다. 캐릭터에 D를 직접 붙이면 무기를 바꿀 때마다
> 어빌리티를 손으로 갈아끼워야 하고, **GAS의 grant 패턴을 못 쓴다** (`CLAUDE.md` §8).

## 1. 슬롯 구조에서 D의 위치

| 슬롯 | 소유자 | 최대 레벨 | 레벨 소스 |
|---|---|---|---|
| **P (패시브)** | 실험체 | 3단계 | 실험체 레벨 |
| **Q / W / E** | 실험체 | 5 | 스킬 포인트 |
| **R (궁극기)** | 실험체 | 3 | 스킬 포인트 |
| **D (무기 스킬)** | ⭐ **무기 계열** | **3구간** | ⭐ **무기 숙련도 5 / 10 / 15** |
| **F (전술 스킬)** | 로비 선택 | 2 | 전술 강화 모듈 소비 |

출처: `이터널리턴_역기획서.md` §5.2 [S5]

> ⭐ **D만 레벨 소스가 다르다.** Q/W/E/R은 플레이어가 스킬 포인트를 찍어 올리지만,
> D는 **찍을 수 없다.** 무기 숙련도가 5/10/15에 도달하는 순간 서버가 자동으로 올린다.
> 즉 `FSkillRow`의 레벨 배열을 그대로 쓰되, **D만 배열 길이 3 + 인덱스 계산이 숙련도에서 온다.**
> 스킬 프레임워크가 "레벨 = 플레이어가 찍은 값"을 전제하면 D에서 무너진다.

## 3. 값 충돌 — 위키 [S8] vs 12.2 실측 [S1]

**원본이 §5.3 서두에 붙여 둔 경고를 그대로 보존한다. 한쪽을 임의로 고르지 않는다.**

| 항목 | 위키 [S8] | 12.2 패치노트 [S1] | 이 문서의 처리 |
|---|---|---|---|
| **채찍 · 바람 가르기 쿨다운** | 25 / 20 / 15초 | **4초 → 5초** | ⚠ **구조 자체가 다르다.** 위키는 숙련도 3구간, 12.2는 단일값. 채택 = **12.2**, 단 구조 불일치를 미해결로 기록 |
| **채찍 · 대상 최대 체력 비율 피해** | 8% | **12%** | 12.2 채택 |
| **석궁 · 강노 이동속도 감소** | 50% | **40%** | 12.2 채택 |
| **암기 · 마름쇠 추가 공격력 계수** | 50% | **65%** | 12.2 채택 |
| **무기 계열 총 개수** | 23종 [S13], [S8] | 공식 문서상 명시 없음 | **(미확인)** — 23종은 위키 기준 (`이터널리턴_역기획서.md` §8.3) |

> ⚠ **채찍의 쿨다운 충돌은 값 차이가 아니라 설계 차이다.**
> 위키가 맞다면 D는 전부 "숙련도 3구간 배열"이고, 12.2가 맞다면 **일부 D는 숙련도로 쿨다운이 변하지 않는다.**
> 표에서 이미 방망이(25) · 양손검(30) · 돌격소총(17) · 암기(30) · 기타(25) · 카메라(30)가 **단일값**으로 기재돼 있다.
> → **데이터 스키마는 `TArray<float> Cooldown` 길이 3을 유지**하되, 단일값 무기는 세 칸에 같은 값을 넣는다.
> 스키마를 단일 `float`으로 좁히면 나중에 되돌릴 수 없다.

## 4. ⭐ 핵심 산출물 2 — 초기 버전 8종 선별

원본 §12.5 「초기 버전에서 잘라내도 되는 것들」:
*"**무기 23종 → 6~8종.** 근접 3(단검·양손검·망치) + 원거리 2(권총·활) + 특수 1 정도면 계열 차별화 체감 가능"*

**그대로 따르지 않는다.** 원본의 예시 조합은 **6인 캐릭터와 맞물리지 않는다** — 활은 6인 중 아무도 쓰지 않고,
저격총·암기·도끼·권총이 빠져 있어 카티야·시셀라·재키·레니가 D를 못 쓴다.

### 4.1 선별 기준 (4개, 이 순서로 적용)

1. **6인이 장착 가능한 무기인가** — `00_공통_구현규약.md` §2.5의 10종 밖은 **검증할 캐릭터가 없다.**
2. **판정 타입이 서로 다른가** — 같은 판정을 쓰는 무기를 둘 넣으면 계열 차별화가 체감되지 않는다.
3. **근접 / 원거리 / 특수 균형** — 세 카테고리가 모두 있어야 "무기 계열"이 시스템으로 보인다.
4. **§12.5의 검증 기준을 성립시키는가** — *"같은 캐릭터를 무기를 바꿔 플레이했을 때 다른 캐릭터로 느껴지는가"*.
   ⭐ **캐릭터당 1무기만 넣으면 이 검증 자체가 불가능하다.** 최소 한 명은 2무기를 가져야 한다.

### 4.2 선별 결과 — **8종, 2단계로 나눠 넣는다**

**1단계 (6종) — 캐릭터당 1종. 시스템 성립용.**

| 계열 | 캐릭터 | D스킬 | 왜 이것인가 |
|---|---|---|---|
| **망치** | 매그너스 | 방어구 파괴 | **가장 싸다**(★). 장비 문서 §3이 **망치 제작 트리를 이미 전수 조사**해 둠 → 아이템 데이터 재작업 없음 |
| **도끼** | 재키 | 피의 나선 | 재키 4무기 중 유일하게 쿨다운 7/6/5초 — **저쿨 D의 조작감**을 검증할 수 있는 유일한 표본 |
| **단검** | 다니엘 | 은신 단도 | 다니엘 E가 은신·순간이동을 이미 씀 → **공용 함수 재사용**(`04_다니엘.md` §4 구현 메모) |
| **암기** | 시셀라 | 마름쇠 투척 | 장판(설치물) + 둔화. 레니 R 발판과 같은 부품 |
| **저격총** | 카티야 | 스나이핑 | **모드 전환**이라는 유일한 신규 축. 이게 없으면 "무기가 플레이를 바꾼다"가 증명 안 됨 |
| **권총** | 레니 | 이동 사격 재장전 | 피해가 없는 **순수 버프형 D** — D가 딜링기만이 아님을 보여주는 표본 |

이 6종은 `00_공통_구현규약.md` §2.5의 「초기 구현 제안」과 **정확히 일치**한다.

**2단계 (+2종) — §12.5의 검증 기준을 성립시키는 최소 추가.**

| 계열 | 캐릭터 | D스킬 | 왜 추가하는가 |
|---|---|---|---|
| **방망이** | 매그너스 (2번째) | 풀스윙 | **가장 싼 두 번째 무기.** 매그너스 E의 넉백+벽충돌 공용 함수를 그대로 쓴다(`02_매그너스.md` §4). 망치(디버프) ↔ 방망이(넉백 CC)로 **플레이 성향이 갈리는지** 검증 가능 |
| **투척** | 시셀라 (2번째) | 연막 | **특수 카테고리 커버**. 시야 차단은 다니엘 W(시야 감소 2초)가 이미 요구하므로 신규 비용이 낮다. 암기(딜·CC) ↔ 투척(순수 유틸)로 성향이 갈림 |

**최종 8종 균형:** 근접 4(망치·방망이·도끼·단검) / 원거리 3(암기·저격총·권총) / 특수 1(투척).
**2무기 캐릭터 2명**(매그너스, 시셀라) → §12.5 검증 기준을 A/B로 비교할 수 있다.

> 8종의 **데미지 계수 원본값은 `이터널리턴_역기획서.md` §5.3에 그대로 있다** — 데이터 테이블 입력용이므로 여기 복사하지 않는다.
> 계수가 실제 피해로 변환되는 공식은 [`스탯_데미지공식_역기획서.md`](스탯_데미지공식_역기획서.md) 담당이다.

### 4.3 잘라내는 15종에 대한 처리

**`EWeaponType` enum에는 23종 전부 자리를 만든다. 데이터 테이블 행은 8개만 만든다.**
이유는 [`전투판정_상태이상_역기획서.md`](전투판정_상태이상_역기획서.md) §6과 같다 —
검증할 캐릭터가 없는 로직을 지금 짜면 **죽은 코드**가 된다 (`CLAUDE.md` §2).
enum 자리를 미리 잡아 두는 것은 **저장된 애셋의 enum 값이 나중에 밀리는 사고를 막기 위해서**다 (`CLAUDE.md` §3).

## 6. 무기 숙련도와 D 해금

**숙련도 시스템 자체(6종 트랙·경험치 공식·복제 정책)는** [`성장_레벨_숙련도_특성_역기획서.md`](성장_레벨_숙련도_특성_역기획서.md) **§3 담당이다.**
여기서는 **D 해금에 걸리는 부분만** 다룬다.

| 구간 | 상태 | D 슬롯 |
|---|---|---|
| 숙련도 0~4 | 잠김 | ⭐ **슬롯 자체가 비활성.** UI에 자물쇠 |
| **숙련도 5** | **해금** | D 인덱스 0 (스킬 개수 4 → **5**) |
| **숙련도 10** | 1차 강화 | D 인덱스 1 |
| **숙련도 15** | 2차 강화 | D 인덱스 2 |

출처: `이터널리턴_역기획서.md` §5.2 / §9.2.1 [S5]

**매치 내 성장 곡선** — 원본 §9.3이 D 해금을 **초반 파워 스파이크의 원인**으로 지목한다.

| 시점 | 사건 |
|---|---|
| 1일차 밤 ~ 2일차 낮 | **숙련도 5 → D 해금.** 스킬 개수 4 → 5 |
| 3~4일차 | 숙련도 10 → D 1차 강화 |
| 5~6일차 | 숙련도 15 → D 2차 강화 |

출처: `이터널리턴_역기획서.md` §9.3, [`성장_레벨_숙련도_특성_역기획서.md`](성장_레벨_숙련도_특성_역기획서.md) §6

⭐ **숙련도 경험치는 실험체 피해가 야생동물의 12.6배다** (실험체 피해 100당 63 / 야생동물 100당 5, `이터널리턴_역기획서.md` §9.2.1).
성장 문서 §3.1의 해석: *"초반에 싸운 쪽이 먼저 스킬 하나를 더 얻는다"*.
→ **D 해금은 스노우볼 장치이며, 이것이 D를 "무기가 주는 보너스"가 아니라 게임 루프의 축으로 만든다.**

**구현 메모**
- `5 / 10 / 15`는 **데이터 테이블 값**이다. 하드코딩하지 않는다 (성장 문서 §구현 메모와 동일 지침).
- 해금·강화 판정은 **숙련도 레벨이 변하는 순간의 서버 이벤트**다. 매 프레임 비교하지 않는다 (`CLAUDE.md` §2).
- 숙련도 값은 `COND_OwnerOnly` 복제가 **권고**된다 — 적의 숙련도가 클라에 있으면 **D 해금 여부를 미리 아는 정보 우위**가 생긴다.
  단 **D 사용 자체는 모든 클라가 봐야 하므로**(연출), 해금 여부와 D 발동은 다른 경로다. 원작 처리 방식은 **(미확인)**.

## 7. D와 F(전술 스킬)의 관계 — 슬롯 스왑을 지원해야 하는가

**원작:** F는 로비에서 선택하는 전략 슬롯이며 **D키와 스왑 가능**하다 (`이터널리턴_역기획서.md` §5.2 [S5]).
**원본 권고:** *"전술 스킬(F) 14종 — D(무기 스킬)와 역할이 겹치고, 슬롯 2개는 초심자에게 과하다.
**초기 버전에서 완전 삭제.** D만 운영"* (`이터널리턴_역기획서.md` §12.5)
성장 문서 §7도 같은 결론이다 — F는 초기 버전에서 삭제, 구현 우선순위 9순위(= 하지 않음).

### 판단

**F 로직은 만들지 않는다. 스왑 UI도 만들지 않는다. 다만 "슬롯의 스킬 소스" 개념 하나만 남긴다.**

| 선택지 | 지금 드는 비용 | F 도입 시 비용 | 채택 |
|---|---|---|---|
| A. D를 캐릭터 스킬 배열의 6번째 칸으로 고정 | 0 | **D 슬롯 전체 재작업** | ✕ |
| B. 슬롯에 **스킬 소스**(캐릭터/무기/전술)를 바인딩하는 구조 | **enum 1개 + 바인딩 함수 인자 1개** | 소스 종류 추가만 | ⭕ |
| C. 지금 D↔F 스왑까지 구현 | 중 | 0 | ✕ (`CLAUDE.md` §2 — 요청받지 않은 확장성) |

**B를 채택한다.** 근거: 비용이 사실상 0인데(§데이터 스키마의 `ESkillSource`), A는 되돌리는 비용이 크다.
D 슬롯의 스킬이 **어디서 오는가**는 어차피 결정해야 하는 값이다 — 그것을 enum으로 이름 붙이는 것뿐이다.

> **(미확인)** 원작의 "D키와 스왑 가능"이 **키 바인딩만 바꾸는 것**인지, **슬롯 자체를 교체해 D를 못 쓰게 되는 것**인지
> 원본 서술로는 판별되지 않는다. F를 실제로 넣을 때 확인해야 한다.

## 8. 네트워크 설계

**매치 규모: 3인 × 8팀 = 최대 24명.** 무기 장착은 **서버 권위**다 (`CLAUDE.md` §6).

### 8.1 무기 교체 → D 교체를 어떻게 복제하는가

⭐ **D스킬을 복제하지 않는다. 무기 계열 ID만 복제한다.**

```
클라 [무기 장착 요청]
  → Server RPC (WithValidation)
  → 서버: ① 인벤토리에 그 아이템이 있는가
          ② FCharacterWeaponRow.AllowedWeapons 에 그 계열이 있는가   ← 장착 제한 검증
          ③ 현재 D 시전 중인가 → 취소 (§8.3)
  → 서버: EquippedWeaponType 갱신
  → UPROPERTY(ReplicatedUsing = OnRep_EquippedWeapon)   ← 전 클라
  → 각 클라 OnRep_ : D 아이콘·쿨다운 UI·무기 메시·기본 공격 사거리 갱신
```

| 항목 | 권위 | 복제 | 이유 |
|---|---|---|---|
| **`EquippedWeaponType`** (uint8) | 서버 | **전 클라** | 적의 무기 모션·**기본 공격 사거리**를 봐야 한다 ([`전투판정_상태이상_역기획서.md`](전투판정_상태이상_역기획서.md) §5.2 — *"기본 공격 사거리는 무기 계열이 결정"*) |
| **무기 숙련도 레벨** (uint8) | 서버 | `COND_OwnerOnly` **권고** | 적의 D 해금 여부 은닉 (§6) |
| **D 스킬 데이터** | — | ❌ **복제 안 함** | `무기 계열 + 숙련도` 로 **양쪽이 같은 테이블에서 파생**한다 |
| **D 쿨다운 잔여** | 서버 | 소유자 | UI는 로컬 보간 (`00_공통_구현규약.md` §3) |
| D 발동 연출 | 서버 판정 후 | `NetMulticast` | |

> **대역폭 계산:** 24명 × `uint8` 2개 = **48바이트**. D스킬 인스턴스를 복제하는 설계와 비교할 필요조차 없다.
> `UPROPERTY(Replicated)` 추가 시 `GetLifetimeReplicatedProps`에 **`DOREPLIFETIME` 반드시 추가** (`CLAUDE.md` §6).

### 8.2 ⭐ 쿨다운 진행 중 무기를 바꾸면 어떻게 되는가

**원작 처리 방식은 (미확인)이다.** 선택지는 셋이고, 각각 다른 게임이 된다.

| 정책 | 동작 | 결과 |
|---|---|---|
| **A. 리셋** | 새 무기의 D가 쿨다운 0에서 시작 | ❌ **명백한 익스플로잇.** 2무기 캐릭터가 D를 무한 연사한다 |
| **B. 무기별 개별 보존** | 계열마다 쿨다운을 따로 들고 있음. 되돌아오면 남은 시간 그대로 | ⚠ 2무기 캐릭터가 **D를 두 번 쓸 수 있다**(각각 1회) |
| **C. 슬롯 단위 승계** | 남은 쿨다운을 새 D에 그대로 넘김 | 무기별 쿨다운 편차(도끼 5초 vs 석궁 40초)를 무시하게 됨 |

**이 문서의 제안: B(무기별 개별 보존) + 무기 교체 시 D 슬롯에 공용 스왑 락.**
근거 — B는 데이터 구조가 가장 자연스럽고(쿨다운은 무기 계열에 귀속), A의 익스플로잇을 원천 차단한다.
B의 부작용("D 두 번")은 **교체 직후 D를 일정 시간 못 쓰게 하는 락 하나**로 막는다.

> ⚠ **락 시간은 자체 결정값이며 원작 확인값이 아니다.** 값은 팀이 정하고, 정했다는 사실을 기록한다.
> 실전에서는 필드에서 무기를 갈아 끼우는 행위 자체에 시간 비용이 있을 가능성이 높으나 **(미확인)**.

### 8.3 무기 교체 시 진행 중인 D 처리

| 상태 | 처리 |
|---|---|
| **저격총 모드 진입 중** | 서버가 **모드 상태를 강제 해제**하고 무기를 교체. 모드 상태가 남으면 기본 공격이 없는 무기로 저격 사격이 나간다 |
| **단검 은신 중** (재사용 대기) | 은신 상태는 **CC 컨테이너 소유**이므로 유지. 단 **2단 발동(순간이동)은 소실** |
| **양손검 패링 무적 0.75초 중** | ⭐ **무기 교체를 서버가 거부한다.** 허용하면 "무적을 켜고 다른 무기로 바꿔 무적만 유지"가 성립 |
| **투척 연막 설치물이 필드에 있음** | 설치물은 **스폰 시점의 소유권**을 갖는다. 무기를 바꿔도 유지·정상 만료 |

> **원칙:** 무기 교체는 **D 시전 중 금지**, **D가 남긴 지속 효과는 유지**.
> 이 규칙은 **자체 결정값**이다 — 원작 확인값이 아니다.

## 데이터 스키마 제안

**경계 선언 — 어느 문서가 무엇을 소유하는가.**

| 구조체 | 소유 문서 | 내용 |
|---|---|---|
| `EWeaponType` (enum) | ⭐ **이 문서** | 무기 계열 23종. 장비 문서의 `FItemRow.WeaponType`이 **이것을 참조**한다 |
| `FWeaponClassRow` | ⭐ **이 문서** | 계열 → D스킬 · 기본 공격 사거리 · 해금 임계값 |
| `FCharacterWeaponRow` | ⭐ **이 문서** | 캐릭터 × 무기 장착 허용 매트릭스 |
| `FItemRow` (무기 **아이템**) | [`장비_아이템_역기획서.md`](장비_아이템_역기획서.md) | 제작 트리·등급·스탯 |
| `FWeaponProficiencyRow` (실험체×무기 계수) | [`성장_레벨_숙련도_특성_역기획서.md`](성장_레벨_숙련도_특성_역기획서.md) | 레벨당 증폭 계수 |
| `FSkillRow` (D스킬 실체) | [`스킬_프레임워크_역기획서.md`](스킬_프레임워크_역기획서.md) | 판정·계수·쿨다운 배열 |

```cpp
UENUM(BlueprintType)
enum class EWeaponType : uint8   // 23종 자리를 만들되, 초기 데이터 행은 8개만 만든다 (§4.3)
{
    None,
    Glove, Tonfa, Bat, Hammer, Axe, Dagger, TwoHandSword, DualSword,      // 근접 13
    Spear, Nunchaku, Rapier, Whip, VFArm,
    Pistol, AssaultRifle, SniperRifle, Bow, Crossbow, Shuriken,           // 원거리 6
    Throw, Guitar, Camera, Arcana,                                        // 특수 4
};
UENUM(BlueprintType) enum class EWeaponCategory : uint8 { Melee, Ranged, Special };
// §7 — F를 만들지 않되, 슬롯이 스킬을 "어디서" 받는지만 이름 붙여 둔다
UENUM(BlueprintType) enum class ESkillSource : uint8 { Character, Weapon, Tactical /*미구현*/ };

USTRUCT(BlueprintType)
struct FWeaponClassRow : public FTableRowBase   // RowName = 계열명 (예: "Hammer")
{
    GENERATED_BODY()
    UPROPERTY(EditDefaultsOnly, Category="Weapon") EWeaponType     WeaponType = EWeaponType::None;
    UPROPERTY(EditDefaultsOnly, Category="Weapon") EWeaponCategory Category   = EWeaponCategory::Melee;
    // ⭐ 기본 공격 사거리는 무기 계열이 결정한다 (전투판정_상태이상_역기획서.md §5.2)
    UPROPERTY(EditDefaultsOnly, Category="Weapon") float BasicAttackRange = 0.f;
    // 계열이 소유하는 D스킬 1개 → FSkillRow(스킬 프레임워크)를 가리킨다. 실체를 복사하지 않는다
    UPROPERTY(EditDefaultsOnly, Category="DSkill") FName DSkillRowName;
    // ⭐ 5/10/15를 하드코딩하지 않는다. 배열 인덱스 0/1/2에 대응
    UPROPERTY(EditDefaultsOnly, Category="DSkill") TArray<int32> ProficiencyThresholds; // {5,10,15}
    UPROPERTY(EditDefaultsOnly, Category="FX") TSoftObjectPtr<UAnimMontage> DSkillMontage; // 연출만
};

USTRUCT(BlueprintType)
struct FCharacterWeaponRow : public FTableRowBase   // RowName = 실험체 (예: "Jackie")
{
    GENERATED_BODY()
    // §5.1 매트릭스. 코드에 박지 않는다 — 캐릭터를 늘릴 때 코드를 고치게 된다
    UPROPERTY(EditDefaultsOnly, Category="Weapon") TArray<EWeaponType> AllowedWeapons;
};
```

**컴포넌트 배치** — D 로직을 `AERCharacterBase`에 박지 않는다 (`CLAUDE.md` §8).

```
UWeaponSkillComponent (신규)
  ├ EquippedWeaponType            : Replicated (전 클라)
  ├ ProficiencyLevel              : Replicated (COND_OwnerOnly 권고) ← 값 자체는 성장 시스템 소유
  ├ TMap<EWeaponType, float>      : 무기별 쿨다운 만료 시각 (서버 전용, §8.2 정책 B)
  ├ GetActiveDSkillRow()          : 무기 계열 + 숙련도 → FSkillRow 파생 (복제하지 않는 이유)
  └ ServerEquipWeapon(...)        : WithValidation. 장착 제한·시전 중 검사
```

**GAS 구현 대응표** — ⭐ **이 시스템이 GAS와 가장 잘 맞는다.**

| 이 게임의 요구 | GAS 구현 |
|---|---|
| `FWeaponClassRow` / `FCharacterWeaponRow` | ✅ **그대로 데이터 소스로 사용** |
| `EWeaponType` | `GameplayTag` (`Weapon.Hammer` 등) |
| **무기 장착 → D 부여** | ⭐ **장비 `GameplayEffect`(Infinite)의 Granted Abilities** |
| **무기 해제 → D 회수** | 해당 GE 제거 → grant된 `UGameplayAbility` 자동 회수 |
| 장착 제한(`AllowedWeapons`) | 장비 GE의 `ApplicationTagRequirements` (캐릭터가 `Character.CanUse.Hammer` 보유) |
| **숙련도 5 해금** | GE의 `OngoingTagRequirements` 또는 어빌리티의 `ActivationRequiredTags` (`Weapon.Proficiency.Lv5`) |
| **숙련도 10 / 15 강화** | `GiveAbility(..., Level)` 의 **AbilityLevel** — 데이터 배열 인덱스가 그대로 대응된다 |
| D스킬 1개의 실행 로직 | `UGameplayAbility` 파생 클래스 1개 (스킬 프레임워크와 동일) |

> ⭐ **"무기가 스킬을 소유한다"는 이 게임의 핵심 구조가 GAS의 grant 패턴과 정확히 일치한다.**
> 장비 GE를 걸면 어빌리티가 따라오고, 벗기면 자동으로 회수된다 — **슬롯 재바인딩 코드를 직접 짤 필요가 없다.**
>
> 그래서 **캐릭터가 들고 있는 것은 무기 계열 ID 하나뿐**이어야 한다는 위 원칙이 더 중요해진다.
> 캐릭터에 D를 직접 붙이면 이 grant 구조를 못 쓰고, 무기 교체마다 어빌리티를 손으로 갈아끼워야 한다.

## 구현 우선순위

**전제: 스킬 프레임워크(`FSkillRow` · 쿨다운 · 시전 파이프라인)가 먼저 서 있어야 한다.**
D는 그 위에 얹히는 것이지, 별도 실행 경로가 아니다.

```
1순위. EWeaponType + FWeaponClassRow + FCharacterWeaponRow 데이터 테이블 (행 8개)
       → 검증: 빌드 통과 + 에디터에서 8행이 로드되고 장착 제한이 읽힘
2순위. UWeaponSkillComponent — EquippedWeaponType 복제 + ServerEquipWeapon(WithValidation)
       → 검증: Play As Client(2인)에서 서버가 장착을 확정하고 양쪽 클라의 무기 메시·기본 공격 사거리가 일치
3순위. D 슬롯 바인딩 — GetActiveDSkillRow() 파생 + D 입력 → 스킬 프레임워크 호출
       → 검증: ⭐ 무기를 바꾸면 D 아이콘과 실제 발동 스킬이 통째로 교체됨 (§12.5 핵심 검증)
4순위. 숙련도 5/10/15 해금·강화 연결 (값은 성장 시스템 소유, 임계값은 데이터 테이블)
       → 검증: 숙련도 5 도달 순간 D 슬롯이 활성화되고, 10에서 계수·쿨다운이 인덱스 1로 바뀜
5순위. 쿨다운 정책 B + 교체 시 스왑 락 + 시전 중 교체 거부 (§8.2 / §8.3)
       → 검증: 매그너스가 망치 D 사용 직후 방망이로 교체해도 D가 즉시 나가지 않음
6순위. 무비용 D 4종 — 망치(디버프) / 도끼(돌진+회복) / 암기(장판+둔화) / 권총(자기 버프)
       → 검증: 4종이 전부 기존 공용 함수만 호출하고 신규 판정 코드가 없음을 diff로 확인
7순위. 재사용 D 2종 — 방망이(넉백+벽충돌+기절 공용 함수) / 단검(은신+블링크 공용 함수)
       → 검증: 매그너스 E와 방망이 D가 같은 벽 충돌 함수를 호출 (호출 지점 2곳)
8순위. 신규 축 D 2종 — 저격총(모드 전환) / 투척(시야 차단 설치물)
       → 검증: 저격총 모드 중 무기 교체 시 모드가 서버에서 강제 해제됨
9순위. (하지 않는다) 전술 스킬 F · 나머지 15개 무기 계열
```

> 각 단계의 1차 검증은 **빌드 통과**다 (`CLAUDE.md` §4).
> 멀티플레이 검증은 전부 **`Play As Client, Number of Players: 2` 이상**에서 확인한다.
>
> ⭐ **3순위가 이 시스템 전체의 존재 이유다.** 원본 §12.5의 검증 기준:
> *"같은 캐릭터를 **무기를 바꿔** 플레이했을 때 플레이 감각이 「다른 캐릭터」로 느껴지는가."*
> 매그너스 = 망치(디버프 브루저) ↔ 방망이(넉백 이니시에이터), 시셀라 = 암기(딜·CC) ↔ 투척(순수 유틸)
> 이 두 쌍으로 A/B 비교한다. **한 캐릭터가 한 무기만 갖는 6종 구성으로는 이 검증이 불가능하다** (§4.1 기준 4).
