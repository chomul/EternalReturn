## 0. 이 시스템의 정체

**네트워크 아키텍처는 "나중에 붙이는 레이어"가 아니라, 이 게임에서 가장 먼저 확정돼야 하는 데이터 배치 규칙이다.**

이 프로젝트에는 이미 데디케이티드 서버 타겟이 실재한다 — `Source/EternalReturnServer.Target.cs:9` 의 `Type = TargetType.Server`. 즉 **"싱글로 만들고 나중에 멀티를 붙인다"는 선택지가 이미 닫혀 있다.** 그런데 현재 `Source/` 에는 모듈 파일 3개(`EternalReturn.Build.cs` / `.cpp` / `.h`)와 타겟 3개만 남아 있고, GameMode·GameState·PlayerController·PlayerState·Character 클래스는 **전부 삭제된 상태다** (`git status` 기준 `D` 마크). 이 문서는 **그 백지 위에 무엇을 어디에 놓을지**를 정한다.

핵심 판단 하나만 먼저 못 박는다.

| 잘못된 접근 | 왜 무너지는가 |
|---|---|
| "일단 `AERCharacterBase`에 다 넣고 나중에 나눈다" | 캐릭터는 **사망 시 파괴되는 액터**다. 크레딧·레벨·전적을 여기 넣으면 사망과 함께 증발한다 |
| "복제는 되는 대로 켜고 대역폭은 나중에 본다" | 24명 × 60Hz는 **8명 × 60Hz의 3배가 아니라, 연결 수 × 액터 수로 곱셈이 된다.** 나중에 끄는 것보다 처음부터 안 켜는 게 싸다 |
| "클라가 판정하고 서버가 확인만 한다" | 이 프로젝트 문서들이 이미 **6개 지점에서 같은 지적을 반복했다** (§9) |

> **구현 관점의 결론:** 이건 "네트워크 코드"가 아니라 **데이터의 수명과 가시 범위를 정하는 작업**이다.
> 각 값에 대해 딱 두 질문만 던지면 배치가 결정된다 — **"사망하면 사라져야 하나?"** 와 **"누가 봐도 되는 값인가?"**

## 1. 매치 규모와 서버 형태

### 1.1 확정 규모

| 항목 | 값 | 근거 |
|---|---|---|
| 팀 인원 | **3명** | `../이터널리턴_역기획서.md:207` |
| 팀 수 | **8팀** | 동일 |
| 최대 접속자 | **24명** | 동일 · `매치진행_게임모드_역기획서.md:100` |
| 서버 : 매치 | **1 : 1** — 데디케이티드 서버 프로세스 1개가 매치 1개를 소유하고, 매치가 끝나면 프로세스가 종료된다 | 이 문서의 **자체 결정값** (원작 운영 구조는 (미확인)) |
| 매치 길이 | 원작 약 26~27분, **클론 권장 15~18분** | `매치진행_게임모드_역기획서.md:140` |

⭐ **`TeamSize` / `TeamCount` 는 처음부터 데이터값으로 뺀다.** `매치진행_게임모드_역기획서.md:138` 가 이미 요구한 사항이며, 네트워크 관점에서도 중요하다 — **팀 크기가 하드코딩되면 팀 시야 릴리번시(별도 문서)가 팀 크기에 의존해 못 짜인다.**

### 1.2 서버 프로세스 모델 — 1 매치 = 1 프로세스

```
매치메이커가 24명 확정
        ↓
데디 서버 프로세스 spawn (포트 1개 점유, 맵 URL + 매치 파라미터를 커맨드라인으로 전달)
        ↓
서버가 Listen → 24명이 개별로 접속 → PostLogin × 24
        ↓
매치 진행 (약 15~27분)
        ↓
결과 확정 → 결과 업로드 → 전원 클라이언트를 로비로 ClientTravel → 프로세스 종료
```

**왜 이 모델인가**

- 매치가 끝나면 프로세스를 죽이므로 **메모리 누수·상태 오염이 매치 경계에서 자동으로 청소된다.** 한 프로세스가 여러 매치를 연달아 돌리면 이전 매치의 액터·타이머·델리게이트가 남았는지를 매번 검증해야 한다.
- `AGameMode::CheckMatchEnd()` 이후의 정리 코드가 단순해진다 — `매치진행_게임모드_역기획서.md:306` 의 `bMatchEnded` 가드가 "종료 후 잔여 RPC 무시"만 책임지면 되고, 상태 리셋을 책임질 필요가 없다.
- ⚠ **비용:** 프로세스 spawn 지연(수 초)이 매칭 완료 후에 추가된다. 실측값 **(미확인)** — 서버 빌드로 빈 맵을 Listen까지 띄우는 시간을 측정해야 한다.

> 대안인 **"서버 프로세스 재사용(seamless travel)"** 은 엔진이 지원한다(`GameModeBase.h:584` `bUseSeamlessTravel`, `PlayerState.h:266` `SeamlessTravelTo`). 하지만 프로토타입 단계에서 매치 간 상태 오염을 디버깅하는 비용이 spawn 지연보다 크다고 판단한다. **자체 결정값이며, 동시접속이 늘어 spawn 비용이 문제가 되면 재검토한다.**

## 2. 프레임워크 클래스 역할 분담

### 2.1 어디에 존재하고 무엇을 담는가

| 클래스 | 존재하는 곳 | 복제 | 수명 | 담을 것 | 담으면 안 되는 것 |
|---|---|---|---|---|---|
| **`AERGameMode`** (`AGameModeBase` 파생) | **서버에만** — `GameModeBase.cpp:66` `bNetLoadOnClient = false`, 클라에는 인스턴스 자체가 없다 | ❌ 없음 | 매치 전체 | 규칙 판정, 페이즈 전환, 승패 판정, 스폰·부활 결정, 로그인 처리 | **클라가 알아야 하는 값 전부.** 클라는 이 객체를 볼 수 없다 |
| **`AERGameState`** (`AGameStateBase` 파생) | **서버 + 모든 클라** | ✅ `bReplicates = true`, `bAlwaysRelevant = true` (`GameStateBase.cpp:25-26`), `NetPriority = 10.f` (`:41`) | 매치 전체 | 매치 페이즈, 페이즈 종료 시각, 생존 팀 수, 팀 목록, 제한구역 상태, 오브젝트 상태 | 개인별 값(개인 폭사 타이머 등) — 24명분이 전원에게 복제된다 |
| **`AERPlayerState`** | **서버 + 모든 클라** | ✅ `bReplicates = true`, `bAlwaysRelevant = true`, `NetUpdateFrequency = 1` (`PlayerState.cpp:24-27`) | **플레이어 접속 ~ 퇴장.** 캐릭터 사망과 무관하게 살아남는다 | 팀 ID, 실험체 ID, 레벨, 크레딧, 킬/데스, 생존 상태, 부활 가능 여부 | 매 프레임 바뀌는 값 — 기본 갱신 빈도가 **1Hz**다 |
| **`AERPlayerController`** | **소유 클라 + 서버.** 다른 클라에는 없다 | ✅ (소유자에게만) `NetPriority = 3.0f` (`PlayerController.cpp:191`) | 접속 ~ 퇴장 | 입력 처리, `Server` RPC 진입점, HUD 소유, 카메라, 관전 대상 | 게임 상태 값 — 남이 못 보는 곳이다 |
| **`AERCharacter`** (`APawn` 파생) | 서버 + **릴리번시를 통과한 클라** | ✅ `NetPriority = 3.0f`, `NetUpdateFrequency = 100.f` (`Pawn.cpp:80-81`) | **스폰 ~ 사망.** 사망하면 파괴된다 | 위치, 체력, 상태이상, 스탯 컴포넌트, 스킬 컴포넌트, 인벤토리(논쟁 — §2.3) | 사망 후에도 남아야 하는 값 전부 |

### 2.2 판단 기준 — 두 질문으로 끝난다

새 데이터가 생길 때마다 이 순서로 묻는다. **"애매하면 PlayerState"는 답이 아니다.**

```
Q1. 캐릭터가 죽었을 때 이 값은 사라져야 하나?
     예  → Pawn (AERCharacter)
     아니오 → Q2

Q2. 나(소유 클라)만 알아야 하나, 남도 봐야 하나?
     나만        → PlayerState + DOREPLIFETIME_CONDITION(..., COND_OwnerOnly)
     팀만        → PlayerState + 팀 범위 조건 (엔진 기본 COND_에 팀 개념은 없다 → 커스텀 필요, §5.4)
     전원        → PlayerState (조건 없음)
     아무도 몰라도 됨 → GameMode (서버 전용)

Q3. 플레이어에게 속하지 않고 매치 전체에 하나뿐인가?
     예 → GameState
```

**적용 예시 — 이 게임의 실제 값들**

| 값 | 판정 | 어디에 | 근거 |
|---|---|---|---|
| 매치 남은 시간 | 매치당 1개 → Q3 | **GameState** (종료 시각 절대값 1개만) | `매치진행_게임모드_역기획서.md:88, 319` |
| 크레딧 | 죽어도 유지 + 본인만 정확히 알면 됨 | **PlayerState** | `경제_크레딧_소비아이템_역기획서.md:37` |
| 레벨 | 죽어도 유지 + 적 HUD에 표시됨 | **PlayerState** (전체 복제) | `성장_레벨_숙련도_특성_역기획서.md:286` |
| 경험치 누적 | 죽어도 유지 + 남이 볼 이유 없음 | **PlayerState** + `COND_OwnerOnly` | `성장_레벨_숙련도_특성_역기획서.md:285` |
| 체력 / 상태이상 | 죽으면 사라짐 | **Pawn**의 컴포넌트 | `스탯_데미지공식_역기획서.md:318` |
| 개인 폭사 잔여 타이머 | 죽으면 사라짐 + 본인만 | **Pawn 또는 PlayerState** + `COND_OwnerOnly` | `매치진행_게임모드_역기획서.md:200, 321` |
| 팀 투표 상태 | 팀 단위 | **GameState**의 팀 배열 | `매치진행_게임모드_역기획서.md:252` |
| HUD 오버레이 토글 | 복제 안 함 | **PlayerController / 위젯 로컬** | `UI_HUD_역기획서.md:162` |

### 2.3 ⚠ 인벤토리는 Pawn인가 PlayerState인가 — 미결

이 게임은 **사망 후 부활이 있다** (`매치진행_게임모드_역기획서.md:251` 자동 → 유료 → 불가 3단 전환). 그래서 판단 기준 Q1이 애매해진다.

| 안 | 배치 | 장점 | 단점 |
|---|---|---|---|
| **A. Pawn** | 캐릭터에 인벤토리 컴포넌트 | "죽으면 아이템을 떨군다"가 자연스럽다. 릴리번시가 캐릭터를 따라간다 | 부활 시 인벤토리를 서버가 명시적으로 복원해야 한다 |
| **B. PlayerState** | 플레이어에 인벤토리 컴포넌트 | 부활해도 인벤토리가 자동 유지. 재접속 복원(§8)이 공짜 | PlayerState는 `bAlwaysRelevant = true`(`PlayerState.cpp:25`) — **24명분 인벤토리가 전원에게 복제될 위험.** `COND_OwnerOnly`를 반드시 걸어야 한다 |

> **결정 필요.** **사망 시 아이템 드롭은 확인됐다** — `../이터널리턴_역기획서.md:151`, `:1140` ("크래프팅이 PvP의 보상 구조 자체"). 상세는 [`장비_아이템_역기획서.md`](장비_아이템_역기획서.md) §7 이 담당한다.
> 다만 **부활 시 인벤토리가 유지되는지, 자동 부활에도 떨구는지는 여전히 (미확인)** 이라 결론이 나지 않는다.
> **잠정 권장: 안 A (Pawn).** 이유는 `UI_HUD_역기획서.md:101` 이 이미 "인벤토리는 `COND_OwnerOnly`, 남의 인벤토리를 클라가 받으면 그대로 정보 유출"이라고 못 박았고, `bAlwaysRelevant`인 PlayerState에 큰 배열을 얹는 것이 그 원칙과 가장 충돌하기 때문이다. **자체 결정값이며 원작 확인값이 아니다.**

## 3. 팀 정보를 어디에 둘 것인가 — 8팀 구조의 핵심 결정

**팀 ID는 이 게임에서 가장 많이 읽히는 값이다.** 데미지 판정의 대상 유효성 게이트(`전투판정_상태이상_역기획서.md:69` 게이트 [1] "팀 판정"), 레니의 팀 분기 스킬(`:229`), 팀 시야, 미니맵 색, 승리 판정이 전부 여기 의존한다.

### 3.1 배치 결정

| 후보 | 판정 |
|---|---|
| **`AERPlayerState::TeamId` (`Replicated`)** | ✅ **채택.** 사망해도 팀은 안 바뀐다(Q1: 아니오). 전원이 알아야 한다(적팀 구분 = 색·아이콘). `PlayerState`는 `bAlwaysRelevant`라 **팀 판정이 필요한 시점에 반드시 존재한다** |
| `AERCharacter::TeamId` | ❌ 사망 시 Pawn이 파괴되면 팀 정보가 사라진다. 관전 중인 죽은 플레이어의 팀을 알 수 없다 |
| `AERPlayerController::TeamId` | ❌ 다른 클라에는 PC 인스턴스가 없다. 적의 팀을 클라가 알 수 없다 |
| `AERGameState`의 팀→플레이어 맵 | ⭕ **병행한다.** 팀 단위 조회(팀 생존 여부, 팀 투표)는 여기서 한다. **단일 진실 원천은 PlayerState이고, GameState는 인덱스다** |

### 4.2 이 장르에 몇 Hz가 필요한가

**정직하게: 측정하지 않았으므로 단정하지 않는다.** 판단 재료만 정리한다.

| 근거 | 함의 |
|---|---|
| 이 게임에 **히트스캔 즉발 판정이 없다.** 투사체는 21~40 m/s의 이동체이고(`전투판정_상태이상_역기획서.md:229`), 대상 지정 스킬은 사거리 검사 후 확정 적중이다 | 서브프레임 정밀도가 FPS만큼 요구되지 않는다 → **30Hz로 충분할 가능성이 높다 (미측정)** |
| CC 지속시간이 **0.5~1.3초** 단위다 (`전투판정_상태이상_역기획서.md:120`) | 33ms(30Hz) 해상도는 CC 만료 판정에 문제없다 |
| 클릭 이동 기반 탑다운이다 | 조준 정밀도가 틱레이트에 직접 걸리지 않는다 |
| **반대 근거:** 24명 동시 접속이다 | 틱레이트를 2배로 하면 서버 CPU와 상행 대역폭이 **선형이 아니라 연결 수 × 틱레이트로 곱해진다** |

> **권장:** **프로토타입은 프로젝트에 이미 설정된 60Hz를 유지**하고, 24명 부하 테스트를 통과한 뒤 **30Hz로 내려도 체감이 같은지 검증**한다. 60→30으로 내리는 것은 ini 한 줄이지만, 30에서 시작해 "느리다"는 인상을 받으면 원인이 틱레이트인지 다른 곳인지 구분이 안 된다.
>
> **측정 방법 (실제로 존재하는 명령으로만 적는다):**
> - `NET DUMPSERVERRPC` — 서버가 받은 RPC 통계 (`Engine/Private/NetDriver.cpp:3699`)
> - `NET DUMPDORMANCY` / `NET ACTIVE` / `NET ALLDORMANT` — 도먼시·활성 액터 확인 (`NetDriver.cpp:3703`, `:3446`, `:3456`)
> - `stat unit` 으로 서버 프레임 시간, `Unreal Insights`의 Networking Insights로 채널별 바이트 (**정확한 트레이스 채널명은 (미확인)**)

이 게임은 팀 범위 복제를 최소 2곳에서 요구한다:
- 팀원 보유 재료 아이콘 (`UI_HUD_역기획서.md:101` — "재료 아이콘용 축약 배열을 따로 두는 편이 안전하다")
- 팀 핑 (`UI_HUD_역기획서.md:161` — "`Server` RPC → 서버 검증 → `NetMulticast`(팀 한정)")

> **권장 대응:** 팀 범위가 필요한 값은 **별도의 축약 구조체를 만들어 `GameState`에 팀별 배열로 두거나**, 전체 복제가 정보 유출인 경우에는 **`Client` RPC로 팀원에게만 개별 전송**한다.
> `NetMulticast`는 **관련 있는 모든 연결에 간다 — "팀 한정 멀티캐스트"는 존재하지 않는다.** `UI_HUD_역기획서.md:161` 의 "`NetMulticast`(팀 한정)"은 **구현 불가능한 표현이며, 팀원 각각에게 `Client` RPC를 보내는 것으로 읽어야 한다.** (그 문서에 수정 제안으로 남긴다 — 이 문서가 임의로 고치지 않는다.)

### 6.1 `WithValidation` 이 실제로 하는 일

`WithValidation` 을 붙이면 UHT가 **`_Validate` 함수를 요구**한다. 이 함수가 `false`를 반환하면 —

1. 엔진이 `RPC_ValidateFailed(Reason)` 로 실패 사유를 기록한다 (`CoreUObject/Public/UObject/CoreNet.h:782`, 구현 `CoreUObject/Private/UObject/CoreNet.cpp:608-611`).
2. `FObjectReplicator::ReceivedRPC` 가 사유가 남아 있음을 확인하고 **`LogRep, Error` 로 로그를 찍은 뒤 `false`를 반환한다** (`Engine/Private/DataReplication.cpp:1389-1392`).
3. 그 `false`가 `ReceivedBunch`까지 전파되고 (`DataReplication.cpp:1160-1164`),
4. **`UActorChannel::ReceivedBunch` 가 연결을 끊는다** — `Connection->Close(ENetCloseResult::ObjectReplicatorReceivedBunchFail)` (`Engine/Private/DataChannel.cpp:3275`, `:3286`).
5. 클라이언트 쪽에는 `ENetworkFailure::ConnectionLost` 또는 `FailureReceived` 로 통지된다 (`Net/Core/Public/Net/Core/Connection/NetEnums.h:21, 26`).

> ⭐ **즉 `_Validate` 실패는 "요청 무시"가 아니라 "접속 끊김"이다.**
> 이 프로젝트가 24명 팀 게임이라는 점에서 이건 중대한 함의를 갖는다 — **`_Validate` 에 "게임 규칙 위반"을 넣으면 안 된다.**
>
> | `_Validate` 에 넣을 것 | `_Implementation` 에 넣을 것 |
> |---|---|
> | **파라미터 자체가 불가능한 값** — `NaN`, 음수 인덱스, 배열 범위 초과, 존재하지 않는 `FName` | **게임 규칙 위반** — 쿨다운 미완료, 크레딧 부족, 사거리 초과, 사망 상태 |
> | → 정상 클라가 절대 보낼 수 없는 값 = **조작된 패킷** → 끊어도 된다 | → 렉·타이밍으로 정상 클라도 보낼 수 있다 → **조용히 무시하고 리턴** |
>
> 이 구분을 안 하면 **핑이 튄 팀원이 스킬을 눌렀다가 접속이 끊긴다.** 팀 게임에서 이건 치명적이다(§8).

### 6.2 RPC 금지 사항

- **RPC에 무거운 로직을 넣지 않는다** (`CLAUDE.md` §6). RPC 함수는 검증 후 실제 처리 함수를 호출만 한다.
- **연출을 `Reliable NetMulticast`로 보내지 않는다.** 신뢰 채널이 막히면 게임플레이 복제까지 밀린다. 연출은 `Unreliable`.
- **매 프레임 RPC 금지.** `UI_HUD_역기획서.md:256` 이 이미 같은 지적을 했다 — "매 획득마다 RPC를 보내는 대신 접속 시 1회 동기화".
- **`Server` RPC의 호출 빈도에 서버측 상한을 둔다.** 엔진에 RPC DoS 감지가 있으나(`DataReplication.cpp:1295-1308`) 기본 비활성이다(`BaseEngine.ini` `[DDoSDetection] bDDoSDetection=false`, `:1647`). 게임 로직 차원의 쿨다운으로 막는다.

## 7. 세션 / 매치메이킹

**아무 문서도 다루지 않은 영역이다.** 현재 프로젝트 설정은 `Config/DefaultEngine.ini:70-71` 의 `[OnlineSubsystem] DefaultPlatformService=NULL` — **온라인 서브시스템이 사실상 꺼져 있다.**

### 7.1 전체 흐름

```
[클라] 로그인 → 로비 위젯
        ↓ 실험체·특성·전술스킬·파밍 루트 사전 저장 (매치진행_역기획서.md:53)
[클라] 파티 구성 (1~3인)  ─── 3인 미만이면 랜덤 매칭으로 채움
        ↓ "매치 찾기"
[매치메이커] 대기열 적재 → 24명(8팀 × 3) 성립 대기
        ↓ 성립
[매치메이커] 데디 서버 프로세스 spawn (맵 URL + 매치 파라미터)
        ↓ 서버 Listen 시작 → 접속 정보(IP:Port)를 24명에게 전달
[클라] ClientTravel("IP:Port") → 서버 PreLogin → Login → PostLogin
        ↓ AGameSession::ApproveLogin 으로 정원(24) 검사
[서버] 24명 전원 접속 확인 (또는 타임아웃) → 팀 배정 확정 → 매치 시작
        ↓ 매치 진행 (§1.2)
[서버] CheckMatchEnd() → 순위 확정 (매치진행_역기획서.md:305 탈락 시각 역순)
        ↓
[서버] 결과를 백엔드로 전송 → 전원에게 결과 화면 복제 → ClientTravel(로비)
        ↓
[서버] 프로세스 종료
```

**엔진이 이미 제공하는 진입점 — 직접 만들지 않는다** (`CLAUDE.md` §1):

| 지점 | 심볼 | 여기서 할 일 |
|---|---|---|
| 접속 승인 | `AGameModeBase::PreLogin` (`GameModeBase.h:293`) → `AGameSession::ApproveLogin` (`GameSession.h:78`) | 정원·매치 참가 자격 검사. `ErrorMessage`를 채우면 거절 |
| 정원 | `AGameSession::MaxPlayers` (`GameSession.h:37`), `MaxSpectators` (`:33`), `MaxPartySize` (`:41`) | **`MaxPlayers = 24`** |
| PC 생성 | `AGameModeBase::Login` (`GameModeBase.h:323`) → `InitNewPlayer` (`:535`) | PlayerState 초기화, **팀 배정** |
| 접속 완료 | `AGameModeBase::PostLogin` (`GameModeBase.h:326`) → `GenericPlayerInitialization` (`:545`) | 스폰, 시작 지역 배치 |
| 퇴장 | `AGameModeBase::Logout` (`GameModeBase.h:341`) | §8 |
| 세션 클래스 지정 | `AGameModeBase::GameSessionClass` (`GameModeBase.h:88`), `GetGameSessionClass()` (`:80`) | `AERGameSession` 파생 지정 |

### 7.2 24명을 어떻게 채울 것인가

`매치진행_게임모드_역기획서.md:131` 이 이미 정확히 지적했다:

> "24명 로비 하나를 채우려면 동시접속이 최소 수백 명 단위로 필요하다. 모드가 2개면 필요 인구가 2배가 아니라 **양쪽 다 매칭이 안 되는 상태**가 된다."

이 지적은 **모드를 늘리지 말라**는 결론으로 이어졌지만(`:135` 표), 모드가 하나여도 **개발 중에는 인구가 0이다.** 기술적 대응:

| 대응 | 내용 | 판정 |
|---|---|---|
| **`TeamCount`를 데이터로 낮춘다** | 프로토타입은 **2~4팀(6~12명)** 으로 시작. `매치진행_역기획서.md:138` 이 이미 `TeamSize`/`TeamCount` 데이터화를 요구했다 | ✅ **가장 싸고 확실하다. 이것부터 한다** |
| **봇으로 빈 슬롯 채우기** | 대기 시간이 상한(예: 60초)에 닿으면 남은 슬롯을 AI로 채우고 시작. 원작도 신규 유저에게 봇 로비를 배정한다 (`매치진행_역기획서.md:475` [S26]) | ⭕ **필요하다. 단 봇 AI 자체는 이 문서 범위 밖** — 여기서 정하는 건 **"슬롯을 봇이 점유해도 서버·팀 구조가 안 깨지는가"** 뿐이다 |
| **대기 시간 완화(매칭 기준 완화)** | 시간이 지날수록 MMR 허용폭을 넓힘 | ⭕ 인구가 생긴 뒤의 문제. 지금은 필요 없다 |
| 크로스 리전 매칭 | — | ❌ 인구 문제를 지연시킬 뿐 |

> ⭐ **봇 슬롯의 네트워크 구조 요구사항** — 봇은 **`APlayerState`를 갖는 `AAIController`** 로 만든다. 이유: §3에서 팀 ID의 단일 진실 원천을 `PlayerState`로 정했기 때문에, **PlayerState가 없는 봇은 팀 판정·승리 판정·HUD 팀원 표시에서 전부 예외 분기를 만든다.** `AGameStateBase::PlayerArray`(`GameStateBase.h:55`)에 봇도 들어가야 `AddPlayerState`(`:112`) 기반 로직이 하나로 유지된다.

### 7.3 ⭐ `OnlineSubsystem` 인가 자체 매치메이킹 서버인가 — **권장을 명확히 한다**

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **A. `OnlineSubsystemNULL` + 직접 IP 접속** | 지금 상태(`Config/DefaultEngine.ini:71`). 서버를 손으로 띄우고 `open IP:Port`로 붙는다 | **추가 작업 0.** 지금 당장 24명 테스트 가능 | 매치메이킹이 없다. LAN/수동 전용 |
| **B. `OnlineSubsystemSteam` 등 플랫폼 SDK** | Steam 세션 검색·로비 | 매치메이킹·친구 초대가 공짜 | 플러그인·앱 ID·플랫폼 정책 필요. **데디 서버 1:1 모델과 로비 모델이 충돌**할 수 있다 |
| **C. 자체 매치메이킹 서버 (HTTP/WebSocket)** | 별도 백엔드가 대기열·서버 spawn·주소 배포 | 규모·정책을 완전히 통제. 봇 채우기·리전 배정도 여기서 | **게임 밖 인프라를 새로 만들어야 한다.** 프로토타입 시점에 가장 비싸다 |

> ⭐ **권장: A로 시작한다. 그리고 A를 오래 쓴다.**
>
> 근거:
> 1. **지금 프로젝트에 GameMode조차 없다.** `Source/` 에는 모듈 파일과 타겟만 있다. 매치메이킹은 **게임이 24명으로 정상 동작한 뒤**에 풀 문제다.
> 2. **A → C 전환 비용이 낮다.** A에서 필요한 것은 `ClientTravel`로 붙을 수 있는 데디 서버뿐이고, C는 그 앞단에 "어느 IP로 붙을지 알려주는 서비스"를 얹는 것이다. **게임 코드가 거의 안 바뀐다.**
> 3. **A → B 전환 비용이 높다.** `OnlineSubsystem`의 세션 API를 쓰기 시작하면 `FUniqueNetIdRepl`(`GameModeBase.h:293`의 파라미터)·세션 등록·로비 개념이 게임 코드에 스며든다. **잘못 들이면 되돌리기 어렵다.**
> 4. **B는 이 게임의 서버 모델과 미묘하게 어긋난다.** Steam 로비는 "호스트가 방을 만들고 사람이 붙는" 모델이고, 이 게임은 "매치메이커가 서버를 띄우는" 모델이다(§1.2).
>
> **다음 단계 (인구가 생긴 뒤): C.** B는 **배포 플랫폼이 확정된 뒤**에만 검토한다.
>
> ⚠ 단, A로 가더라도 **`AERGameSession`(`AGameSession` 파생)은 처음부터 만든다.** `MaxPlayers = 24`와 `ApproveLogin` 훅이 여기 있고, 나중에 C를 붙일 때 **이 클래스가 그대로 진입점이 된다.**

## 8. 접속 끊김 / 재접속

**3인 팀에서 1명이 빠지면 전투력이 33% 사라진다.** 24명 배틀로얄에서 이건 그 팀만의 문제가 아니라 **매치 밸런스 전체의 문제**다.

### 8.1 엔진이 실제로 하는 일

| 단계 | 심볼 |
|---|---|
| 타임아웃 | `ConnectionTimeout = 60.0` / `InitialConnectTimeout = 60.0` (`NetDriver.h:905`, `:897` / `BaseEngine.ini:1630-1631`) |
| 통지 | `ENetworkFailure::ConnectionLost` / `ConnectionTimeout` / `FailureReceived` (`Net/Core/Public/Net/Core/Connection/NetEnums.h:21, 23, 26`) |
| 퇴장 처리 | `AGameModeBase::Logout` (`GameModeBase.h:341`) |
| **PlayerState 보관** | `AGameMode::AddInactivePlayer` (`GameMode.h:183`) → `InactivePlayerArray` (`GameMode.h:138`) |
| 보관 기간 | `InactivePlayerStateLifeSpan = 300.f` (5분), `MaxInactivePlayers = 16` (`Engine/Private/GameMode.cpp:46-47`) |
| **재접속 시 복원** | `AGameMode::PostLogin` 이 `FindInactivePlayer(NewPlayer)` 호출 (`GameMode.cpp:115`) → 본체 `GameMode.cpp:671-720` |
| 매칭 키 | `UniqueId` 우선, 없으면 `SavedNetworkAddress` + `PlayerName` (`GameMode.cpp:685-690`) |
| 값 이관 | `OverridePlayerState` → `DispatchOverrideWith` (`GameMode.cpp:725`) → `APlayerState::OverrideWith` (`PlayerState.h:281`) |
| 유사 함수 | `APlayerState::CopyProperties` (`PlayerState.h:284`) — **seamless travel 용**. 재접속 경로는 `OverrideWith` 다 |

> ⚠ **정정: `bReconnect` 라는 심볼은 UE 5.4.4 엔진 소스에 존재하지 않는다.**
> `grep -rn "bReconnect" C:/UnrealEngine-5.4.4/Engine/Source/Runtime/` 결과 **0건**.
> 재접속 복원의 실제 경로는 위 표의 **`InactivePlayerArray` + `FindInactivePlayer` + `OverrideWith`** 다. 문서나 대화에서 `bReconnect`를 근거로 삼지 말 것.

⭐ **즉 엔진은 "재접속 시 PlayerState 복원"을 이미 5분간 공짜로 제공한다.** 단 두 조건이 필요하다:
1. **`AGameMode`(`AGameModeBase`가 아니라)를 상속해야 한다** — `InactivePlayerArray`는 `AGameMode`에만 있다 (`GameMode.h:138`).
2. **팀 ID·크레딧·레벨이 `PlayerState`에 있어야 한다** (§2, §3에서 이미 그렇게 정했다). Pawn에 있으면 복원되지 않는다.
3. `AERPlayerState::OverrideWith` 를 오버라이드해 **복원할 필드를 명시**해야 한다. 기본 구현은 이름·id 정도만 옮긴다.

### 8.2 정책 결정 — 무엇을 할 것인가

| 안 | 내용 | 판정 |
|---|---|---|
| **A. 즉시 사망 처리** | 끊기면 캐릭터를 죽인다 | ❌ **가장 나쁘다.** 순간 렉으로 끊긴 사람이 팀을 무너뜨린다. 고의 방생(troll)도 이걸 악용한다 |
| **B. 캐릭터를 월드에 남기고 무방비 방치** | 조작 없이 서 있음 | ❌ 상대에게 공짜 킬을 준다. 팀 시야도 계속 제공된다 |
| **C. ⭐ 재접속 허용 + 그동안 AI가 조종** | 끊기면 `AAIController`가 Pawn을 `Possess`. 재접속하면 `APlayerController`가 다시 `Possess` | ✅ **채택 권장.** 팀 전력이 유지되고, 재접속 경로가 엔진 기본과 맞는다 |
| **D. 재접속 허용, 그동안 캐릭터는 무적으로 사라짐** | Pawn을 숨기고 대상 지정 불가 | ❌ 위험지대·크로노 스피어와 충돌한다. "끊고 시간을 벌기"가 전략이 된다 |

**권장안 C의 구체 규칙 — 전부 자체 결정값 (원작 처리는 (미확인))**

| 항목 | 값 |
|---|---|
| 끊김 감지 | 엔진 `ConnectionTimeout` 60초를 **그대로 두지 않는다.** 게임 로직에서 **10초** 무응답이면 AI 인계 (60초는 너무 길다) |
| AI 인계 | `Logout` 시 Pawn을 파괴하지 말고 `AERBotController`가 `Possess`. **PlayerState는 `AddInactivePlayer`로 보관** |
| 재접속 허용 시간 | `InactivePlayerStateLifeSpan` 기본 300초(5분)를 **매치 길이(15~27분)에 맞춰 상향 검토.** 매치 전체를 허용할지는 결정 필요 |
| 재접속 시 | `FindInactivePlayer` 가 성사되면 `OverrideWith`로 팀·크레딧·레벨 복원 → AI를 `UnPossess` → PlayerController가 `Possess` |
| 재접속 후 상태 | 체력·위치·인벤토리는 **AI가 플레이한 결과 그대로.** 되돌리지 않는다 |
| 봇 슬롯과의 관계 | §7.2의 봇과 **같은 컨트롤러 클래스를 쓴다.** 두 벌 만들지 않는다 |

> ⚠ **미결:** 매치 종료 순위 산정에서 "끊긴 채로 AI가 이긴 팀"을 어떻게 처리할지 **(미확인)**. `매치진행_역기획서.md:305` 의 "탈락 시각 역순" 규칙에는 이 케이스가 없다.
> ⚠ **`MaxInactivePlayers = 16` (`GameMode.cpp:47`)** — 24명 매치에서 16명 초과가 동시에 끊기면 오래된 것부터 버려진다 (`GameMode.cpp:650-655`). 24 이상으로 올릴지 결정 필요.

### 9.1 일반 규칙 — 어느 것 하나도 클라를 믿지 않는다

| 축 | 규칙 | 위반 시 생기는 핵 |
|---|---|---|
| **위치** | 이동 결과를 서버가 검증한다. 텔레포트·강제 이동은 전부 서버가 실행 | 스피드핵, 텔레포트핵 |
| **시야** | ⭐ **"클라에 보내고 안 그리기"는 치팅 방지가 아니다.** 안 보여야 하는 액터는 **복제 자체를 막는다** | 맵핵 — 패킷만 봐도 위치가 나온다 |
| **데미지** | 계산은 서버 한 곳(`스탯_데미지공식_역기획서.md:124` `if (!HasAuthority()) return 0.f;`). 클라는 결과만 받는다 | 데미지핵, 원킬핵 |
| **쿨다운 / 자원** | 서버가 타이머와 잔액을 소유. 클라 값은 표시용 | 쿨다운 무시, 무한 크레딧 |
| **아이템 / 제작** | 획득·소비·제작 전부 서버 검증 후 반영 | 아이템 복사 |
| **입력 빈도** | 서버가 요청 빈도에 상한 | RPC 스팸 |
| **정보** | 본인만 알아야 할 값은 `COND_OwnerOnly`. 팀만 알 값은 `Client` RPC (§5.5) | 정보 우위형 핵 |

> ⭐ **가장 중요한 한 줄: "클라이언트에 보내지 않은 정보만이 숨겨진 정보다."**

## 10. GAS와 이 아키텍처의 접점

이 프로젝트는 **GAS 기반으로 만든다** (`CLAUDE.md` §8). 아키텍처에 영향을 주는 결정은 하나다.

### 10.1 ⭐ ASC 배치 — **권장: PlayerState** (확정은 F00-02)

> ⚠ **아직 코드로 확정되지 않았다.** 결정 자리는 [`Docs/Task/F00_GAS기반세팅/02_ASC_배치결정.md`](../../Task/F00_GAS기반세팅/02_ASC_배치결정.md) 이고, 이 절은 그 판단의 **네트워크 측 근거**만 제공한다.

| 배치 | 맞는 경우 | 이 게임에서의 함의 |
|---|---|---|
| ASC on Pawn | 사망 시 능력·속성이 사라져도 되는 게임 | 부활마다 어트리뷰트를 서버가 재초기화해야 한다. Pawn 파괴와 함께 진행 중인 GE가 전부 사라진다 |
| ⭐ **ASC on PlayerState** | **부활이 있고 성장이 캐릭터 수명보다 긴 게임** (MOBA 표준) | 부활해도 레벨·스킬 레벨·숙련도가 유지된다 |

**이 게임은 후자다** — 부활이 3단으로 존재하고(`매치진행_게임모드_역기획서.md:251`), 레벨·숙련도·특성이 매치 전체에 걸쳐 누적된다.

**배치에 따라오는 설정 두 가지** (`Docs/Task/F00_GAS기반세팅/` 참조):

- ⚠ `APlayerState` 는 **`NetUpdateFrequency = 1`** (`Engine/Private/PlayerState.cpp:26`). 그대로 두면 **체력바가 초당 1회 갱신된다.** 반드시 올린다.
- ⚠ `bAlwaysRelevant = true` (`:27`). 24명분 ASC가 전원에게 관련 액터가 되므로 **복제 모드를 `Mixed`** 로 설정한다.
  `Minimal` 은 소유자가 있는 ASC에서 동작하지 않는다 — 엔진 주석: *"this does not work for Owned AbilitySystemComponents (Use Mixed instead)"* (`AbilitySystemComponent.h:87`).

### 10.2 예외 — 야생동물은 Pawn에 ASC를 붙인다

야생동물·보스는 PlayerState가 없다. 즉 이 프로젝트는 **두 배치가 공존한다.**
`IAbilitySystemInterface::GetAbilitySystemComponent()` 를 양쪽 다 구현하면 **호출부는 어디에 붙었는지 몰라도 된다.**

야생동물 ASC는 개체가 120~200마리이므로 복제 모드를 **`Minimal`** 로 둔다 (소유 컨트롤러가 없어 동작한다).

### 10.3 §2의 데이터 배치와의 관계

§2.2에서 정한 배치가 그대로 유효하다 — 레벨·크레딧·숙련도·특성은 PlayerState, 체력·상태이상은 어트리뷰트다.
다만 **체력·CC를 Pawn의 자체 컴포넌트에 두지 않는다.** ASC의 어트리뷰트와 GE가 그 자리를 맡는다.

### 10.4 영향받지 않는 부분

§1(서버 모델) · §4(틱레이트) · §5(릴리번시) · §7(세션) · §8(재접속) · §9(치팅 원칙)은 **GAS와 무관하다.**
GAS는 능력·속성의 복제 방식을 바꿀 뿐, 프레임워크 클래스 배치와 세션 구조를 바꾸지 않는다.
